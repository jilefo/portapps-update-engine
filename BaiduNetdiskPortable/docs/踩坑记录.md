> 本项目（及姊妹项目）在便携化过程中踩过的坑与最终解法，**勿重复**。
> Custom.nsh 头部注释中的编号与本文件条目一一对应。

## 1. `node_modules\koffi\...\koffi.node not found in ...app.asar`

**现象**：启动即弹 `A JavaScript error occurred in the main process`：

```
Uncaught Exception:
Error: ENOENT, node_modules\koffi\build\koffi\win32_x64\koffi.node not found in
D:\...\BaiduNetdiskPortable\dist\BaiduNetdiskPortable\...app.asar
    at createError (node:electron/js2c/asar_bundle:2:1312)
    at Object.func [as .node] (node:electron/js2c/asar_bundle:2:20301)
    at Module._compile (node:internal/modules/cjs/loader:1141:14)
```

**根因**：不是文件丢失。百度把 `module\BrowserEngine\resources\app.asar`
里的 17 个 `.node` 原生模块**全部封在 asar 归档内，且未标记 `unpacked`**。
Node 的 `process.dlopen` 必须拿到**真实文件路径**才能 `LoadLibrary`，
无法从 asar 归档内加载 DLL。Electron 的 `.node` 加载器会转去
`<asar>.unpacked\` 找同名文件，找不到就抛上面这个 ENOENT。

**为什么 CherryStudio 不犯**：CherryStudio 的 app.asar 头部里
`koffi.node` 条目带 `"unpacked": true`，运行时从
`app.asar.unpacked\...` 加载，一切正常。

**解法**（已落地，勿改回去）：
把 Windows 侧原生模块解到 asar 旁的 `.unpacked` 目录，asm 头部不用动：

```powershell
python scripts\asar_unpack.py "<...>\module\BrowserEngine\resources\app.asar"
```

解包 7 个 win32 侧模块（koffi、electron-clipboard-ex、uiohook-napi、
@baidu/pc-electron-native-util、@baidu/electron-panel-window、
windows-notification-state、windows-quiet-hours），共约 3.5 MB，
每个都按 asar 头部 `integrity.blocks` 的 SHA256 校验通过。

> darwin/macOS 条目（约 8 MB）不解——Windows 包用不到。

**工具**：`scripts\asar_unpack.py`（解析 asar 头部 JSON 变体、按 `offset`
从数据区抽取、SHA256 对账）。**asar 数据区起点 = `align4(16 + 头部JSON长度)`**，
漏掉这 3 字节对齐填充会全量哈希不符（见 `_dbg_asar_offset.py` 的定位过程）。

**任何 Electron 应用便携化都要查这项**：打包方忘了 `asarUnpack` 时表现相同。

## 2. 悬空 Junction 让启动器静默卡死

**现象**：双击 `BaiduNetdiskPortable.exe` 只剩启动器窗口，主程序不出现，
**没有任何报错**，能卡几分钟。

**根因**：`%APPDATA%\baidunetdisk` 等 5 个宿主路径仍是 Junction，
但目标指向**搬迁前的旧路径** `<旧工作区>/BaiduNetdiskPortable\...`，
该目录已删除。真目录被替换成悬空联接后，启动器的 `NP_JunctionCreate`
判断 `${If} ${FileExists} "${_HOST}"` 为真 → 走「先删除宿主再 mklink」分支，
删除/重建流程在悬空目标上空转，主程序迟迟不启动。

**解法**：把仍指向不存在目标的联接点摘掉（`Directory::Delete` 只删联接本身，
不递归目标，不会碰到包内 Data）：

```powershell
[System.IO.Directory]::Delete("$env:APPDATA\baidunetdisk", $false)
```

**判定口诀**：`Get-Item ... | % Target` 取到目标路径后 `Test-Path` 为假
⇒ 悬空联接 ⇒ 可安全摘除。

## 3. 移植目录后 `%APPDATA%` 数据泄漏

**现象**：直接跑 `App\BaiduNetdisk\BaiduNetdisk.exe`（绕开启动器）做排障时，
应用把数据写进了真实 `%APPDATA%\baidunetdisk` 等目录（本次实测涌入约 44 MB），
而便携包的 `Data\settings\` 里什么都没有。

**根因**：数据重定向**只由启动器建立**（`SetEnvironmentVariable` + Junction）。
绕过启动器 = 没有任何重定向，应用按安装模式写宿主 profile。

**防法**：排障可以直接跑 exe，但事后必须把泄漏目录清掉
（已移至 `GreenSoftMake\Backups\appdata-leak-20261017\`），
否则下次启动器会把这些内容 robocopy 合并进包内 Data，污染便携数据。

## 4. 启动器「慢」不是故障

**现象**：启动器窗口停留 1–2 分钟才拉起主程序，排查时容易误判为卡死。

**原因**：`Custom.nsh_PreExecPrimary` 里 5 个 `NP_JunctionCreate` 逐个
robocopy + 强删宿主目录，`%APPDATA%\baidu` 体量可达数万文件
（GenFlowPro 自带 node 运行时），耗时集中在这里，**不是** hung。

**排错口径**：看 `Data\settings\junction-blocked-*.log` 有没有新增；
没有新增就是正常慢，有新增才是被锁死（见第 2 条）。

## 5. robocopy `/MIR` 不清源端

**现象**：`robocopy 源 目标 /MIR` 跑完 rc=1（成功），源目录却一个字节没少，
误判成「文件仍被占用」。

**根因**：`/MIR` 只做镜像同步目标，**不会删源**；搬空并删源必须加 `/MOVE`。

**正确写法**：`robocopy <源> <空目录> /MOVE /E /R:1 /W:1`（PowerShell 调用；
Git Bash 会把 `/E` `/MOVE` 当路径改写，rc=16）。
