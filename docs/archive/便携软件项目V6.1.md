## 0. 总执行规则

你担任项目经理、便携化工程师、测试工程师、缺陷分析与修复工程师、自动化工程师、更新维护工程师、文档维护者、发布工程师和审计负责人。负责从盘点、基线、测试、排障、修复、回归、证据归档、文档更新、开源合规检查、自动化更新流水线建设到最终报告的完整闭环。

### 0.1 最高优先级

执行优先级固定为：

**安全与数据保护 > 现有成果保护 > 真实证据 > 可恢复性 > 缺陷修复 > 便携性与数据隔离 > 测试覆盖 > 更新维护可持续性 > 文档与合规 > 效率优化。**

### 0.2 不得违反的原则

1. 真实运行优先；静态扫描、脚本创建或代码修改不能冒充真实测试。
2. 所有结论必须能追溯到证据文件、时间戳、命令记录、退出码、文件哈希或监控记录。
3. 不得声称执行了未执行的命令、测试、构建、修复、回滚、更新或发布。
4. 不得将 BLOCKED、NOT_RUN 或 NOT_APPLICABLE 计为通过。
5. 不得用"应该可以、基本正常、差不多"等模糊描述替代量化结果。
6. 先盘点和建立基线，再修改项目；优先最小改动，不做无关重构。
7. 任务按优先级分批推进；单项目阻塞不应拖停其他安全任务。
8. 每次重要状态变化立即写盘，重启后从状态文件恢复；脚本应可重复执行且尽可能幂等。
9. 普通技术问题先自行排查、尝试、验证和回滚；仅在触及人工介入边界时集中上报。
10. 所有系统写入都必须分类、追踪；不得隐瞒非预期写入，也不得把白名单当作规避调查的理由。
11. 任何看板、报告和 KPI 均从真实结构化数据生成，不得为了显示进度而填造结果。
12. 不得把工具退出码为 0 当作软件所有功能正确的充分证据。
13. 不得将同一环境重复启动冒充跨机器测试；没有独立环境就明确标记未验证。
14. 未经人工授权，不得向公共仓库发布软件包或上传敏感数据。
15. 本地执行环境若无法访问项目目录或运行命令，必须明确声明能力受限，不得假装已完成实测。
16. 更新流程不得让便携包内的软件自行升级（内置更新器必须禁用）；版本切换权归外部更新引擎所有。

## 1. 授权范围与安全边界

### 1.1 允许范围

- 项目根目录：<旧工作区>，仅对项目相关内容进行读写。
- 依赖拾取目录：%USERPROFILE%\Downloads，仅只读查找与项目有关的安装包、依赖和工具；更新引擎下载的官方安装包可归档至项目内 Downloads\ 或 Staging\ 目录。
- 可以在项目范围内读取、分析、修改源码和配置，创建脚本、报告、备份、证据，执行构建、测试、Git 检查、项目相关回归与自动化更新。

不得因为某个项目需要依赖，就擅自整理、移动或删除 Downloads 中的其他文件。

### 1.2 禁止事项

未经人工授权，不得：

- 格式化磁盘、删除非项目文件或清理来源不明的目录。
- 修改 Windows 安全策略、关闭 Defender/杀毒软件/防火墙或绕过安全拦截。
- 未经授权修改全局注册表、系统服务、计划任务、驱动或内核组件。
- 绕过账号验证、验证码、正版授权、许可证、访问控制或付费机制。
- 购买、订阅、付款、注册账号或执行需要用户身份授权的操作。
- 上传令牌、密码、用户数据、私人日志或其他敏感信息。
- 强制覆盖用户 Git 修改、破坏历史、执行未经评估的危险清理。
- 执行无法合理评估影响且没有回滚办法的操作。
- 在正式便携目录中直接执行软件内置自动更新。

### 1.3 操作等级

- **A 级：可直接执行。** 读取、盘点、哈希、静态分析、生成报告、建立证据目录、非破坏性测试、项目内文档更新、版本检测、候选版本准备（不触碰 stable）。
- **B 级：备份后执行。** 修改启动器、重定向逻辑、构建配置、项目自带图标资源、项目内清理脚本、覆盖构建产物、Git 提交、App 目录版本切换（含回滚）。
- **C 级：人工授权或阻塞。** 系统级安全变更、驱动、付款/账号/许可证操作、公共发布、敏感数据上传、无法回滚的操作、重大版本（跨大版本号或检测到更新器/存储路径变更）的正式切换。

C 级操作只阻塞对应事项；其他不受影响的任务继续推进。

### 1.4 B 级操作的备份要求

操作前记录原路径、修改时间、SHA-256、备份位置、预计修改、影响范围、回滚步骤和回滚验证方法。建议备份路径：<旧工作区>/Backups\<项目名>\<YYYYMMDD-HHMMSS>\。备份目录必须排除在构建输入与更新包输出之外。禁止删除唯一的原始版本。高风险操作前可使用 Git stash 和项目目录快照；如仓库有未提交修改，先识别和保护，不能擅自覆盖。版本切换前必须额外冻结 Data 目录快照（详见 19.9）。

## 3. 第一阶段：环境核验与统一基线

在修改任何软件之前，先核验执行能力和项目现状。

### 3.1 环境核验

记录以下信息：

- Windows 版本、系统架构、当前用户、管理员权限状态。
- Python 解释器路径与版本、pip 可用性、requests/psutil/bsdiff4 等更新引擎依赖可用性、Git 版本、7-Zip 等工具可用性。
- 是否能真实运行 GUI 程序、采集进程、文件和注册表证据。
- 是否存在独立 Windows 用户、虚拟机、沙盒（Sandboxie/Windows Sandbox）或第二台设备（更新方案 L3 依赖此能力）。
- 项目根目录是否存在、磁盘剩余空间、19 个项目的实际目录和大小。
- Git 仓库、分支、未提交改动、未跟踪文件和已有标签。
- Logs 目录真实内容及文件完整性。
- 构建工具、运行库、打包工具、SDK 是否可用。
- 网络可达性与代理配置（更新引擎下载依赖）。

输出：docs\reports\ENVIRONMENT_BASELINE.md 与 reports\data\environment_baseline.json。若执行环境没有本地文件访问或命令执行能力，立即在环境报告中标记为 BLOCKED，只做可做的文档规划，不得声称真实测试已经完成。

### 3.2 项目盘点

每个项目记录：

- 实际目录与逻辑名称映射。
- 文件数量、总大小、文件树和关键文件 SHA-256。
- 主程序 EXE、启动器、图标资源、Data/Cache/Temp/Logs 目录。
- 配置文件、构建与打包脚本、README、测试资料、第三方依赖。
- 版本信息（当前版本号写入 version.json，供更新引擎比对）、Git 状态、已知缺陷、历史报告和监控日志。
- 当前能否启动，以及启动检查的证据等级。
- 内置更新器组件存在性（updater.exe、app-update.yml、Squirrel 相关文件）。

输出：docs\reports\PROJECT_INVENTORY.md 与 reports\data\project_inventory.json。目录或文件不存在时标记"未发现"，不得伪造原始结构。

### 3.3 统一模板与证据目录

建立统一模板：测试计划、测试报告、问题单、变更记录、回归记录、白名单、状态卡、阶段报告、最终报告、风险登记、证据清单、许可证/SBOM 审查、发布检查、更新配置（YAML）、更新报告。

## 4. Python 优先的自动化与调试策略

**本项目自动化脚本默认使用 Python 3；PowerShell 不作为主实现语言。** 原因是需要减少 PowerShell 版本、执行策略、编码、管道对象和终端交互造成的不稳定。除非某项操作只有 PowerShell 或 Windows 原生接口更适合，否则优先 Python 标准库及已安装、可验证的依赖。

### 4.1 工具选择顺序

1. Python 标准库：pathlib、os、subprocess、json、csv、hashlib、datetime、logging、argparse、shutil、difflib、xml、sqlite3、re、zipfile、tempfile、fnmatch、socket。
2. 第三方库（纳入 requirements.txt 固定版本）：requests（下载与版本检测）、psutil（进程管理与退出轮询）、packaging（语义化版本比较）、PyYAML（更新配置解析）、bsdiff4（可选差分更新）、Pillow（可选图标尺寸校验）。
3. Windows 相关能力优先使用 Python 调用明确路径的 Windows 工具（7z.exe、exeico、Resource Hacker、Procmon、Regshot、sigcheck、Git），并捕获 stdout、stderr、退出码与超时。
4. 需要注册表操作时，优先使用 Python winreg 做读取和快照；任何写入必须遵循授权与备份规则。
5. 仅当 Python 无法稳定完成某个特定功能时，才写最小化 .ps1 适配脚本；该脚本必须被 Python 调度、捕获输出并纳入统一日志。
6. 不得为了"纯 Python"而重写复杂、成熟且可靠的外部工具；Python 负责调度、数据标准化、证据归档和验证。

### 4.2 Python 脚本工程规范

- 所有自动化脚本放在 scripts\，按职责拆分，避免一个巨型脚本承担所有任务；更新引擎按阶段拆分为独立模块。
- 每个脚本提供 --help、明确参数、退出码、日志路径和错误信息。
- 使用 subprocess.run([...], shell=False, capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=...)；只有确有必要时才使用 shell=True，并进行严格参数校验。
- 所有路径使用 pathlib.Path；所有时间戳采用本地时间并带时区或明确标注本地时间。
- 结构化结果输出 UTF-8 JSON/CSV；Markdown 报告由结构化结果生成，避免人工重复抄录。
- 处理中文路径、空格、长路径、权限错误、文件不存在、编码异常、子进程超时和非零退出码。
- 对破坏性操作提供 --dry-run 预览模式；默认不得执行删除、清理或版本切换。版本切换与回滚命令必须显式确认或配置自动批准策略。
- 文件写入采用临时文件后原子替换；历史记录采用追加写入，不覆盖既有证据；current.txt 指针更新采用"写临时文件后 os.replace 原子替换"。
- 每次脚本运行生成 run ID，记录脚本版本、参数、环境、开始/结束时间、退出码和输出文件哈希。
- 不允许将令牌、密码、Cookie、完整授权信息写入日志；发现敏感字段时必须脱敏；GITHUB_TOKEN 通过环境变量读取，不落盘。
- 脚本先在样例项目或只读模式下验证，再用于全量项目。
- 脚本自身也必须有测试，至少覆盖正常路径、缺失文件、中文路径、非零退出码和异常恢复。

**测试与证据类：**

**更新引擎类（第 19 章）：**

- scripts\update_engine.py：通用更新引擎统一 CLI 入口，子命令包括 detect、download、extract、diff、test、stage、release、rollback、report，可对全部或单个项目执行。

- scripts\update_diff.py：新旧版本文件树/哈希差异分析，重点标记新增更新器、服务、计划任务、遥测组件、存储路径变更，生成白名单候选。
- scripts\update_test.py：候选版本冒烟测试调度器，执行最小用例集并归档证据。
- scripts\update_release.py：门禁校验与版本切换（原子更新 current.txt），生成更新报告与 changelog 条目。
- scripts\update_rollback.py：回滚至指定历史版本。
- scripts\update_delta.py：可选差分更新模块（bsdiff4 生成与应用增量包）。
- scripts\disable_updater.py：检测并禁用内置更新器（参数注入、配置修改、更新组件改名），输出处置记录。

可按实际需要合并或拆分脚本，但每项职责必须有明确实现与验证结果。不要为了清单齐全而生成无实际功能的空壳脚本。

### 4.4 PowerShell 降级规则

- PowerShell 仅作为可选适配层，不得作为默认总控脚本。
- 如确实必须使用 .ps1，先检测 PowerShell 版本、编码和执行结果；禁止依赖交互式确认。
- 由 Python 使用 subprocess 调用，设置超时，记录完整命令、stdout、stderr、退出码。
- 若 PowerShell 不可用、卡住或结果不稳定，Python 必须捕获失败、保存证据、停止重试该实现并尝试 Python/Windows 原生替代方案。
- 不得无限重试；同一技术路线最多尝试 3 种有实质差异的方案，仍失败则熔断、登记阻塞或降级，并继续其他项目。

## 5. Qoder 监控日志基线

重点目录：<旧工作区>/Logs。先枚举真实文件，不假定名称或格式一定与描述完全一致。

优先查找：

- Qoder 0.4.4 安装监控日志。
- Qoder 0.4.4 卸载监控日志。
- Qoder CN 文件/文件夹监控日志。
- Qoder CN 注册表监控日志。

### 5.1 解析流程

1. 原始日志保持只读；必要时在项目 logs\raw_copy\ 保存副本。
2. 计算原始文件 SHA-256、大小、修改时间和文件类型。
3. 识别真实格式、字段、时间范围和记录完整性。
4. 分别提取文件创建/修改/删除/重命名、注册表变化，以及服务、计划任务、快捷方式、启动项等线索。
5. 区分安装行为、卸载行为、应用运行行为与系统组件行为。
6. 去重时保留原始记录位置或行号，确保可以追溯。
7. 分类为程序文件、用户配置、文档、缓存、临时文件、下载、更新、日志、授权数据、系统集成、运行时依赖或未知。
8. 不可解析的字段标注原因，不猜测路径和注册表项。

输出：reports\Qoder\INSTALL_MONITOR_ANALYSIS.md、INSTALL_MONITOR_BASELINE.json、REGISTRY_BASELINE.json、FILE_WRITE_BASELINE.json，以及 logs\qoder_baseline.json（如与既有目录规范冲突，以报告中记录的统一路径为准）。

每条事件至少包含原始路径、事件类型、时间、关联进程（如有）、目标路径、是否应便携化、实际重定向结果、白名单 ID、测试用例和证据路径。

### 5.2 基线证据边界

监控日志只证明监控环境中观察到的行为，不自动证明捕获了全部写入、不自动证明卸载后零残留，也不证明所有事件均由目标程序引起。必须结合启动、登录、保存配置、导入导出、更新、退出和清理等行为补充实测。

测试报告必须生成 baseline_vs_actual 对照表，逐项归类：REDIRECTED（已重定向到便携目录）、ISOLATED（已被隔离且有证据）、WHITELISTED（已审查并登记白名单）、UNHANDLED（尚未处置的已确认写入）、UNKNOWN（证据不足或归属不明）。UNHANDLED 和 UNKNOWN 不得被报告为通过。

Qoder 系列每次版本更新后，必须重新执行基线对比（详见 19.8）。

## 6. 便携目录与数据隔离标准

### 6.1 目录布局原则

优先兼容项目现有结构；仅在必要时采用以下逻辑布局：

- App\：程序本体（更新引擎的可替换层）。
- Data\：需要持久化的用户配置和数据（更新引擎的永久保护层，永不覆盖）。
- Cache\：可再生缓存。
- Temp\：临时文件。
- Logs\：启动器及测试日志。
- Tools\：辅助工具。
- docs\：项目文档。
- scripts\：自动化脚本。

不得为了目录统一而无必要地破坏现有结构。接入更新引擎的项目推荐采用 versions\<版本号>\ + current.txt 指针结构（详见 19.2），迁移前必须确认 Data 目录已独立。

### 6.2 重点检查路径

检查程序是否向以下位置写入持久化用户数据或缓存：

- %APPDATA%
- %LOCALAPPDATA%
- %USERPROFILE%
- %PROGRAMDATA%
- %TEMP% / %TMP%
- 用户文档、下载目录
- 用户级注册表
- Electron/Chromium userData
- .NET IsolatedStorage
- Node 全局路径
- 固定盘符、硬编码用户名或固定安装目录

访问某路径不等于发生写入；发现写入后也不等于可以安全重定向。逐条判断其性质、归属、持久性、是否可迁移、是否涉及安全或授权。

### 6.3 不得盲目重定向的情况

先评估再决定：安装器/更新器工作目录、系统临时文件、COM 注册、驱动/服务、Windows 凭据管理器、DPAPI 数据、硬件绑定许可证、企业 SSO、云同步数据库、多进程锁与 IPC 文件等。若重定向导致登录循环、数据损坏、启动失败或安全性下降，应选择更合适的隔离方案并记录限制。

### 6.4 数据验证

至少验证：

1. 首次启动能初始化数据。
2. 配置变更能持久化。
3. 正常关闭后数据完整。
4. 二次启动能正确读取。
5. 目录迁移后数据仍可读取。
6. 可再生缓存删除后能重建。
7. 是否向其他位置意外写入。
8. 是否存在锁文件、数据库损坏或并发冲突。
9. Data 缺失时能否安全初始化。
10. Data 不可写时是否明确报错而不是静默丢数据。

授权或安全数据若无法迁移，必须明确说明，不得承诺绝对跨机器迁移。

## 7. 白名单与残留治理

所有已识别的非预期系统写入都必须调查、分类和记录。可迁移的持久化用户数据原则上应保存于便携目录；确有技术理由无法迁移的，经过审查后列入白名单。

白名单文件建议为 whitelist\WL-<项目名>-NNN.yaml，至少包含：id、project、event_type、target_path_or_key、data_category、reason、required_for_normal_operation、avoidable、portable_impact（low/mid/high）、personal_data、cross_machine_impact、cleanup_plan、risk_level、verified_evidence、review_date、decision。

未登记且未解释的非预期写入不得通过验收。

### 7.1 残留检查

在可恢复环境中检查程序目录、用户级配置、注册表、公共程序数据、临时目录、启动项、快捷方式、服务、计划任务、文件关联、COM 注册、更新器、后台进程和云同步数据库。权限不足时明确记录检查范围，不能宣称完成了全系统检查。

### 7.2 清理脚本安全

清理脚本默认 --dry-run；只处理可明确归属本项目的目标；逐项记录对象；执行前验证路径；禁止宽泛通配符删除未知文件；不自动删除归属不明的注册表项；失败时保留证据；重复运行不得破坏其他数据。

## 8. 测试框架：12 类标准场景

每个项目至少完成 10 类场景；目标是覆盖全部 12 类。若场景不适用，必须说明理由并设计替代场景，不适用不等于通过。

- S01 首次冷启动：记录进程、退出码、初始化文件和文件树。
- S02 二次热启动：验证启动耗时、配置读取和重复启动行为。
- S03 登录/配置保存：验证数据写入 Data 及重启后持久化；需人工登录时不得伪造。
- S04 文件导入/导出：记录文件 I/O 和输出位置。
- S05 下载/更新/版本检查：记录网络相关日志、写入路径和更新后完整性；不得绕过授权。
- S06 异常强制退出后重启：检查锁文件、数据库和恢复行为。
- S07 Windows 重启后启动：记录重启前后差异；无法真实重启时标记未运行。
- S08 便携目录迁移：移动/复制到含空格或不同盘符的新路径后启动并验证数据。
- S09 新用户/独立设备语义：优先使用独立 Windows 用户或 VM；不能独立验证时标记未验证。
- S10 边界路径和权限：中文、空格、长路径、普通用户、只读/不可写目录。
- S11 多实例/重复启动：验证互斥、锁、数据冲突和退出行为。
- S12 清理/卸载残留：检查文件、注册表、进程、服务、计划任务等可观测范围。

### 8.1 每轮执行步骤

1. 检查环境与恢复点。
2. 记录 run ID、开始时间、版本、关键哈希。
3. 采集运行前文件/注册表/进程基线。
4. 启动程序并记录实际命令、工作目录、参数和非敏感环境变量。
5. 执行明确的操作步骤。
6. 采集运行日志与进程状态。
7. 正常关闭；轮询确认进程退出，超时则记录。
8. 采集运行后快照和注册表差异。
9. 检查 Data、系统写入、残留和异常日志。
10. 对照预期结果，保存证据并更新状态。

### 8.2 测试结果枚举

只能使用：

- PASS：实际执行且符合预期。
- FAIL：实际执行且不符合预期。
- BLOCKED：外部依赖、权限或环境阻止完成。
- NOT_RUN：尚未执行。
- NOT_APPLICABLE：经说明确认不适用。

每条结果必须有预期、实际、证据路径、时间戳和判定依据。

### 8.3 回归轮次

- P0 修复目标及其关键场景：每次修复后至少 3 轮完整回归。
- 其他重要缺陷修复：至少 3 轮回归。
- 更新引擎候选版本的冒烟测试：最小集为 S01、S02、S03、S08、S12（详见 19.8）。
- 三轮应覆盖正常启动/退出、数据持久化、原失败场景和至少一个相关边界场景。
- 同一轮中的多次点击不能算作多轮；三轮中有一轮失败不得宣告通过。
- 纯文档或格式调整可简化验证，但必须说明理由。

### 8.4 环境矩阵

根据软件风险覆盖 Windows 10/11、64 位、普通用户/必要时管理员、干净/已有用户配置、中文/空格/长路径、网络正常/中断、只读目录、目录迁移、系统重启、独立用户/设备、沙盒或虚拟机。无需对所有组合穷举，但测试计划必须说明选择依据。没有独立设备或 VM 时，不得宣称完成跨机器测试。

## 9. 便携性红线与故障排查

### 9.1 便携性检查清单

逐项调查并记录：

- 硬编码盘符、用户名、固定安装目录。
- %APPDATA%、%LOCALAPPDATA%、%USERPROFILE%、%PROGRAMDATA%、%TEMP% 等路径逃逸。
- Electron/Chromium userData 泄漏。
- .NET IsolatedStorage、Node 全局路径。
- VC++ manifest、运行库或 DLL 依赖异常。
- 更新器劫持或更新后破坏便携化。
- SmartScreen/Defender 拦截（只检查记录，不关闭防护）。
- Windows 事件日志中的 Error/Crash 记录。
- 数据目录、数据库、锁文件、多实例冲突。
- 登录、网络、证书、TLS、代理、许可证或硬件绑定限制。
- 清理脚本、卸载残留和启动器调用链。

### 9.2 通用启动故障排查顺序

1. 主程序 EXE 是否存在、文件大小和哈希是否合理。
2. 原程序版本、依赖文件和资源是否完整。
3. 启动器实际调用的 EXE、参数、工作目录是否正确。
4. 标准输出、标准错误、退出码、启动耗时和崩溃日志。
5. 残留进程、互斥体、锁文件和重复实例。
6. VC++、.NET、Node、Python、Electron 等运行依赖。
7. 中文、空格、长路径、权限和只读目录。
8. Data 初始化、重定向配置和配置文件格式。
9. 事件查看器、应用程序日志和崩溃记录。
10. 网络、认证、更新和在线校验依赖。
11. 安全软件拦截证据；不得擅自关闭安全软件。
12. 基于证据实施最小修复，建立差异并进行回归。

### 9.3 WinClawPortable 专项

必须先保留原始失败证据，再确认主程序 EXE、启动参数、工作目录、依赖和重定向。图标从原程序 EXE 或官方资源提取，核对 ICO 是否含 16、32、48、256 像素尺寸；验证启动器关联，以及资源管理器、任务栏、Alt+Tab 的显示。若涉及图标缓存，记录刷新/验证过程（执行 ie4uinit.exe -show 或重启 explorer 后复检）。不得只修图标就宣告启动问题解决。该项目的版本更新后必须重跑图标校验与启动校验。

### 9.4 LobsterAIPortable 专项

建立可复现的启动失败基线；按通用决策顺序排查主程序、工作目录、参数、依赖、数据目录、锁文件、网络/认证和安全拦截。修复后至少 3 轮关键场景回归。不得仅凭启动器返回成功退出码判断应用已正常运行。

## 10. 问题管理、修复闭环与熔断

### 10.1 问题单

路径：issues\<项目名>\ISSUE-NNN.md。至少包含：

- ID、项目、严重级别、标题、首次发现时间。
- 复现环境、前置条件、复现步骤。
- 预期结果、实际结果、证据路径。
- 根因（证据不足时标记待确认）。
- 影响范围、风险。
- 修复方案、修改文件、修复 diff/哈希。
- 回归场景与每轮结果。
- 临时替代方案、长期建议。
- 状态、关闭条件、关闭时间。

严重级别：

- S1：无法启动、数据丢失/损坏、越权系统写入、安全风险。
- S2：核心功能异常、迁移失败、登录/配置无法持久化。
- S3：非核心功能或兼容性问题。
- S4：文档、外观、低风险改进。

更新流程产生的失败（冒烟失败、解包失败、差异异常）同样必须建立问题单。

### 10.2 修复步骤

1. 复现并保存基线。
2. 建立问题单。
3. 结合日志、进程、文件/注册表差异和源码定位根因。
4. 制定最小修复，说明风险和回滚方案。
5. 备份后实施修复。
6. 检查变更 diff，排除无关修改和敏感数据。
7. 执行针对性测试与规定的回归轮次。
8. 更新问题单、测试报告、状态卡、变更日志和坑点知识库。
9. 若回归失败，立即回滚或恢复快照，再分析。
10. 根因不明确时不得把问题单标记为已修复。

### 10.3 熔断与超时

- 单个项目或同一根因的尝试达到 3 种有实质差异的方案仍失败，停止盲目尝试。
- 单项操作超时或工具无响应时，先保存输出和进程证据，再终止本次子进程；不得无期限等待。
- 环境污染或异常退出后，恢复快照或确认环境干净再开始下一轮。
- 将问题标记为阻塞/有条件通过，写明已尝试方案、证据、影响、临时方案和长期建议，然后继续其他项目。

## 11. 质量门禁与 KPI 计算口径

每个项目都必须从真实数据计算 KPI，不得手工填入理想值。

- 场景覆盖率 = 已实际执行的适用场景数 / 计划适用场景数。
- 启动成功率 = 实际成功启动次数 / 实际启动尝试次数；需定义何为成功启动。
- 数据便携化率 = 已验证写入便携 Data 的应迁移持久化数据项 / 已识别应迁移持久化数据项。
- 非预期系统写入数 = 未被重定向、未隔离、未获批准白名单且已确认归属目标软件的写入数。
- 回归通过率 = PASS 回归用例数 / 实际执行回归用例数。
- 证据完整率 = 有有效证据路径和哈希的测试记录数 / 实际测试记录数。
- 更新相关 KPI（详见 19.14）：版本检测覆盖率、下载校验成功率、解包成功率、冒烟通过率、Data 完整率。

### 11.1 项目级验收目标

1. 12 类场景全部执行，或至少 10 类执行并对未覆盖项给出可审计原因；任何未执行项不得算 PASS。
2. P0 关键场景修复后至少 3 轮回归。
3. 用户持久化数据进入 Data 的覆盖率目标为 100%；无法迁移的授权/系统数据必须明确列入白名单并解释。
4. 非预期系统写入目标为 0；已审查并批准的白名单例外单独统计。
5. 冷启动、目录迁移、跨用户等指标仅在实际执行的环境范围内报告；未验证不得宣称 100%。
6. 阻断性崩溃为 0，或明确标记阻塞并解释原因。
7. 问题单、测试报告、证据、白名单、坑点、SBOM/许可证审查材料齐全。
8. Qoder 系列已完成真实监控基线对比。
9. WinClaw 图标正确且启动正常；Lobster 启动正常。
10. 所有状态、报告、看板与结构化数据一致。
11. 已接入更新引擎的项目具备可执行的版本检测、候选测试与回滚能力。

### 11.2 最终状态

每个项目只能标记以下之一：

- 通过：满足适用验收门禁，证据充分。
- 有条件通过：核心可用，但存在已知限制或非阻断问题。
- 不通过：实际测试未满足关键验收条件，且并非外部阻塞。
- 阻塞：权限、环境、外部服务、账号授权或不可安全解决的依赖导致无法完成。

每个项目状态必须附理由、证据链接、未完成项和下一步建议。

## 12. Git、版本控制与回滚

1. 先检查仓库是否存在、当前分支、工作区、未跟踪文件和已有提交；不假定分支名固定。
2. 禁止覆盖用户未提交的修改；不得自动清理未知文件。
3. 采用最小改动、可审查 diff；重要修复关联问题单 ID。
4. 如项目现有约定允许，提交格式建议：type(scope): desc [ISSUE-xxx]；版本更新提交格式建议：chore(update): 项目 vX.Y.Z → vA.B.C [UPDATE-xxx]。
5. 可使用 main、dev、portable、test 等分支，但必须先检查现有分支策略，不能擅自重写分支。
6. 高风险操作前备份或 stash；如有冲突，停止自动覆盖并记录阻塞。
7. 变更记录追加写入 changelog\，坑点记录追加写入 docs\04-避坑手册.md；更新引擎每次切换版本自动追加一条 changelog。
8. 所有修复应能追踪到变更 diff、测试证据和回滚方法。
9. 不未经授权推送到远程仓库，不发布公共版本。
10. 版本更新节点建议打 Git Tag：v-项目缩写-版本号-日期。

## 15. 状态机与断点恢复

状态序列：

未开始 → 基线测试 → 问题登记 → 修复中 → 回归中 → 文档中 → 最终验收 → 通过 / 有条件通过 / 不通过 / 阻塞

每个状态必须定义进入条件、退出条件、必需证据和下一步动作。

更新引擎子状态（与主状态机并行记录于版本状态）：待检测 → 已检测有新版 → 下载中 → 解包中 → 差异分析中 → 冒烟测试中 → 候选待发布 → 已发布 → 已回滚。

### 15.1 单项目循环

1. 读取状态卡和工作日志，识别上次中断位置。
2. 校验已有证据路径和哈希，避免重复生成基线。
3. 执行或补齐基线测试。
4. 登记问题并分析根因。
5. 备份后修复。
6. 执行回归测试。
7. 更新报告、问题单、白名单、知识库和文档。
8. 校验报告字段、证据链接与数据一致性。
9. 更新状态卡、总看板、工作日志。
10. 进入下一个非阻塞项目。

状态为"文档中"及之后的项目，先核验前阶段证据是否仍有效；有效则跳过已完成工作，无效才重跑相关部分。

### 15.2 断点恢复

恢复执行时第一步读取 PROJECT_STATUS.md、state.json、结构化状态数据和 WORKLOG.md，从首个未完成且可执行的项目继续。每次重要状态变化都立即写盘。不得因为会话中断就把已完成且有证据的工作全部重做。更新引擎中断时，依据 Staging 目录与版本状态文件判断已完成阶段，从断点续跑，不重复下载或重复测试。

## 19. 便携软件自动化更新维护流水线（新增章节）

本章整合《便携软件更新策略》全部有效结论，确立长期更新维护的最佳方案。核心结论：**不把"下载最新安装包 → 本机安装 → 拷出来"作为日常方案**（仅作最后兜底）；维护重点从逐个手工更新 19 个项目，转变为维护一套通用 Python 更新引擎加 19 份轻量配置。

### 19.1 更新策略四级优先级

对每个项目按以下优先级选择更新方式，上一级失败才降级到下一级，降级原因必须记录：

| 级别 | 方式 | 适用条件 | 关键约束 |
|---|---|---|---|
| L1 | 官方 ZIP/便携包直接替换 | 官方提供 ZIP、portable 版或 Electron 应用官方发布压缩包；Cursor、Qoder、CodeArts 等 VS Code/Electron 系优先 | 下载→校验→解压到新版本目录→保留 Data→测试→切换 |
| L2 | 安装包静态解包 | 无 ZIP 但安装包为 NSIS/Inno Setup/MSI 等常见格式 | 用 7-Zip（NSIS）、innounp（Inno Setup）、lessmsi（MSI）等工具解出文件，**不真实安装、不写系统**；保留原始安装包为证据 |
| L3 | 沙盒/虚拟机隔离安装捕获 | L2 解包失败；程序依赖安装器释放的组件或在线下载器 | 在 Sandboxie/Windows Sandbox/VM 快照环境中静默安装，Procmon/Regshot 捕获写入基线，提取文件后销毁沙盒；生成新基线并与旧基线 diff |
| L4 | 手动安装再拷出 | 无解包方案且沙盒不可用 | 最后兜底；每次都要重做便携化与基线监控，成本最高；必须登记降级原因 |

禁止的第五种方式：让软件内置更新器在正式便携目录中自行升级——会写回 %LOCALAPPDATA%、破坏重定向、使引擎失去版本追踪、产生半更新状态。该方式在任何情况下都不得采用。

### 19.2 核心架构：三层分离与版本目录

每个接入更新引擎的项目采用"程序层、封装层、数据层"三分离：

- App 层（可重生）：主程序文件与运行时资源，更新时整体替换，等价于消耗品。
- Launcher 层（稳定）：便携启动器、启动参数、环境变量注入、更新器禁用配置，更新时原则上不动，仅在差异分析显示需调整时修改。
- Data 层（资产）：配置、登录态、对话历史、插件扩展、缓存索引，更新引擎永不覆盖。

推荐版本目录结构（在项目现有结构兼容前提下逐步迁移，不要求立即搬家）：

- 项目根\versions\v1.0.0\（各历史版本完整程序目录）
- 项目根\versions\current.txt（内容为当前版本号，如 v1.0.0；启动器读取该文件决定启动哪个版本目录；回滚仅需改写此文件）
- 项目根\Data\（永久用户数据，跨版本共享）
- 项目根\Staging\（候选版本工作区：Staging\<项目>\v新版本-candidate\）
- 项目根\Backups\<版本>-<时间戳>\（更新前 App 快照，保留最近 3 版）
- 项目根\version.json（当前版本号、更新源、最后检查时间、更新通道）

模型文件、大体量下载内容独立外置（如 Data\Models 或独立目录），不进入 App 更新包。

### 19.3 通用更新引擎与单项目配置

架构原则：**一个 Python 更新引擎 + 19 份 YAML 配置**，不为每个项目写独立完整脚本。

引擎入口：scripts\update_engine.py，统一 CLI：

- python update_engine.py detect [--project 名称 | --all]：检测新版本。
- python update_engine.py download --project 名称：下载并校验。
- python update_engine.py extract --project 名称：按 L1→L2→L3 解包提取。
- python update_engine.py diff --project 名称：新旧版本差异分析。
- python update_engine.py test --project 名称：候选版本冒烟测试。
- python update_engine.py stage --project 名称：生成候选版本目录。
- python update_engine.py release --project 名称 [--confirm]：门禁校验与版本切换。
- python update_engine.py rollback --project 名称 --to 版本号：回滚。
- python update_engine.py report --project 名称：生成更新报告。

单项目配置文件 Configs\<项目名>.yaml 必备字段：

- project：项目逻辑名称与实际目录。
- version_source：版本检测源类型与地址（官方 API / GitHub Releases / latest.yml / 下载页正则 / manual）。
- download_url 或 url_pattern：官方下载来源或可靠 URL 解析规则。
- package_type：zip / nsis / inno / msi / msix / electron-installer / unknown。
- extract_strategy：direct_zip / static_unpack / sandbox_capture / manual_fallback。
- entry_exe：实际启动程序路径。
- launcher_args：启动参数、环境变量、工作目录。
- data_dir：必须保持的便携数据目录（引擎保护清单）。
- protected_paths：禁止覆盖的文件与目录清单。
- extensions_dir：扩展/插件目录重定向规则（如适用）。
- updater_disable：内置更新器禁用方式（参数、配置文件、待改名组件清单）。
- test_profile：冒烟测试项（默认 S01/S02/S03/S08/S12）。
- full_regression_trigger：触发完整回归的条件（大版本跨越、更新器变更、存储路径变更）。
- rollback_policy：回滚条件与保留版本数量（默认 3）。
- update_channel：stable / beta / 其他官方通道。
- release_policy：auto（低风险自动）/ manual_confirm（默认）/ blocked（强制人工）。
- schedule：检测频率（weekly / biweekly / monthly）。
- delta_update：是否启用差分更新（默认 false）。

### 19.4 版本检测优先级

按可信度与稳定性排序，配置中记录所用级别与最后验证时间：

1. 官方 Update API 或更新清单：VS Code 系 /api/latest/win32-x64/stable 类接口；electron-builder 发布的 latest.yml（含 version、path、sha512 三字段，可直接校验）。最优。
2. GitHub Releases API：GET /repos/{owner}/{repo}/releases/latest，取 tag_name 与 assets 列表；资产名用正则匹配（如 win32-x64.*\.zip）而非硬编码；未认证 API 限速 60 次/小时，批量检查 19 项目时配置 GITHUB_TOKEN 环境变量。
3. 官方下载页解析：脆弱，页面一改即失效；仅作备用，必须记录页面地址、版本正则、下载链接规则、最后验证时间，失效时自动告警降级为手动登记。
4. RSS/Atom 更新日志或 Release Notes：辅助来源。
5. 手动登记：无稳定公开接口的软件不强行爬取，配置中标记 source: manual，定期人工检查并回填版本号。

重要约束：检测到新版本不等于具备可靠更新能力；版本号未变但文件可能已变（以哈希为准）；正式版、预览版、灰度版可能混发，配置必须锁定 update_channel。

### 19.5 更新流水线七阶段

引擎按阶段推进，每阶段独立可执行、可断点续跑、产出结构化证据：

**阶段一 detect（版本检测）：** 按 19.4 优先级获取最新版本，与 version.json 比对（packaging.version 语义化比较），写入 reports\data\update_versions.json。无可靠来源的项目标记 needs_manual，不猜测版本。

**阶段二 download（下载与安全校验）：** 优先官方来源，记录下载 URL、文件大小、SHA-256；官方提供可信哈希或数字签名则校验并记录结果；缺少可信基准时，明确记录"仅本地计算哈希，未验证官方真实性"，不得宣称已验证。原始安装包归档至 Staging\<项目>\downloads\。

**阶段三 extract（解包提取）：** 按 extract_strategy 执行 L1 直接解压 / L2 静态解包 / L3 沙盒捕获；L3 捕获时同步产出新版安装写入基线（文件清单、注册表键、服务、任务），与旧基线 diff；失败降级时记录原因。输出候选程序目录树。

**阶段四 diff（差异分析）：** 比较新旧版本文件清单、哈希、大小、目录结构、启动器参数、运行库、配置模板。重点自动标记四类高危变化：

1. 新增或变更的更新器组件（Update.exe、app-update.yml、Squirrel 文件、自动升级服务）。
2. 新增的服务、计划任务、启动项、遥测组件。
3. 存储路径变更（userData 位置、扩展目录、缓存目录迁移）。
4. 依赖大版本跨越（Electron 主版本、Node、内置运行时）。

命中第 1、3、4 类时 release_policy 自动升级为 manual_confirm；新增系统写入点自动生成白名单候选条目，待人工复核。

**阶段五 test（冒烟测试）：** 在候选目录上执行最小用例集 S01（冷启动）、S02（二次启动）、S03（配置持久化）、S08（目录迁移）、S12（残留检查）；复用 run_scenario.py 与证据体系；检查进程正常、日志无阻断错误、数据正确写入 Data。禁用内置更新器的处置必须在测试中验证有效（无更新相关后台进程、无更新目录写入）。

**阶段六 stage（候选归档）：** 测试通过后，候选版本移入 versions\vX.Y.Z-candidate\（或 Staging 候选区），生成更新报告（旧版本、新版本、差异摘要、测试结果、风险标记、回滚命令）。此时 stable 未被触碰。

**阶段七 release（门禁发布与切换）：** 门禁条件：冒烟全 PASS、无未解释高危差异、Data 完整性校验通过（更新前后 Data 快照对比，差异为零或仅为预期内变更）、更新器禁用有效。通过后：psutil 确认主进程退出 → 备份当前 App 至 Backups → 原子更新 current.txt → 写回 version.json → 追加 changelog → 更新状态卡与看板。Qoder 系列追加执行监控基线重新对比；WinClaw/Lobster 追加图标校验与启动校验。任一门禁失败：保留旧版、禁止替换、建立问题单、标记阻塞。

### 19.6 内置更新器禁用规范

每个接入项目必须在首次接入时执行 disable_updater.py 并留存处置记录。按优先级尝试，至少一种生效且经测试验证：

1. 启动参数禁用：启动器追加 --disable-updates、--no-auto-update、update.mode=none 等参数。
2. 配置文件禁用：argv.json 写入 "disable-updates": true，或应用自身配置中的更新开关。
3. 组件物理处置：重命名或移除 App\resources\app-update.yml、Update.exe、Squirrel 相关组件；改名而非删除，保留恢复路径，处置动作登记 changelog。
4. 环境变量禁用：如 UPDATE_DISABLED=1 等应用支持的变量。

约束：不得破坏软件正常启动与核心功能；每次版本更新后 diff 阶段重新检测更新组件变化，变化即告警并重新执行禁用处置；处置证据（执行前后的文件状态、进程检查、目录写入检查）归档。

### 19.7 候选版本与门禁发布模式

发布策略采用"候选版本 + 门禁"，禁止发现新版本立即替换 stable：

- 默认 release_policy 为 manual_confirm：候选就绪后生成报告，人工确认后执行 release --confirm。
- 仅对连续两次更新冒烟全 PASS、差异分析无高危项、历史稳定的低风险项目，可经人工批准将 release_policy 降为 auto。
- 大版本跨越（主版本号变更）、更新器行为变更、存储路径变更、强登录/授权机制变更：无条件强制人工复核。
- 更新失败或门禁拒绝：自动回滚指针（若已切换）、保留候选与日志、建立问题单，stable 保持原状。
- 终端用户侧原则：交付给终端用户的便携包禁止用户在包内直接自动升级程序本体；升级必须通过下载新版完整/增量便携发布包完成。

### 19.8 更新后回归测试

- 最小集（所有更新必跑）：S01 冷启动、S02 二次启动、S03 配置持久化、S08 目录迁移、S12 残留检查。
- 完整集（触发条件任一）：大版本跨越、差异分析命中高危变化、冒烟出现 FAIL 后修复、Qoder 系列、WinClaw/Lobster——执行 12 场景全量 + 关键场景 3 轮回归。
- Qoder 系列专项：每次更新后重新执行 parse_qoder_logs.py 与 compare_baseline.py，比对新版安装/运行行为与既有基线，新增写入点进入白名单流程。
- WinClaw/Lobster 专项：更新后重跑 verify_icon.py（四尺寸校验 + 图标缓存清理后复检）与启动校验（S01/S02）。
- 登录态与授权验证：更新后验证 Data 中登录态是否仍生效；失效属正常情况的登记 KnownIssues，不得伪造登录成功；需账号验证的场景标记人工介入。

### 19.9 回滚机制

- 回滚操作：修改 current.txt 指回旧版本号（原子替换），或执行 update_rollback.py --to 版本号；启动器随后加载旧版本目录。
- 升级前三件套（强制）：冻结 Data 快照（快照工具或 Python 目录树 + 哈希清单至 Backups\pre_<新版本>_Data\）；备份当前 App 至 Backups\<旧版本>-<时间戳>\；生成 rollback.md 写明版本号、时间戳、回滚命令与验证方式。
- 版本保留策略：Backups 与 versions 保留最近 3 版，超过自动清理最旧（清理前确认非唯一副本）。
- 回滚触发条件：新版本启动失败（启动器轮询超时未检测到主进程）、冒烟或回归关键场景失败、用户反馈功能异常。
- 回滚后处理：Data 目录原位保留（Data 通常向上兼容）；若新版曾写入导致旧版不识别的 schema 变更，记录 KnownIssues，必要时从 pre_ 快照定向恢复受影响文件；回滚动作本身必须复测 S01/S03 并留证。

### 19.10 可选增强：差分更新

定位为分发效率优化，非必需能力，默认关闭：

- 工具：bsdiff4（Python 库）生成与应用增量补丁；适用于自建分发或团队内网多机场景。
- 流程：以 Backups 中保留的旧版全量包为基线，对新版全量包生成 .patch 与 .meta.json（含旧包哈希、新包哈希、补丁哈希）；应用前先校验本地基线哈希与补丁自身哈希。
- 降级规则：大版本跨越（Electron 主版本升级、工具链变化）可能导致差分包大于全量，自动降级为全量下载；基线仅保留最近 3~5 版，更老版本直接全量。
- 约束：差分仅优化下载量，不改变 19.5 的七阶段门禁流程；未启用 delta_update 配置的项目忽略本节。

### 19.11 维护节奏分级

- P0 高频高危类（Cursor、Qoder 系列、CodeArts 系列、CodeBuddy、Comate、JoyCode、WorkBuddy）：每周自动检测；候选版本自动准备至 stage；发布默认人工确认。
- 常规工具类（AiPyPro、Miaoshou、MiniMaxCode、OfficeAce、TodayCN、FoxitPDF、WeMeet、QuarkCloudDrive）：每月检测；仅重大版本迭代启动更新流程，小版本可按配置跳过。
- 紧急修复类（WinClaw、Lobster）：修复稳定并建立版本快照前不接入自动更新；稳定后按 P0 节奏纳入。
- 紧急安全更新：官方说明含重大安全修复时走加急流程——检测→下载→解包→冒烟（压缩至 S01/S02/S12）→人工确认→切换；全程留证。
- 定时调度：Windows 任务计划程序调用 Python 脚本（schtasks 创建每日/每周任务），或启动器冷启动时顺带触发 detect；避免常驻后台进程。

### 19.12 AI 工具更新维护特有风险与对策

1. 模型与运行时分离：模型文件（数 GB 级）独立于 App 更新包，放 Data\Models 或外置目录；引擎只管程序层。
2. 登录态与 API Key：登录态存于 Data 自动保留；API Key 等敏感信息放 Data\secrets，绝不写入 version.json、配置仓库或日志；大版本后 token 失效登记 KnownIssues，不绕过认证。
3. 扩展与插件：VS Code 系工具扩展默认装于用户主目录 .vscode/.cursor 下的 extensions，必须重定向至 Data\extensions（启动器参数或 Junction），否则升级后扩展丢失；Junction 方案登记白名单并说明清理策略。
4. 首启自动下载的运行时/模型/二进制依赖：重定向至 Cache\ 并登记白名单或便携策略，不混入 App 版本目录。
5. 云端服务依赖变化：新版可能变更接口地址、认证方式、网络策略；冒烟测试至少确认可启动、可进入主界面、无网络异常导致的启动失败；深度功能验证受账号边界限制时如实标记。
6. 后台常驻进程类设计：部分工具启动时安装常驻后台进程并自动下载更新重启（对便携化致命）；diff 阶段专门检测新后台进程与自启动注册，发现即标记 S1 并拦截。
7. GitHub API 限流与代理：批量检测配置 GITHUB_TOKEN；企业内网配置 requests 代理（HTTPS_PROXY 环境变量或配置项），代理未穿透是更新失败的常见根因。
8. 配置 schema 兼容：升级前扫描 Data 中可能被新版改变结构的文件（settings.json、argv.json、state 数据库、Web 存储）；发现迁移需求时在更新报告标记 migration_required，升级后触发迁移脚本并验证。

### 19.13 与现有状态机的融合

更新引擎不另起体系，完全复用 V6.1 既有机制：

- 脚本规范：引擎模块遵循第 4 章全部工程规范（run ID、证据、--dry-run、原子写、熔断）。
- 状态持久化：版本状态并入 state.json 与状态卡字段（当前版本、最新版本、更新状态）。
- 证据体系：每阶段证据入 evidence\<项目>\<run-id>\update-<阶段>\。
- 问题单：更新失败建立 ISSUE 单，严重级别按第 10.1 节判定。
- 白名单：diff 阶段产出的新增写入候选进入 whitelist\ 流程。
- changelog：每次 release 或 rollback 自动追加条目。
- 基线联动：Qoder 系列更新后重跑基线对比；其他项目更新后重跑 check_residuals.py。
- 看板联动：dashboard.html 展示更新状态列；数据源为 reports\data\update_versions.json。

### 19.14 更新 KPI

从引擎结构化数据计算，不得手工填造：

- 版本检测覆盖率 = 有可靠版本源配置的项目数 / 19。
- 下载校验成功率 = 通过哈希/签名校验的下载次数 / 总下载次数。
- 解包成功率 = L1/L2 解包成功次数 / 总解包尝试次数（L3/L4 降级单列统计）。
- 冒烟通过率 = 冒烟全 PASS 的候选版本数 / 进入冒烟的候选版本数。
- 发布回滚比 = 执行回滚次数 / 正式发布次数（趋势指标，无目标值，异常升高需排查）。
- Data 完整率 = 更新前后 Data 差异为零或仅预期变更的更新次数 / 总更新次数，目标 100%。
- 更新器禁用有效率 = 禁用验证通过的更新次数 / 总更新次数，目标 100%。
