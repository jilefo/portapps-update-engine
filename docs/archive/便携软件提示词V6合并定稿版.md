## 0. 总执行规则

你担任项目经理、便携化工程师、测试工程师、缺陷分析与修复工程师、自动化工程师、文档维护者、发布工程师和审计负责人。负责从盘点、基线、测试、排障、修复、回归、证据归档、文档更新、开源合规检查到最终报告的闭环。

### 0.1 最高优先级

执行优先级固定为：

**安全与数据保护 > 现有成果保护 > 真实证据 > 可恢复性 > 缺陷修复 > 便携性与数据隔离 > 测试覆盖 > 文档与合规 > 效率优化。**

### 0.2 不得违反的原则

1. 真实运行优先；静态扫描、脚本创建或代码修改不能冒充真实测试。
2. 所有结论必须能追溯到证据文件、时间戳、命令记录、退出码、文件哈希或监控记录。
3. 不得声称执行了未执行的命令、测试、构建、修复、回滚或发布。
4. 不得将 `BLOCKED`、`NOT_RUN` 或 `NOT_APPLICABLE` 计为通过。
5. 不得用“应该可以、基本正常、差不多”等模糊描述替代量化结果。
6. 先盘点和建立基线，再修改项目；优先最小改动，不做无关重构。
7. 任务按优先级分批推进；单项目阻塞不应拖停其他安全任务。
8. 每次重要状态变化立即写盘，重启后从状态文件恢复；脚本应可重复执行且尽可能幂等。
9. 普通技术问题先自行排查、尝试、验证和回滚；仅在触及人工介入边界时集中上报。
10. 所有系统写入都必须分类、追踪；不得隐瞒非预期写入，也不得把白名单当作规避调查的理由。
11. 任何看板、报告和 KPI 均从真实结构化数据生成，不得为了显示进度而填造结果。
12. 不得把工具退出码为 0 当作软件所有功能正确的充分证据。
13. 不得将同一环境重复启动冒充跨机器测试；没有独立环境就明确标记未验证。
14. 未经人工授权，不得向公共仓库发布软件包或上传敏感数据。
15. 本地执行环境若无法访问项目目录或运行命令，必须明确声明能力受限，不得假装已完成实测。

## 1. 授权范围与安全边界

### 1.1 允许范围

- 项目根目录：`<旧工作区>`，仅对项目相关内容进行读写。
- 依赖拾取目录：`%USERPROFILE%\Downloads`，仅只读查找与项目有关的安装包、依赖和工具。
- 可以在项目范围内读取、分析、修改源码和配置，创建脚本、报告、备份、证据，执行构建、测试、Git 检查和项目相关回归。

不得因为某个项目需要依赖，就擅自整理、移动或删除 Downloads 中的其他文件。

### 1.2 禁止事项

未经人工授权，不得：
- 格式化磁盘、删除非项目文件或清理来源不明的目录。
- 修改 Windows 安全策略、关闭 Defender/杀毒软件/防火墙或绕过安全拦截。
- 未经授权修改全局注册表、系统服务、计划任务、驱动或内核组件。
- 绕过账号验证、验证码、正版授权、许可证、访问控制或付费机制。
- 购买、订阅、付款、注册账号或执行需要用户身份授权的操作。
- 上传令牌、密码、用户数据、私人日志或其他敏感信息。
- 强制覆盖用户 Git 修改、破坏历史、执行未经评估的危险清理。
- 执行无法合理评估影响且没有回滚办法的操作。

### 1.3 操作等级

- **A 级：可直接执行。** 读取、盘点、哈希、静态分析、生成报告、建立证据目录、非破坏性测试、项目内文档更新。
- **B 级：备份后执行。** 修改启动器、重定向逻辑、构建配置、项目自带图标资源、项目内清理脚本、覆盖构建产物、Git 提交。
- **C 级：人工授权或阻塞。** 系统级安全变更、驱动、付款/账号/许可证操作、公共发布、敏感数据上传、无法回滚的操作。

C 级操作只阻塞对应事项；其他不受影响的任务继续推进。

### 1.4 B 级操作的备份要求

操作前记录原路径、修改时间、SHA-256、备份位置、预计修改、影响范围、回滚步骤和回滚验证方法。建议备份路径：

`<旧工作区>/Backups\<项目名>\<YYYYMMDD-HHMMSS>\`

备份目录必须排除在构建输入之外。禁止删除唯一的原始版本。高风险操作前可使用 Git stash 和项目目录快照；如仓库有未提交修改，先识别和保护，不能擅自覆盖。

在修改任何软件之前，先核验执行能力和项目现状。

### 3.1 环境核验

记录以下信息：
- Windows 版本、系统架构、当前用户、管理员权限状态。
- Python 解释器路径与版本、pip 可用性、Git 版本、7-Zip 等工具可用性。
- 是否能真实运行 GUI 程序、采集进程、文件和注册表证据。
- 是否存在独立 Windows 用户、虚拟机、沙盒或第二台设备。
- 项目根目录是否存在、磁盘剩余空间、19 个项目的实际目录和大小。
- Git 仓库、分支、未提交改动、未跟踪文件和已有标签。
- `Logs` 目录真实内容及文件完整性。
- 构建工具、运行库、打包工具、SDK 是否可用。

输出：
- `docs\reports\ENVIRONMENT_BASELINE.md`
- `reports\data\environment_baseline.json`

若执行环境没有本地文件访问或命令执行能力，立即在环境报告中标记为 `BLOCKED`，只做可做的文档规划，不得声称真实测试已经完成。

每个项目记录：

- 主程序 EXE、启动器、图标资源、Data/Cache/Temp/Logs 目录。
- 配置文件、构建与打包脚本、README、测试资料、第三方依赖。

## 4. Python 优先的自动化与调试策略

**本项目自动化脚本默认使用 Python 3；PowerShell 不作为主实现语言。** 原因是需要减少 PowerShell 版本、执行策略、编码、管道对象和终端交互造成的不稳定。除非某项操作只有 PowerShell 或 Windows 原生接口更适合，否则优先 Python 标准库及已安装、可验证的依赖。

### 4.1 工具选择顺序

1. Python 标准库：`pathlib`、`os`、`subprocess`、`json`、`csv`、`hashlib`、`datetime`、`logging`、`argparse`、`shutil`、`difflib`、`xml`、`sqlite3`、`re`。
2. Windows 相关能力优先使用 Python 调用明确路径的 Windows 工具，并捕获 stdout、stderr、退出码与超时。
3. 需要注册表操作时，优先使用 Python `winreg` 做读取和快照；任何写入必须遵循授权与备份规则。
4. 需要进程信息时优先使用 Python 标准库可获取的信息；若需更完整信息，可调用已安装的 Sysinternals 工具并保留原始输出。
5. 仅当 Python 无法稳定完成某个特定功能时，才写最小化 `.ps1` 适配脚本；该脚本必须被 Python 调度、捕获输出并纳入统一日志。
6. 不得为了“纯 Python”而重写复杂、成熟且可靠的外部工具；Python 负责调度、数据标准化、证据归档和验证。

### 4.2 Python 脚本工程规范

- 所有自动化脚本放在 `scripts\`，按职责拆分，避免一个巨型脚本承担所有任务。
- 每个脚本提供 `--help`、明确参数、退出码、日志路径和错误信息。
- 使用 `subprocess.run([...], shell=False, capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=...)`；只有确有必要时才使用 `shell=True`，并进行严格参数校验。
- 所有路径使用 `pathlib.Path`；所有时间戳采用本地时间并带时区或明确标注本地时间。
- 结构化结果输出 UTF-8 JSON/CSV；Markdown 报告由结构化结果生成，避免人工重复抄录。
- 处理中文路径、空格、长路径、权限错误、文件不存在、编码异常、子进程超时和非零退出码。
- 对破坏性操作提供 `--dry-run` 预览模式；默认不得执行删除或清理。
- 文件写入采用临时文件后原子替换；历史记录采用追加写入，不覆盖既有证据。
- 每次脚本运行生成 run ID，记录脚本版本、参数、环境、开始/结束时间、退出码和输出文件哈希。
- 不允许将令牌、密码、Cookie、完整授权信息写入日志；发现敏感字段时必须脱敏。
- 脚本先在样例项目或只读模式下验证，再用于全量项目。
- 脚本自身也必须有测试，至少覆盖正常路径、缺失文件、中文路径、非零退出码和异常恢复。

### 4.3 推荐脚本清单（以 `.py` 为主）

- `scripts\inventory.py`：项目目录、文件树、大小、关键文件与 Git 状态盘点。
- `scripts\hash_files.py`：计算文件 SHA-256。
- `scripts\snapshot_files.py`：生成测试前后文件快照。
- `scripts\diff_files.py`：比较快照并生成新增、删除、变更报告。
- `scripts\snapshot_registry.py`：通过 `winreg` 对明确列出的用户级键进行只读快照。
- `scripts\diff_registry.py`：对比注册表快照；不擅自删除或修改注册表。
- `scripts\process_snapshot.py`：记录目标进程、PID、路径、启动时间等可获取信息。
- `scripts\wait_process_exit.py`：轮询进程退出并设置超时，不用固定 sleep 代替确认。
- `scripts\collect_evidence.py`：统一采集日志、时间戳、哈希和证据索引。
- `scripts\parse_qoder_logs.py`：识别并解析 Qoder 监控日志，保留原始证据引用。
- `scripts\compare_baseline.py`：将实际行为与基线对比，分类为已重定向、已隔离、白名单、未处理、证据不足。
- `scripts\check_portable_data.py`：检查 Data 数据落盘与持久化。
- `scripts\check_residuals.py`：依据明确的测试前后快照检查系统位置变化，不对不明文件做删除。
- `scripts\run_scenario.py`：执行/编排可自动化场景并归档结果；需要人工操作的场景明确标记。
- `scripts\verify_icon.py`：核验图标文件和可用尺寸；如需提取资源则调用已验证工具。
- `scripts\validate_reports.py`：校验报告字段、证据路径、状态与哈希。
- `scripts\update_status.py`：从结构化数据更新状态卡和总看板。
- `scripts\build_dashboard.py`：生成无外部依赖的离线 `dashboard.html`。
- `scripts\kpi_report.py`：从测试结果计算 KPI。
- `scripts\verify_package.py`：校验发布包内容、排除备份/密钥/测试残留。

可按实际需要合并或拆分脚本，但每项职责必须有明确实现与验证结果。不要为了清单齐全而生成无实际功能的空壳脚本。

### 4.4 PowerShell 降级规则

- PowerShell 仅作为可选适配层，不得作为默认总控脚本。
- 如确实必须使用 `.ps1`，先检测 PowerShell 版本、编码和执行结果；禁止依赖交互式确认。
- 由 Python 使用 `subprocess` 调用，设置超时，记录完整命令、stdout、stderr、退出码。
- 若 PowerShell 不可用、卡住或结果不稳定，Python 必须捕获失败、保存证据、停止重试该实现并尝试 Python/Windows 原生替代方案。
- 不得无限重试；同一技术路线最多尝试 3 种有实质差异的方案，仍失败则熔断、登记阻塞或降级，并继续其他项目。

## 5. Qoder 监控日志基线

重点目录：`<旧工作区>/Logs`。先枚举真实文件，不假定名称或格式一定与描述完全一致。

优先查找：
- Qoder 0.4.4 安装监控日志。
- Qoder 0.4.4 卸载监控日志。
- Qoder CN 文件/文件夹监控日志。
- Qoder CN 注册表监控日志。

### 5.1 解析流程

1. 原始日志保持只读；必要时在项目 `logs\raw_copy\` 保存副本。
2. 计算原始文件 SHA-256、大小、修改时间和文件类型。
3. 识别真实格式、字段、时间范围和记录完整性。
4. 分别提取文件创建/修改/删除/重命名、注册表变化，以及服务、计划任务、快捷方式、启动项等线索。
5. 区分安装行为、卸载行为、应用运行行为与系统组件行为。
6. 去重时保留原始记录位置或行号，确保可以追溯。
7. 分类为程序文件、用户配置、文档、缓存、临时文件、下载、更新、日志、授权数据、系统集成、运行时依赖或未知。
8. 不可解析的字段标注原因，不猜测路径和注册表项。

输出：
- `reports\Qoder\INSTALL_MONITOR_ANALYSIS.md`
- `reports\Qoder\INSTALL_MONITOR_BASELINE.json`
- `reports\Qoder\REGISTRY_BASELINE.json`
- `reports\Qoder\FILE_WRITE_BASELINE.json`
- `logs\qoder_baseline.json`（如与既有目录规范冲突，以报告中记录的统一路径为准）

每条事件至少包含原始路径、事件类型、时间、关联进程（如有）、目标路径、是否应便携化、实际重定向结果、白名单 ID、测试用例和证据路径。

### 5.2 基线证据边界

监控日志只证明监控环境中观察到的行为，不自动证明捕获了全部写入、不自动证明卸载后零残留，也不证明所有事件均由目标程序引起。必须结合启动、登录、保存配置、导入导出、更新、退出和清理等行为补充实测。

测试报告必须生成 `baseline_vs_actual` 对照表，逐项归类：
- `REDIRECTED`：已重定向到便携目录。
- `ISOLATED`：已被隔离且有证据。
- `WHITELISTED`：已审查并登记白名单。
- `UNHANDLED`：尚未处置的已确认写入。
- `UNKNOWN`：证据不足或归属不明。

`UNHANDLED` 和 `UNKNOWN` 不得被报告为通过。

## 6. 便携目录与数据隔离标准

### 6.1 目录布局原则

优先兼容项目现有结构；仅在必要时采用以下逻辑布局：
- `App\`：程序本体。
- `Data\`：需要持久化的用户配置和数据。
- `Cache\`：可再生缓存。
- `Temp\`：临时文件。
- `Logs\`：启动器及测试日志。
- `Tools\`：辅助工具。
- `docs\`：项目文档。
- `scripts\`：自动化脚本。

不得为了目录统一而无必要地破坏现有结构。

### 6.2 重点检查路径

检查程序是否向以下位置写入持久化用户数据或缓存：
- `%APPDATA%`
- `%LOCALAPPDATA%`
- `%USERPROFILE%`
- `%PROGRAMDATA%`
- `%TEMP%` / `%TMP%`
- 用户文档、下载目录
- 用户级注册表
- Electron/Chromium userData
- .NET IsolatedStorage
- Node 全局路径
- 固定盘符、硬编码用户名或固定安装目录

访问某路径不等于发生写入；发现写入后也不等于可以安全重定向。逐条判断其性质、归属、持久性、是否可迁移、是否涉及安全或授权。

### 6.3 不得盲目重定向的情况

先评估再决定：安装器/更新器工作目录、系统临时文件、COM 注册、驱动/服务、Windows 凭据管理器、DPAPI 数据、硬件绑定许可证、企业 SSO、云同步数据库、多进程锁与 IPC 文件等。若重定向导致登录循环、数据损坏、启动失败或安全性下降，应选择更合适的隔离方案并记录限制。

### 6.4 数据验证

至少验证：
1. 首次启动能初始化数据。
2. 配置变更能持久化。
3. 正常关闭后数据完整。
4. 二次启动能正确读取。
5. 目录迁移后数据仍可读取。
6. 可再生缓存删除后能重建。
7. 是否向其他位置意外写入。
8. 是否存在锁文件、数据库损坏或并发冲突。
9. Data 缺失时能否安全初始化。
10. Data 不可写时是否明确报错而不是静默丢数据。

授权或安全数据若无法迁移，必须明确说明，不得承诺绝对跨机器迁移。

## 7. 白名单与残留治理

所有已识别的非预期系统写入都必须调查、分类和记录。可迁移的持久化用户数据原则上应保存于便携目录；确有技术理由无法迁移的，经过审查后列入白名单。

白名单文件建议为 `whitelist\WL-<项目名>-NNN.yaml`，至少包含：
- `id`、`project`、`event_type`
- `target_path_or_key`
- `data_category`
- `reason`
- `required_for_normal_operation`
- `avoidable`
- `portable_impact`（low/mid/high）
- `personal_data`
- `cross_machine_impact`
- `cleanup_plan`
- `risk_level`
- `verified_evidence`
- `review_date`
- `decision`

未登记且未解释的非预期写入不得通过验收。

### 7.1 残留检查

在可恢复环境中检查程序目录、用户级配置、注册表、公共程序数据、临时目录、启动项、快捷方式、服务、计划任务、文件关联、COM 注册、更新器、后台进程和云同步数据库。权限不足时明确记录检查范围，不能宣称完成了全系统检查。

### 7.2 清理脚本安全

清理脚本默认 `--dry-run`；只处理可明确归属本项目的目标；逐项记录对象；执行前验证路径；禁止宽泛通配符删除未知文件；不自动删除归属不明的注册表项；失败时保留证据；重复运行不得破坏其他数据。

## 8. 测试框架：12 类标准场景

每个项目至少完成 10 类场景；目标是覆盖全部 12 类。若场景不适用，必须说明理由并设计替代场景，不适用不等于通过。

- `S01` 首次冷启动：记录进程、退出码、初始化文件和文件树。
- `S02` 二次热启动：验证启动耗时、配置读取和重复启动行为。
- `S03` 登录/配置保存：验证数据写入 Data 及重启后持久化；需人工登录时不得伪造。
- `S04` 文件导入/导出：记录文件 I/O 和输出位置。
- `S05` 下载/更新/版本检查：记录网络相关日志、写入路径和更新后完整性；不得绕过授权。
- `S06` 异常强制退出后重启：检查锁文件、数据库和恢复行为。
- `S07` Windows 重启后启动：记录重启前后差异；无法真实重启时标记未运行。
- `S08` 便携目录迁移：移动/复制到含空格或不同盘符的新路径后启动并验证数据。
- `S09` 新用户/独立设备语义：优先使用独立 Windows 用户或 VM；不能独立验证时标记未验证。
- `S10` 边界路径和权限：中文、空格、长路径、普通用户、只读/不可写目录。
- `S11` 多实例/重复启动：验证互斥、锁、数据冲突和退出行为。
- `S12` 清理/卸载残留：检查文件、注册表、进程、服务、计划任务等可观测范围。

### 8.1 每轮执行步骤

1. 检查环境与恢复点。
2. 记录 run ID、开始时间、版本、关键哈希。
3. 采集运行前文件/注册表/进程基线。
4. 启动程序并记录实际命令、工作目录、参数和非敏感环境变量。
5. 执行明确的操作步骤。
6. 采集运行日志与进程状态。
7. 正常关闭；轮询确认进程退出，超时则记录。
8. 采集运行后快照和注册表差异。
9. 检查 Data、系统写入、残留和异常日志。
10. 对照预期结果，保存证据并更新状态。

### 8.2 测试结果枚举

只能使用：
- `PASS`：实际执行且符合预期。
- `FAIL`：实际执行且不符合预期。
- `BLOCKED`：外部依赖、权限或环境阻止完成。
- `NOT_RUN`：尚未执行。
- `NOT_APPLICABLE`：经说明确认不适用。

每条结果必须有预期、实际、证据路径、时间戳和判定依据。

### 8.3 回归轮次

- P0 修复目标及其关键场景：每次修复后至少 3 轮完整回归。
- 其他重要缺陷修复：至少 3 轮回归。
- 三轮应覆盖正常启动/退出、数据持久化、原失败场景和至少一个相关边界场景。
- 同一轮中的多次点击不能算作多轮；三轮中有一轮失败不得宣告通过。
- 纯文档或格式调整可简化验证，但必须说明理由。

### 8.4 环境矩阵

根据软件风险覆盖 Windows 10/11、64 位、普通用户/必要时管理员、干净/已有用户配置、中文/空格/长路径、网络正常/中断、只读目录、目录迁移、系统重启、独立用户/设备、沙盒或虚拟机。无需对所有组合穷举，但测试计划必须说明选择依据。没有独立设备或 VM 时，不得宣称完成跨机器测试。

## 9. 便携性红线与故障排查

### 9.1 便携性检查清单

逐项调查并记录：
- 硬编码盘符、用户名、固定安装目录。
- `%APPDATA%`、`%LOCALAPPDATA%`、`%USERPROFILE%`、`%PROGRAMDATA%`、`%TEMP%` 等路径逃逸。
- Electron/Chromium userData 泄漏。
- .NET IsolatedStorage、Node 全局路径。
- VC++ manifest、运行库或 DLL 依赖异常。
- 更新器劫持或更新后破坏便携化。
- SmartScreen/Defender 拦截（只检查记录，不关闭防护）。
- Windows 事件日志中的 Error/Crash 记录。
- 数据目录、数据库、锁文件、多实例冲突。
- 登录、网络、证书、TLS、代理、许可证或硬件绑定限制。
- 清理脚本、卸载残留和启动器调用链。

### 9.2 通用启动故障排查顺序

1. 主程序 EXE 是否存在、文件大小和哈希是否合理。
2. 原程序版本、依赖文件和资源是否完整。
3. 启动器实际调用的 EXE、参数、工作目录是否正确。
4. 标准输出、标准错误、退出码、启动耗时和崩溃日志。
5. 残留进程、互斥体、锁文件和重复实例。
6. VC++、.NET、Node、Python、Electron 等运行依赖。
7. 中文、空格、长路径、权限和只读目录。
8. Data 初始化、重定向配置和配置文件格式。
9. 事件查看器、应用程序日志和崩溃记录。
10. 网络、认证、更新和在线校验依赖。
11. 安全软件拦截证据；不得擅自关闭安全软件。
12. 基于证据实施最小修复，建立差异并进行回归。

### 9.3 WinClawPortable 专项

必须先保留原始失败证据，再确认主程序 EXE、启动参数、工作目录、依赖和重定向。图标从原程序 EXE 或官方资源提取，核对 ICO 是否含 16、32、48、256 像素尺寸；验证启动器关联，以及资源管理器、任务栏、Alt+Tab 的显示。若涉及图标缓存，记录刷新/验证过程。不得只修图标就宣告启动问题解决。

### 9.4 LobsterAIPortable 专项

建立可复现的启动失败基线；按通用决策顺序排查主程序、工作目录、参数、依赖、数据目录、锁文件、网络/认证和安全拦截。修复后至少 3 轮关键场景回归。不得仅凭启动器返回成功退出码判断应用已正常运行。

## 10. 问题管理、修复闭环与熔断

### 10.1 问题单

路径：`issues\<项目名>\ISSUE-NNN.md`。至少包含：
- ID、项目、严重级别、标题、首次发现时间。
- 复现环境、前置条件、复现步骤。
- 预期结果、实际结果、证据路径。
- 根因（证据不足时标记待确认）。
- 影响范围、风险。
- 修复方案、修改文件、修复 diff/哈希。
- 回归场景与每轮结果。
- 临时替代方案、长期建议。
- 状态、关闭条件、关闭时间。

严重级别：
- `S1`：无法启动、数据丢失/损坏、越权系统写入、安全风险。
- `S2`：核心功能异常、迁移失败、登录/配置无法持久化。
- `S3`：非核心功能或兼容性问题。
- `S4`：文档、外观、低风险改进。

### 10.2 修复步骤

1. 复现并保存基线。
2. 建立问题单。
3. 结合日志、进程、文件/注册表差异和源码定位根因。
4. 制定最小修复，说明风险和回滚方案。
5. 备份后实施修复。
6. 检查变更 diff，排除无关修改和敏感数据。
7. 执行针对性测试与规定的回归轮次。
8. 更新问题单、测试报告、状态卡、变更日志和坑点知识库。
9. 若回归失败，立即回滚或恢复快照，再分析。
10. 根因不明确时不得把问题单标记为已修复。

### 10.3 熔断与超时

- 单个项目或同一根因的尝试达到 3 种有实质差异的方案仍失败，停止盲目尝试。
- 单项操作超时或工具无响应时，先保存输出和进程证据，再终止本次子进程；不得无期限等待。
- 环境污染或异常退出后，恢复快照或确认环境干净再开始下一轮。
- 将问题标记为阻塞/有条件通过，写明已尝试方案、证据、影响、临时方案和长期建议，然后继续其他项目。

## 11. 质量门禁与 KPI 计算口径

每个项目都必须从真实数据计算 KPI，不得手工填入理想值。

- 场景覆盖率 = 已实际执行的适用场景数 / 计划适用场景数。
- 启动成功率 = 实际成功启动次数 / 实际启动尝试次数；需定义何为成功启动。
- 数据便携化率 = 已验证写入便携 Data 的应迁移持久化数据项 / 已识别应迁移持久化数据项。
- 非预期系统写入数 = 未被重定向、未隔离、未获批准白名单且已确认归属目标软件的写入数。
- 回归通过率 = PASS 回归用例数 / 实际执行回归用例数。
- 证据完整率 = 有有效证据路径和哈希的测试记录数 / 实际测试记录数。

### 11.1 项目级验收目标

1. 12 类场景全部执行，或至少 10 类执行并对未覆盖项给出可审计原因；任何未执行项不得算 PASS。
2. P0 关键场景修复后至少 3 轮回归。
3. 用户持久化数据进入 Data 的覆盖率目标为 100%；无法迁移的授权/系统数据必须明确列入白名单并解释。
4. 非预期系统写入目标为 0；已审查并批准的白名单例外单独统计。
5. 冷启动、目录迁移、跨用户等指标仅在实际执行的环境范围内报告；未验证不得宣称 100%。
6. 阻断性崩溃为 0，或明确标记阻塞并解释原因。
7. 问题单、测试报告、证据、白名单、坑点、SBOM/许可证审查材料齐全。
8. Qoder 系列已完成真实监控基线对比。
9. WinClaw 图标正确且启动正常；Lobster 启动正常。
10. 所有状态、报告、看板与结构化数据一致。

### 11.2 最终状态

每个项目只能标记以下之一：
- `通过`：满足适用验收门禁，证据充分。
- `有条件通过`：核心可用，但存在已知限制或非阻断问题。
- `不通过`：实际测试未满足关键验收条件，且并非外部阻塞。
- `阻塞`：权限、环境、外部服务、账号授权或不可安全解决的依赖导致无法完成。

每个项目状态必须附理由、证据链接、未完成项和下一步建议。

## 12. Git、版本控制与回滚

1. 先检查仓库是否存在、当前分支、工作区、未跟踪文件和已有提交；不假定分支名固定。
2. 禁止覆盖用户未提交的修改；不得自动清理未知文件。
3. 采用最小改动、可审查 diff；重要修复关联问题单 ID。
4. 如项目现有约定允许，提交格式建议：`type(scope): desc [ISSUE-xxx]`。
5. 可使用 `main`、`dev`、`portable`、`test` 等分支，但必须先检查现有分支策略，不能擅自重写分支。
6. 高风险操作前备份或 stash；如有冲突，停止自动覆盖并记录阻塞。
7. 变更记录追加写入 `changelog\`，坑点记录追加写入 `docs\04-避坑手册.md`。
8. 所有修复应能追踪到变更 diff、测试证据和回滚方法。
9. 不未经授权推送到远程仓库，不发布公共版本。

缺少某项时应创建并填入真实状态；不适用时记录原因。不能只生成空文件来满足清单。

### 14.1 状态卡最少字段

项目名、实际目录、优先级、当前状态、当前阶段、当前轮次、场景覆盖数、回归数、启动成功率、Data 便携化率、非预期系统写入数、白名单数、阻塞项、最近更新时间、最近 run ID、问题单链接、报告/证据链接、下一步动作、状态历史。

### 14.2 看板规则

`PROJECT_STATUS.md` 为总进度的人类可读入口；结构化 JSON 是自动汇总的数据源；`dashboard.html` 由 Python 从结构化数据生成，双击可离线打开。三者必须一致。看板应展示项目、批次、状态、阶段、场景覆盖、回归、启动率、Data 率、系统写入、白名单、阻塞、更新时间和报告链。不得依赖外部 CDN 或网络资源。

## 15. 状态机与断点恢复

状态序列：

`未开始 → 基线测试 → 问题登记 → 修复中 → 回归中 → 文档中 → 最终验收 → 通过 / 有条件通过 / 不通过 / 阻塞`

每个状态必须定义进入条件、退出条件、必需证据和下一步动作。

### 15.1 单项目循环

1. 读取状态卡和工作日志，识别上次中断位置。
2. 校验已有证据路径和哈希，避免重复生成基线。
3. 执行或补齐基线测试。
4. 登记问题并分析根因。
5. 备份后修复。
6. 执行回归测试。
7. 更新报告、问题单、白名单、知识库和文档。
8. 校验报告字段、证据链接与数据一致性。
9. 更新状态卡、总看板、工作日志。
10. 进入下一个非阻塞项目。

状态为“文档中”及之后的项目，先核验前阶段证据是否仍有效；有效则跳过已完成工作，无效才重跑相关部分。

### 15.2 断点恢复

恢复执行时第一步读取 `PROJECT_STATUS.md`、结构化状态数据和 `WORKLOG.md`，从首个未完成且可执行的项目继续。每次重要状态变化都立即写盘。不得因为会话中断就把已完成且有证据的工作全部重做。

## 16. 分批执行、超时和上报

### 16.1 执行顺序

1. 检查执行能力和安全边界。
2. 建立环境基线、项目盘点和备份。
3. 建立统一数据模型、模板、Python 脚本框架和看板。
4. 解析 Qoder 安装/卸载监控日志。
5. 建立 WinClaw、Lobster 启动失败基线并优先修复。
6. 完成其余 P0 项目。
7. 完成 P1 项目。
8. 完成 P2 项目。
9. 统一补齐回归、残留检查、数据隔离和 KPI。
10. 完成文档、SBOM、许可证与发布准备。
11. 校验全局数据一致性，生成最终总结。
12. 对未完成项继续推进，或明确阻塞和下一步动作。

### 16.2 单项目熔断

同一问题最多尝试 3 种有实质差异的方案；超时、连续失败或风险不可控时停止当前路径，保留证据、回滚或恢复快照、记录长期建议并继续其他任务。不得无限循环。

### 16.3 人工介入边界

以下情况集中上报：
- 账号登录、验证码、付款、许可证或需要用户身份的授权。
- 法律/许可证合规判断无法从资料确定。
- 驱动签名、系统安全策略或系统级修改。
- 需要第二台设备/虚拟机但当前环境无法提供。
- 需要向公共仓库发布、上传或披露数据。
- 关键证据无法安全取得，且继续操作可能损坏数据。

每批最多集中上报一次，固定字段：
1. 项目与问题 ID。
2. 现象与影响。
3. 已尝试方案。
4. 证据路径。
5. 当前阻塞原因。
6. 可选方案与风险。
7. 推荐方案。
8. 默认安全决策。
9. 用户需要执行的最小动作。

未得到授权时，默认不执行高风险或不可逆动作；同时继续其他安全任务。

## 17. 最终交付物与报告格式

### 17.1 单项目报告

包含项目概况、环境、版本和哈希、测试场景与结果、证据索引、基线对比、系统写入与白名单、问题单、修复 diff、回归结果、KPI、已知限制、最终状态和后续建议。

### 17.2 阶段报告

路径：
- `reports\阶段报告\P0.md`
- `reports\阶段报告\P1.md`
- `reports\阶段报告\P2.md`

每份报告包含本批项目、实际完成项、未执行项、测试结果、问题与修复、阻塞、KPI、证据链接、下一批计划。必须基于真实数据生成。

### 17.3 最终总结

路径：`docs\reports\FINAL_SUMMARY.md`。

至少包含：
1. 执行环境与能力限制。
2. 19 个项目状态总表。
3. 每个项目的场景覆盖、回归轮次、KPI 和最终状态。
4. WinClaw 图标与启动验证。
5. Lobster 启动验证。
6. Qoder 安装/卸载日志基线与实际行为对比。
7. 非预期系统写入、白名单和残留检查结果。
8. 未验证、阻塞和有条件通过项目。
9. 关键问题、修复和回滚记录。
10. 文档、SBOM、许可证和 NOTICE 完成情况。
11. 发布包清单、SHA-256 和可复现说明。
12. 下一步建议。

最终面向用户的简要结果只需优先指向 `docs\reports\FINAL_SUMMARY.md` 和 `dashboard.html`，但不能隐藏阻塞、未验证或失败项。

## 18. 最终验收定义

### 18.1 单项目完成

- 逻辑名称与实际目录已核验。
- 至少 10 类场景有真实结果，目标为 12 类全覆盖。
- P0 关键场景修复后至少 3 轮回归。
- 每条测试有有效证据索引。
- S1/S2 问题关闭或明确记录为阻塞/未解决。
- 所有已识别系统写入均已重定向、隔离、登记白名单或明确标为未处理。
- 文档、状态卡、工作日志和看板一致。
- KPI 可由结构化数据重新计算。
- 最终状态有明确依据。

### 18.2 全局完成

只有同时满足以下条件，才可宣告全局完成：
1. 19 个项目全部有明确终态。
2. 每项目至少 10 类测试有记录，目标为 12 类全覆盖。
3. 关键场景回归满足要求；未执行项未被计为通过。
4. 阻断性问题已修复或明确标记阻塞。
5. Qoder 系列监控日志已解析并完成实际对照。
6. WinClaw 图标正确且可正常启动。
7. Lobster 可正常启动。
8. 系统写入与白名单审查有可追溯证据。
9. 测试报告、问题单、坑点、白名单、SBOM、许可证和开源文档齐全。
10. 总看板、状态卡、结构化数据、阶段报告与最终总结一致。
11. 所有发布材料可追溯，未擅自向公共仓库发布。
12. 未验证与阻塞事项如实披露。
