## 一、输入法绿色化

### 1.1 清风输入法无法进入切换列表（v1.0 重大缺陷）

- **现象**：绿化后按 Win+Space / Ctrl+Shift 切换输入法，清风输入法**不出现在切换列表中**，无法启用。
- **根因**：v1.0 只注册了 HKLM 的 CLSID 与 CTF TIP，**遗漏了 HKCU 用户级切换列表** `HKCU\Software\Microsoft\CTF\SortOrder`。Windows 的输入法切换列表是**用户级**配置，仅写 HKLM 不足以让输入法进入当前用户的可切换集合。
- **解决方案**（v2.0 修复）：绿化脚本新增 HKCU SortOrder 注册，**动态追加索引**到现有列表末尾；卸载脚本按 CLSID 匹配一一对应删除。
- **预防措施**：任何 TSF 输入法绿化都必须同时处理 HKLM（CLSID + TIP）与 HKCU（SortOrder + DirectSwitchHotkeys + Assemblies），三处缺一不可。

### 1.2 切换快捷键不统一

- **现象**：绿化后 Ctrl+Space 无法在中英文间切换。
- **根因**：未注册 `HKCU\Software\Microsoft\CTF\DirectSwitchHotkeys`。
- **解决方案**（v2.0 修复）：绿化脚本新增 DirectSwitchHotkeys 注册，统一 Ctrl+Space 切换快捷键；卸载时按 CLSID 匹配删除。

### 1.3 IimServer 自启残留指向原版路径

- **现象**：卸载原版冰凌输入法后，`Run` 键仍残留指向**原版安装路径**的自启项，开机报错或静默失败。
- **根因**：v1.0 绿化时直接写了 `Run` 键（或沿用了指向原版路径的值），原版卸载后路径失效。
- **解决方案**（v2.0 修复）：绿化时**不再写 Run 键**，或确保其指向绿色目录；卸载脚本清理对应残留。
- **预防措施**：绿色化脚本对任何自启项都要么不写、要么指向 `%~dp0` 绿色目录，绝不沿用原版绝对路径。

### 1.4 半成品注册（目录缺文件仍写入注册表）

- **现象**：绿色目录文件不完整时运行绿化脚本，注册表写入成功但输入法无法使用，排查困难。
- **根因**：v1.0 缺少文件完整性前置校验。
- **解决方案**（v2.0 修复）：绿化前校验目录内关键文件，缺失时以**退出码 3** 拒绝执行，杜绝"注册成功但不可用"的半成品状态。

### 1.5 绿化/卸载后输入法框架不生效

- **现象**：绿化完成后输入法未出现在语言栏，需重启系统才生效。
- **根因**：ctfmon（文本服务框架宿主进程）仍持有旧的输入法注册缓存。
- **解决方案**（v2.0 修复）：绿化/卸载结束后**结束相关进程并重启 ctfmon**，输入法框架即时生效，无需重启系统。

## 二、便携化通用

### 2.1 在监控日志分析完成前编写 launcher.ini

- **现象**：凭经验猜测软件的注册表键与数据目录，生成的 launcher.ini 看似合理，实测时配置不持久或宿主残留。
- **根因**：跳过了九步工作流的第 1、2 步（读日志、分析写入行为），配置缺乏事实来源。
- **解决方案**：launcher.ini 中**每一个注册表键和文件路径都必须来自监控日志**，并在配置注释中标注对应日志行号或关键字。
- **预防措施**：执行九步工作流不得跳步；项目质量红线第 1、4 条（不猜测、未分析不动笔）。

### 2.2 RegistryCleanupIfEmpty 清理顺序错误

- **现象**：便携版退出后，宿主注册表仍残留 `HKCU\Software\{厂商}` 父键。
- **根因**：清理顺序写成了先父后子——父键因尚有子键而无法删除。
- **解决方案**：编号顺序必须**先清理深层子键，再逐层向上清理父键**。例如先 `HKCU\Software\Tencent\WeMeet`，再 `HKCU\Software\Tencent`。

### 2.3 把卸载注册表项导入最终用户系统

- **现象**：为方便"干净卸载"，把分析用的卸载 `.reg` 直接导入用户系统，导致误删共享键或系统键。
- **根因**：混淆了"分析原料"与"部署产物"——卸载注册表项只用于分析软件写入了什么，**绝不是部署脚本**。
- **解决方案**：质量红线第 3 条——卸载注册表项仅用于分析，绝不导入最终用户系统；同时不得放入最终便携包。

### 2.4 对系统级软件强行便携化

- **现象**：试图把依赖系统服务、驱动、Shell 扩展或实时监控的软件做成便携版，最终启动失败或系统不稳定。
- **根因**：这类软件的组件必须由系统级机制加载，无法通过数据重定向隔离。
- **解决方案**：选路决策第一关即识别此类软件，**直接标记为不适合便携化并说明原因**，不浪费制作成本。
- **预防措施**：制作前先用 Total Uninstall 监控安装过程，确认无服务/驱动/Shell 扩展写入。

### 2.5 忽视开机自启、计划任务与后台进程

- **现象**：便携版退出后，`Zoom.exe`、`WeMeetApp.exe`、输入法外挂进程仍在后台运行；或重启后软件被自启项拉起，破坏"零残留"承诺。
- **根因**：只处理了数据目录与注册表配置，没处理三类系统集成分支。
- **解决方案**：`Custom.nsh` 专门处理且仅处理这三类——`Run` 键自启项删除、`schtasks /delete` 删计划任务、`FuncEnd` 钩子强制结束后台进程。
- **预防措施**：视频会议与输入法类软件必须检查这三类；更新后必须重新检查（新版可能重新注册自启）。

### 2.6 便携目录移动后失效

- **现象**：把便携包目录移动或改名后，软件无法启动或配置丢失。
- **根因**：（绿色化路线）注册表写的是绝对路径，移动目录即失效；（便携化路线）PAL 结构本身支持任意路径，但若配置文件写死了盘符绝对路径同样失效。
- **解决方案**：绿色化部署后**不要移动目录**；便携化配置一律使用 `%PAL:DataDir%`、`%PAL:LastDrive%` 等变量，不写死盘符。
- **预防措施**：验证清单第 6 条——必须把便携目录复制到**不同盘符路径**下测试配置可读。

### 2.7 验收脚本的四个假阳性/假阴性陷阱（2026-10-15 实战）

批量验收脚本 `_analysis\test_portable.py` 首轮跑出"5/18 通过"的惨状，逐条排查后**大部分是脚本自身的判定缺陷**，不是便携包有问题。

- **现象**：同一批包反复出现"主程序没起来""宿主大量泄漏"，但手工复跑又正常。
- **根因**（四个独立缺陷）：
  1. **按映像名全局强杀**：收尾用 `taskkill /IM <名>.exe`，Trae CN / WorkBuddy / Cursor 等便携包与宿主正式安装版**同名**，直接把宿主的 IDE 及其整个进程树杀掉（本次连测试会话本身都被打断）。
  2. **启动前不清 RuntimeData**：异常退出遗留的 `Data\PortableApps.comLauncherRuntimeData-<包名>.ini` 会触发 CrashCleanup 弹框，之后所有钩子不执行 → 看起来"启动器没反应"（MiaoshouPortable 因此假 FAIL）。
  3. **泄漏判定收进 `%LOCALAPPDATA%\Temp` 噪声**：PAL 的 Temp 段会建 `Temp\<包名>Temp`，NSIS/Electron 还会吐 `nsn*.tmp`、`safe-rm-protection-flag-*` 等瞬时文件，正常退出自行清理，却造成大面积假泄漏。
  4. **`wmic` 输出丢字**：`wmic process get ExecutablePath /FORMAT:CSV` 经管道按本地代码页编码，用 `errors="ignore"` 解码时非 ASCII 路径（`妙手.exe`）被静默丢弃 → 名字判空，把"已启动"误判成"未启动"。
- **解决方案**：
  - 收尾一律**按可执行路径**限定（`kill_scoped()`：先 `taskkill /PID` 优雅关闭并等 12s 让 PAL 退出钩子跑完，再 `/F /PID /T` 兜底）；**严禁** `taskkill /IM`。
  - `test_one()` **启动前**调 `clean_runtime(data_dir)`。
  - 泄漏过滤排除 `Temp` 及其子项。
  - 进程枚举改用 `psutil.process_iter(["pid", "exe"])`（走原生 Unicode API，彻底免疫代码页问题）。
  - 残留 junction 用 `sweep_junctions()` **全量扫顶层联接**（只拆目标指向本项目 Work 的），不能只看"测试期间新增的顶层名"——联接名若测试前就存在，`after - before` 里根本不出现，残留会被静默漏过。
- **预防措施**：验收脚本本身也要验收——任何"大面积 FAIL"先怀疑判定逻辑；**任何按名操作的进程动作都要先问一句"这个名字会不会命中宿主的同名程序"**。

## 三、Electron / VS Code 系

### 3.1 ELECTRON_RUN_AS_NODE 脏环境变量导致闪退

- **现象**：WorkBuddy 等 Electron 应用通过便携启动器拉起时闪退或无窗口，直接在命令行运行主程序却正常。
- **根因**：宿主环境残留 `ELECTRON_RUN_AS_NODE` 等环境变量（常见于安装过多个 Electron 开发工具的机器），Electron 运行时将其误解为 Node 模式，跳过主进程窗口创建。
- **解决方案**：`_analysis\launcher_wrapper.py` 生成 `_launcher.bat` 包装层——启动主程序前**显式清除** `ELECTRON_RUN_AS_NODE` 等脏变量，并设置 `APPDATA / LOCALAPPDATA / TEMP` 指向便携 `Data\`，再启动主程序。
- **预防措施**：Electron 系软件一律走包装层启动；调试期用 `probe_electron.py`、`probe_wrapper*.py` 系列脚本定位环境变量干扰。

### 3.2 只改 launcher.ini 而忽视包装层环境

- **现象**：`[Environment]` 已在 launcher.ini 配置重定向，但数据仍写入宿主 APPDATA。
- **根因**：部分 Electron 应用在 PAL 环境变量生效**之前**就完成了路径解析，或存在多进程（主进程 / 渲染进程 / GPU 进程）环境继承不一致。
- **解决方案**：launcher.ini 的 `[Environment]` 与 `_launcher.bat` 包装层**双保险**；用 `verify_redirect.py` 对比启动前后 Data 与宿主 APPDATA 的文件变化来确认真实生效。
- **预防措施**：Electron 系软件的重定向**必须经 `verify_redirect.py` 实测确认**，不能只看配置。

### 3.3 launcher.ini 反复修复的历史教训

- **现象**：`_analysis` 目录存在大量修复脚本（`fix_ini.py`、`fix_env.py`、`fix_launcher_keys.py`、`fix_launcher_values.py`、`fix_missing.py`、`fix_patch_vars.py`、`fix_custom_nsh.py` 等），反映 launcher.ini 曾反复出现键名拼写、变量引用、取值格式错误。
- **根因**：早期手工编写多个便携包的 ini 配置，缺乏统一的生成与校验机制。
- **解决方案**：沉淀 `build_batch3.py` / `build_batch45.py` 等**通用构建器**，把 Cursor、Trae CN、CodeBuddy CN、Qoder CN、WorkBuddy 等 VS Code 系包的主程序、版本、AppInfo 与 launcher 参数集中定义，机器生成代替手工编写。
- **预防措施**：同类软件一律走通用构建器；新增软件先加进构建器配置，不手工复制旧 ini。

### 3.4 USERPROFILE 重定向把 Electron 应用搞崩——多包复现与通用规律（2026-10-15 实战）

- **现象**：OfficeAce / MiniMaxCode / AiPyPro 三个便携包经 PAL 启动后**进程塌缩、无窗口**（13→1 / 7→1 / 9→1 个进程）；直接双击本体或只改 `APPDATA / LOCALAPPDATA / TEMP / TMP` 均正常出窗口。
- **根因**：launcher.ini 的 `[Environment]` 写了 `USERPROFILE=%PAL:DataDir%\settings\user`。用 `bisect_env.py` 双分定位（clean → 仅 APPDATA+LOCALAPPDATA → +TEMP/TMP → 全套含 USERPROFILE）实测：**USERPROFILE 一改写 Electron 启动即塌缩**，与 TodayCN（见 4.7）完全同型。这不是孤例，而是一类 Electron 应用的共性——它们对 `os.homedir()` 被改写极其敏感。
- **解决方案**：
  - `[Environment]` **删掉 USERPROFILE 行**，并在 ini 注释里写明"禁止重定向"的原因和实测证据，防止后人"补全"时再踩。
  - USERPROFILE 下的落点（OfficeAce→`.office-claw`、MiniMaxCode→`.minimax`、AiPyPro→`.aipyapp`+`aipywork`）由 Custom.nsh 建 **Junction** 收纳到 `Data\settings\` 下，启动前建、退出时拆（rmdir 不带 /s），宿主零残留。
  - **同一应用可能同时写 USERPROFILE 和 APPDATA 两处**（MiniMaxCode 还写 `%APPDATA%\MiniMax`，AiPyPro 还写 `%APPDATA%\aipy-pro`）——只 junction USERPROFILE 不够，必须实测运行期宿主 APPDATA 是否有新增目录，发现即补 junction。
- **预防措施**：
  - `[Environment]` 里 USERPROFILE **不是标配**：新包先按最小集（APPDATA / LOCALAPPDATA / TEMP / TMP）跑通，再加项；每加一项都实测主程序能起。
  - Electron 应用排查崩溃时，"进程数塌缩"是强信号：正常 Electron 启动后应有 5+ 进程（主进程+渲染+GPU+工具），只剩 1 个基本就是启动即崩。
  - 验收时不能只测"能打开"——必须同时检查宿主 USERPROFILE 和 APPDATA 两侧是否新增目录，Electron 的落点经常分散在多处。

### 3.5 Custom.nsh 钩子宏名静默失效——三个包集体中招（2026-10-15 实战）

- **现象**：OfficeAce / MiniMaxCode / AiPyPro 的 `Custom.nsh` 里写了完整的清理函数（KillResidual / DeleteRunKey / DeleteUpdateTask / DeleteFileAssoc），但运行后宿主残留进程、开机自启项、文件关联全部没清——整个 Custom.nsh **从未被执行过**。
- **根因**：三个包的钩子宏名写成了 `CustomInit` / `CustomPreStart` / `CustomPostClose` / `CustomUnInit`（或 `Custom.nsh` 缺下划线），而 PAL 只认 `Custom.nsh_<阶段>` 格式（Segments.nsh L54）。宏名不匹配 → NSIS 编译不报错 → PAL 运行时不调用 → **静默失效，无任何报错**。TodayCN 之前踩过同一个坑（见 4.7）。
  - **第三种形态（2026-10-15 FoxitPDF 复查发现）**：`Custom.nsh` 文件**整体缺失**——PAL 的 `!include /nonfatal`（Segments.nsh L122）对不存在的 Custom.nsh 静默跳过，编译、启动、试点批次泄漏检测**全部通过**，但收尾清理（残留进程/自启/计划任务/文件关联）与顽固路径 junction 兜底从未存在。这说明"验收通过"只能证明已配置的机制有效，**不能证明该配的机制都配了**。
- **解决方案**：钩子宏名一律用 `Custom.nsh_PreExecPrimary`（主程序启动前）/ `Custom.nsh_PostPrimary`（主程序退出后）/ `Custom.nsh_Unload`（卸载前）；改完**必须重编译启动器**（Custom.nsh 是编译期内嵌，改文件不重新编译等于没改）。
- **预防措施**：
  - 新包的 Custom.nsh 一律从已验证的模板（TodayCNPortable）复制改包名，不手写宏名。
  - 验收时加一个硬检查：启动后宿主目标路径是 junction（`Get-Item` 的 LinkType=Junction），如果还是真实目录，说明钩子没执行——这是最直接的"钩子失效"信号。
  - 编译后用调试模式（`PAL_DEBUG=1`）跑一次，看 debug.log 里 `Custom/PreExecPrimary`、`Custom/PostPrimary` 段是否真的执行了（About to execute / Finished executing 成对出现）。

  - **第四批中招（2026-10-16 启动器配置全量审计发现）**：Cursor / CodeBuddyCN / Comate / JoyCode / WorkBuddy 五包仍是同一套旧宏名 + `$INSTDIR` + 裸函数调用（宏体从未被 insert 编译，所以裸调用也不报错）。用 `Work\_analysis\audit_launcher_config.py` 普查 + `fix_dead_hooks.py` 机械改写（宏名→`Custom.nsh_*`、`$INSTDIR`→`$EXEDIR`、裸调用→`Call 函数名`）后重编译闭环。**教训：凡从旧模板批量生成的包，其 Custom.nsh 必须过审计脚本，不能只看单个包修没修。**
  - 同轮审计澄清：这 5 包及 LobsterAI/Miaoshou/WinClaw/QoderCNIDE/CodeArtsAgent 的 ini 里 `USERPROFILE` 重定向**仍然保留且实测不崩**（Cursor 用全新空 Data 目录首启验证通过，窗口/进程/Data 生成全正常）——3.4 的崩溃只在"重定向目标目录不存在且 app 在 boot 早期调 appData"时触发，PAL 会先建 `Data\settings` 故这些包不中招。**是否删 USERPROFILE 以实测为准，不做无证据的批量删除。**

## 四、具体软件

### 4.1 Zoom：打开便携目录后浏览器自动下载 Zoom

- **现象**：双击打开 `ZoomPortable` 目录（尚未运行任何程序），浏览器却自动开始下载 Zoom 安装包。
- **根因**（两种可能，按概率排序）：
  1. 目录中存在指向**在线 stub 安装器**的脚本/快捷方式，或被放置了触发 `zoommtg://` 协议唤醒的链接——浏览器/系统解析该协议时自动拉起下载；
  2. 误用了 Zoom 在线安装器而非离线完整安装包。
- **解决方案**：检查目录中是否存在协议链接或在线安装器引用；确认使用**离线完整安装包**（MSI 或完整 EXE）；便携启动器只引用本地 `App\Zoom` 下的程序。
- **预防措施**：安装包一律从官方离线渠道获取；`zoommtg://` 等自定义协议的关联文件不得进入便携包。

### 4.2 WeMeet（腾讯会议）：环境变量→FilesMove→Junction 三轮迭代终局（2026-10-15 实战）

- **现象**：WeMeetPortable 能正常启动，但用户数据（Global/Users 等 387.9 MB）全部写到宿主 `%USERPROFILE%\AppData\Roaming\Tencent\WeMeet`，Data 目录为空——完全失去便携性。同时启动时弹出一个无文字的红叉对话框。
- **根因（三层叠加）**：
  1. **弹框**：上次异常退出残留 `Data\PortableApps.comLauncherRuntimeData-WeMeetPortable.ini`，本次启动走 CrashCleanup 分支弹框（见 6.x 踩坑清单第 5 条）。
  2. **数据泄漏**：WeMeet 不认进程环境变量。主进程调 `SHGetFolderPath`、CEF 子进程（WMExternal/XnnExternal）走 **KnownFolder API**——二者都绕过进程环境块。launcher.ini 的 `[Environment]` 段只对 `getenv()` 类程序有效；Custom.nsh 的 `SHSetFolderPathW` 只修正**当前进程**的 Shell 视图，子进程重新初始化后即失效。且 `SHSetFolderPathW` 会改写注册表 Shell Folders，**反过来干扰 PAL FilesMove 对 %APPDATA% 真实路径的解析**——必须弃用。
  3. **Custom.nsh 隐性 bug**：`System::Call 'kernel32::SetEnvironmentVariable(t, t)' '.r0' '路径'` 的第一个参数是字面字符串 `.r0`，实际设置了一个名叫 `.r0` 的环境变量，三次调用全无效。
- **解决方案（三轮迭代，Junction 为终局）**：
  - **第一轮（环境变量，失败）**：`SetEnvironmentVariable` 对 SHGetFolderPath/KnownFolder API 无效。
  - **第二轮（FilesMove，跨盘失败）**：PAL 原生 `[FilesMove]` 同盘可用，但**跨卷（便携包在 D 盘、宿主 APPDATA 在 C 盘）时 PAL 退化为【复制】**（Data 侧源完整保留），退出时"搬回"因 Data 侧已有同名目录而**静默失败**——宿主残留 + 会话数据变更丢失（实测复现：正常退出后宿主 473 MB 数据残留，靠 robocopy 手动救回）。
  - **第三轮（Junction，闭环 ✅）**：`Custom.nsh` 里用 `mklink /J` 把宿主 `%APPDATA%\Tencent\WeMeet` 建成指向 `Data\settings\Tencent\WeMeet` 的目录联接，退出时 `rmdir`（**不带 /s**，只删链接）。Junction 是文件系统级指针，对一切 API 透明，**零搬运、跨卷无感、无搬回失败风险**。实测闭环：启动→junction 建立（ReparsePoint，目标=Data）→运行日志实时落 Data→退出→宿主路径消失、Data 473 MB 完好、零残留。
- **Junction 实现要点**（代码见 [Custom.nsh](file:///<旧工作区>/Work/WeMeetPortable/App/AppInfo/Launcher/Custom.nsh)）：
  - 路径解析用 NSIS 内置 `$APPDATA` 常量（SHGetFolderPath 读注册表），**不受 PAL `[Environment]` 改进程环境的影响**；绝不能在 `cmd /c` 里用 `%APPDATA%`（继承被改的进程环境，会指向便携路径）；
  - 判断 junction vs 真实目录：`GetFileAttributesW & 0x400`（FILE_ATTRIBUTE_REPARSE_POINT）；宿主真实目录先 `robocopy /E /XO` 合并回 Data 再移除，残留 junction 直接 `rmdir`——**绝不丢数据**；
  - 删联接**只用 `rmdir` 不带 /s**，防止删穿 junction 误删 Data 数据（`rmdir /s` 会删穿！）；
  - 异常退出后 junction 残留无害（数据本就在 Data），下次启动 PreExec 检测残留自动 rmdir 重建（幂等自愈）；
  - 退出钩子在 `Custom.nsh_PostPrimary`（主程序退出后 PAL 执行）；`Custom.nsh` 必须**带 UTF-8 BOM**，否则 Unicode makensis 静默解析中断（编译后必查 BOM）。
- **托盘程序自动退出方法**（验收用）：托盘进程可能**无任何顶层窗口**（窗口数为 0），WM_CLOSE 无处投递、pywinauto taskbar 对溢出隐藏区支持不稳。可靠方法：Toolhelp32 枚举进程所有线程 → `PostThreadMessageW(tid, WM_QUIT, 0, 0)` 让消息循环正常退出（脚本沉淀于 `_analysis\_tray_quit_wemeet.py`）。
- **关键操作纪律**：
  - **绝不搬运共享目录**：`%APPDATA%\Tencent\` 下的 `Marvis`（宿主独立安装的 Marvis 套件，`<本机工具目录>/Marvis` 7 进程常驻）、`beacon/BeaconConfig/DtConfig`（腾讯系多软件共享埋点缓存）、`xwechat/Androws/qimei`（微信）**都不是 WeMeet 的数据**。FilesMove 只登记 WeMeet 专属子目录，逐目录核对归属，不确定时用进程路径反查（`Get-Process | Select Path`）。
  - **删除宿主目录前必须确认无进程占用**：被占用的目录极可能属于正在运行的其他软件（本次 Marvis 即因此被识别）。
- **预防措施**：凡"环境变量重定向无效"的软件（实测数据仍落宿主），**跨盘场景直接用 Junction 方案**（FilesMove 仅同盘可用）；迁移数据前列出宿主目录清单逐一确认归属。同类顽固软件（KnownFolder API 类）复制 WeMeet 的 Custom.nsh 宏组（`WM_IsJunction` / `WM_JunctionCreate` / `WM_JunctionRemove`）即可复用。

### 4.2.2 Zoom：自动更新下载根治——方案A证伪与「直启+Junction」终案（2026-10-15 实战）

- **现象**：启动 ZoomPortable 后，无论是否已安装都会后台自动下载更新包（`Zoom.msi` 36.67MB + `vcredist_x86.exe` 4.02MB + `Installer.exe` 1.12MB 共 41.8MB 落 `Zoom\ZoomDownload`）；判定"未安装"时更从 zoom.us 全量下载 268MB。
- **根因（四层叠加）**：
  1. **下载主犯是 Zoom_launcher 自身**：它是引导下载器，读 `HKCU\Software\ZoomUMX\InstallLocation` 拼 `\Zoom.exe` 找程序——找不到→全量下载 268MB 装到 `%APPDATA%\Zoom\bin`；即使找到，后台仍闲时下载 41.8MB 更新包（安装日志 L909/L1003 确证其"自安装到用户目录"设计）。
  2. **方案A（删 zUpdater.exe）实测证伪**：删除后 41.8MB 下载依旧——zUpdater 只是被拉起的执行组件，下载行为由 launcher 发起。此条推翻 4.1 的隐含假设，证明"删更新组件"对"引导器型"软件无效。
  3. **Zoom.exe 写数据用 SHGetFolderPath/KnownFolder API**：`[Environment]` env 重定向完全无效（直启实测 28.84MB 泄漏宿主 `%APPDATA%\Zoom`）——与 WeMeet 同款顽固，必须 Junction。
  4. **PAL 钩子两处隐性 bug**：`$INSTDIR` 在 PAL 启动器中**未初始化展开为空**（杀进程函数长期静默失效），路径一律用 `$EXEDIR` 运行时拼接；`!define` 含 `$EXEDIR` 会在**编译期**展开成字面量（导致启动器崩溃退出码 -1073741571）。
- **解决方案（终案：直启 + Junction，两轮实测三项全 PASS）**：
  - **直启绕过 launcher**：`launcher.ini` 直接 `ProgramExecutable=Zoom\bin\Zoom.exe`——PAL 拉起真程序，`Zoom_launcher.exe` 永不执行，下载链从源头消失。无需 ShellExecute 钩子、无需同步 bin 到 Data、无需伪造 InstallLocation 标记（前三轮方案的过度设计全部回滚）。
  - **Junction 重定向数据**：复用 WeMeet 宏组（`ZM_IsJunction`/`ZM_JunctionCreate`/`ZM_JunctionRemove`），启动前建 宿主`%APPDATA%\Zoom` → `Data\settings\user\AppData\Roaming\Zoom`，退出 `rmdir`（不带 /s）拆除，宿主零残留。
  - **兜底三件套**：启动时删 `zUpdater.exe`（幂等）+ 按前缀 `ZoomUpdateTaskUser*` 通配删计划任务（任务名内嵌用户 SID）+ 删 Run 键自启项。
  - **验收**（脚本 `_analysis\_zoom_direct_junction_test.py` + `_zoom_portable_e2e_test.py`）：直启 90s 零下载；e2e 全流程 junction 生命周期正常、从 App\bin 拉起、退出零残留；**首次启动场景**（Data 无 Zoom 目录）自动建结构、Zoom 从零初始化 0.18MB 落 Data。Data 侧旧方案 robocopy 的 268MB 程序副本已清除。
- **钩子宏名三轮踩坑**（PAL Custom 钩子正确格式）：`CustomPreStart`/`CustomPostClose`（PAL 不认）→ `CustomPreExecPrimary`（仍不认）→ **`Custom.nsh_PreExecPrimary`**（正确，见 Segments.nsh L54 `!insertmacro ${Segment}.nsh_${__FUNCTION__}`，格式为 `Custom.nsh_<阶段>`）。
- **本包编码特例**：Zoom 的 `Custom.nsh` 必须 **UTF-8 无 BOM**（带 BOM 报 `Invalid command: ?;`）——与 WeMeet 必须带 BOM **相反**，两包编译器行为不同，按各自编译实测为准，勿互相套用。
- **关键操作纪律**：
  - 测试前必删 `Data\PortableApps.comLauncherRuntimeData-ZoomPortable.ini`（残留触发 CrashCleanup 弹框，所有钩子不执行，会误判成"钩子没生效"）；
  - 下载检测只认**测试开始后 mtime 新增**的文件（首版脚本把历史残留误判为下载证据，虚报 FAIL）；
  - 宿主已有真实 Zoom 目录时的策略与 WeMeet 一致：`robocopy /XO` 合并回 Data 再移除，绝不丢数据。
- **预防措施**：凡"引导器/启动器型"软件（Zoom_launcher、Teams Update.exe、Chrome 的 setup.exe 等），先识别真程序本体，`ProgramExecutable` 直指本体，**不要让引导器进启动链**；便携版固定版本原则下，一切自更新组件（updater/计划任务/Run 键）全删，更新统一走项目 `_更新.bat` 流程；数据重定向按 env→FilesMove→Junction 阶梯，确认 KnownFolder API 类直接上 Junction，不浪费时间试前两级。

### 4.7 Today CN：USERPROFILE 重定向把程序搞崩 + `.updaterId` 走 API 路径泄漏（2026-10-15 实战）

- **现象**：`TodayCNPortable.exe` 启动后主程序秒退，`Data\settings\local\CrashDumps\` 里留下 6 个 `TodayCN.exe.<pid>.dmp`（各约 4MB）；而直接双击 `App\Today CN\TodayCN.exe` 能稳定存活 20s+。PAL `debug.log` 显示全链路正常（ExecString → ExecWait 返回 → 钩子全部执行完毕），即**程序在 PAL 的环境重定向下自己崩了**。
- **根因**：两个互不相关的问题叠在一起。
  1. **崩溃**：launcher.ini 的 `[Environment]` 重定向了 `USERPROFILE=%PAL:DataDir%\settings\user`。用 Python 直接拉起本体做**单变量二分**（每次只改一项环境变量）实测：单独改 `USERPROFILE` 即复现秒退；只改 `APPDATA / LOCALAPPDATA / TEMP / TMP` 均稳定存活。该应用对 USERPROFILE 被改写极其敏感（放弃作进一步内部归因）。
  2. **泄漏**：宿主 `%APPDATA%\Today CN\.updaterId` 仍新增 —— TodayCN.exe 内部用 `SHGetFolderPath` / KnownFolder API 取 Roaming 路径，**该 API 读注册表 Shell Folders，不读进程环境变量**，所以 `APPDATA` 的 env 重定向对它无效（这是本项目"环境变量重定向对 SHGetFolderPath 类 API 完全无效"的又一次复现）。
- **解决方案**：
  - `[Environment]` **删掉 `USERPROFILE` 行**（`Data\settings` / `Data\settings\local` 已覆盖 Chromium/Electron 全部落点，实测 40s 运行上百 MB 全落 Data），并在 ini 里写明"禁止重定向"的原因，防止后人"补全"时再踩。
  - 泄漏用 **Junction 补齐**：`Custom.nsh` 在 `Custom.nsh_PreExecPrimary` 建 宿主`%APPDATA%\Today CN` → `Data\settings\Today CN` 目录联接，`Custom.nsh_PostPrimary` / `Custom.nsh_Unload` 用 `rmdir`（不带 `/s`）拆除；建联接前若宿主路径是真实目录，先 `robocopy` 合并回 Data 再删，保证不丢数据（宏组复用自 ZoomPortable）。
  - 顺带修掉该文件的历史缺陷：原钩子宏名是 `CustomInit` / `CustomPreStart` / `CustomPostClose` / `CustomUnInit`（PAL 只认 `Custom.nsh_<阶段>`，**原名静默失效，整个 Custom.nsh 从未被执行过**），且用未初始化的 `$INSTDIR` 定位进程目录（展开为空 → 过滤条件恒不成立），已全部改为 `$EXEDIR`。
- **预防措施**：
  - `[Environment]` 里 `USERPROFILE` **不是标配**：新包先按最小集（`APPDATA / LOCALAPPDATA / TEMP / TMP`）跑通，再加项；每加一项都要实测主程序能起、且无 CrashDumps。
  - 崩溃排查用"**单变量二分 env**"（Python 直接拉起本体、逐项加变量），比反复重建启动器快一个数量级。
  - 见的 `.dmp` 就是硬证据：`Data\settings\local\CrashDumps\` 出现 `<主体exe>.<pid>.dmp` = 程序在重定向下崩溃，别再怀疑 PAL 逻辑。
  - junction 类修复必须在宿主侧留"幂等自愈"：`TC_JunctionCreate` 遇到残留联接只 `rmdir` 重建，遇到真实目录先合并。

  - Electron 包修复 USERPROFILE 崩溃后**必须复测一轮宿主 APPDATA 增量**，发现新目录立即补 junction——本包就是"修好崩溃才发现泄漏"的典型两段式。
  - 泄漏目录里出现 `Network\Cookies`、`Local Storage\leveldb` 这类**登录态载体**时优先级最高：不收纳等于用户登录态写在宿主，换机即丢。

### 4.9 AiPyProPortable：三落点收纳 + 退出验证的三个坑（2026-10-15 实战）

- **现象**：用户报"打不开"（9 进程塌缩到 1）。修掉 USERPROFILE 重定向并建好 `.aipyapp` / `aipywork` 两个 junction 后窗口能出（标题显示 **"trustoken.ai" / "Trustoken 中国站"** 而非应用名），但复测发现宿主 `%APPDATA%\aipy-pro` 泄漏 **25.8MB**（Electron userData + `aipy` / `aipy-shm` / `aipy-wal` SQLite 三件套 + sentry + extensions）。另在退出验证环节连踩三个坑（见根因 3-5）。
- **根因**：
  1. **崩溃**：USERPROFILE 重定向（同 4.7 / 4.8）。
  2. **泄漏**：`%APPDATA%\aipy-pro` 走 KnownFolder API，env 重定向无效（同 4.8）。
  3. **窗口标题陷阱**：主窗口标题是动态的站点名（"trustoken.ai"），**不是应用名**——按标题找窗口会漏检，必须按"可执行路径过滤 + `MainWindowTitle` 非空"判定。
  4. **托盘驻留型退出**：`CloseMainWindow()` 返回 False、向主线程 `PostThreadMessage(WM_QUIT)` 也无效；可行终案是**只强杀带窗口的主 UI 进程**——PAL 检测到子进程退出后自己跑完 `PostPrimary` 钩子（junction 拆除、残留清理全部完成）。
  5. **验收脚本误杀启动器**：一次清理时把包目录下**所有**进程（含 PAL 启动器本体）一起 `Stop-Process`，启动器先死 → `PostPrimary` 钩子永远没机会执行 → `.aipyapp` / `aipywork` junction 残留在宿主。手工 `os.rmdir` 才拆掉（junction 上 `rmdir` 只删链接不删数据，安全）。
- **解决方案**：
  - ini 删 `USERPROFILE` 行；Custom.nsh 按模板重写（钩子宏名 + `$EXEDIR`），建**三个** junction：`%USERPROFILE%\.aipyapp`、`%USERPROFILE%\aipywork` → `Data\settings\` 下同名目录，`%APPDATA%\aipy-pro` → `Data\settings\aipy-pro`；重编译。
  - 退出验证流程固化为：`CloseMainWindow()` 失败 → **仅**对"可执行路径在本包内且 `MainWindowTitle` 非空"的主进程 `Stop-Process -Force` → 等 15-20s 让 PAL 钩子跑完 → 校验 junction 已拆、进程归零。
  - 验收脚本清理残留进程时**必须排除 PAL 启动器进程**（包根目录下与包同名的 exe）。
- **实测验证**：窗口正常（9 进程）；三个 junction 全部 `LinkType=Junction`、Target 指向 Data；Data 64.3→80.1MB；强杀主进程后残留归零、三 junction 全拆、宿主零残留。
- **预防措施**：
  - AiPyPro 这类 **AI 站点套壳应用**的窗口标题 = 内嵌站点名，窗口判定一律走"路径 + 标题非空"双条件，禁止按标题字面量匹配。
  - SQLite 主库带 `-wal`/`-shm` 副车文件随包运行属正常（见 2.7 持久化对比规则），但**位置在宿主**就是泄漏，本案即靠 `aipy-wal` 的 mtime 定位到 `%APPDATA%\aipy-pro`。
  - "杀光包目录进程"和"让 PAL 优雅收尾"互斥：要先收尾验证，后兜底清扫；顺序颠倒必然留下 junction 残留。

### 4.10 CodeArtsPortable：旧编译产物让"已修好"的钩子失效 + 单实例残留把复测变成空跑（2026-10-15 实战）

  - 调试验证完**按普通模式再编译一次**发布（调试构建会把 `Data\debug.log` 写进用户数据目录），并对发布二进制再跑一轮快速回归。

- **实测验证**（发布二进制 + 持久化实证）：向 `Data\settings\codearts\` 写标记文件 → 启动 → 退出（junction 拆除、标记保留）→ 二次启动读回标记内容一致 → 最终退出后宿主零残留、`Data\debug.log` 未生成、RuntimeData ini 自动清除。数据保存链路（Data 落盘 + 跨启动持久化）完整通过。
- **预防措施**：
  - **改完 Custom.nsh / launcher.ini 必须重编译**，并把"重编译"列为修复 checklist 的最后一步；判断部署是否最新，比对 exe 与 Custom.nsh 的 mtime。
  - 调试模式（`PAL_DEBUG=1`）只用于取证，验证完**必须按普通模式重新编译发布**。

### 4.11 QoderCNPortable：launcher state 机制拒绝启动 + `install-type.json` 改 "system" 是毒药（2026-10-15 实战）

- **现象**：用户报"打不开"。PAL 拉起后 2 进程、窗口标题 "Error"（截图内容是 Qoder 加载动画）；`--verbose` 直启控制台报 `[Launcher] Startup selection failed { code: 'WINDOWS_LAUNCHER_STATE_MISSING' }`。此前还有 7 个残留进程 + RuntimeData 残留（CrashCleanup 风险）叠加。

  - Junction 收纳 `~\.qoder-cn`（638MB，agent/模型/扩展缓存）。

### 4.13 QoderCNPortable：Electron userData 第三落点逃逸——`--user-data-dir` 与环境变量都盖不住 appData 拼接（2026-10-16 动态落盘测试发现）

- **现象**：20 包动态落盘验证中，QoderCN 运行 30s 即向宿主 `%APPDATA%\com.qodercn.app.stable` 写入 63 文件/8.3MB（auth.v1.dat、main.sqlite、Preferences、Cache）。而 `launcher.ini` 的 `APPDATA` 重定向和 `--user-data-dir=Data\settings` 均已配置——两条既有防线同时失效。

### 4.14 JoplinPortable 建包三坑：双层解包取错位数、`--profile` 与 Junction 的分工、显示环境变化的归因陷阱（2026-10-16）

- **现象一**：解包 Joplin-Setup-3.7.21.exe 后直启，120s 无窗口且**该进程连一个顶层窗口都没有**（EnumWindows 总数 0），但 CDP 调试端口显示 renderer 已运行；stderr 报 `keytar.node is not a valid Win32 application` 与 `onnxruntime 找 ia32 binding`。
- **根因一**：electron-builder 的 NSIS 安装器是双层打包——外层 `$PLUGINSDIR\app-32.7z / app-64.7z`，内层才是程序本体。解包脚本用 `sorted(...)[0]` 取内嵌包，`app-32.7z` 按字典序排在 `app-64.7z` 前面，**解出了 32 位包**：32 位主进程加载 x64 native 模块（keytar/onnxruntime 均为 unpacked 的 .node）→ 架构错配三症状叠加。
- **解决方案一**：7z `e` 命令显式按名提取 `$PLUGINSDIR\app-64.7z` 再解第二层；解包后必须用 pefile 复核 `Joplin.exe` 与关键 `.node` 的 `FILE_HEADER.Machine`（0x8664=x64 / 0x014c=x86）一致才算解包成功。
- **现象二**：换成 64 位包后，主数据落点 `~\.config\joplin-desktop` 被 `--profile` 参数完全盖住（直指 Data），但 `%APPDATA%\Joplin` 仍有 46 文件 Chromium 层残留（GPUCache/DawnGraphiteCache/Local Storage/Network）。
- **根因二**：Joplin 主进程 `setPath` 只挪走自己组件；Chromium 网络层/GPU 缓存仍按默认 `userData`（`SHGetKnownFolderPath` + productName）写入——**环境变量重定向无效**（4.13 同机理）。
- **解决方案二**：三层防线分工——`--profile "%PAL:DataDir%\settings\profile"` 收主数据（官方 CLI 参数，第一道）；launcher.ini 重定向 `APPDATA/LOCALAPPDATA/TEMP`（第二道）；Custom.nsh 双 Junction 兜底 `%APPDATA%\Joplin` 与 `~\.config\joplin-desktop`（第三道）。实测双轮：103 文件/7.8MB 全落 Data、退出双链零残留、database.sqlite 持久化保留。
- **现象三**：GPU 参数四连试、官方安装器静默安装对照全部无窗口后，复跑此前 PASS 的 Zoom/TodayCN **也全部无窗口**。
- **根因三**：宿主显示环境在 23:22-23:41 之间变化（awesun 向日葵远控会话重连/显示驱动切换），当前桌面会话内**所有 Electron 主窗口都无法创建**——Joplin 无窗口并非包缺陷。
- **预防措施**：
  - electron-builder 双层解包：**按文件名精确取 app-64.7z**，禁止 `sorted()[0]`；解包后 PE Machine 必检。
  - 支持 `--profile` 型 CLI 参数的应用（Joplin/部分 Electron），优先用它做主数据第一道防线，Junction 只兜底环境变量管不住的 KnownFolder 层残留。
  - **窗口验证前必须先跑一个"已知能出窗口的包"做环境对照**——环境失败时全部窗口结论作废，防止把环境问题归因到新包（本次若先归因 Joplin 就会白修）。Joplin 的窗口显示待显示环境恢复后补验。

### 4.15 SublimeTextPortable：钩子「假失效」真凶是宿主同 AppID 实例占用 PAL 互斥体（2026-10-16 实战）

- **现象**：首轮动态验证 HOOK_FAIL——`App\SublimeText\Data` junction missing、`Data\custom_hook.txt` 未写入、宿主 `%APPDATA%\Sublime Text` 泄漏 201 文件；而同模板同管线构建的 SoloMDPortable 却 PASS。
- **根因**：宿主 `D:\SoftApp\Develop\SublimeTextPortable\` 有一个**正在运行的同 AppID 便携实例**（用户自装的官方便携版）。PAL 的 `Segments\InstanceManagement.nsh` L16 用互斥体 `PortableApps.comLauncher$AppID-$BaseName` 查重——AppID 与 exe 名完全相同时互斥体名撞车，新实例被判 `Launcher already running: secondary launch`（debug.log L230 实证），走 secondary 路径：**跳过 PreExecPrimary/PostPrimary、强制 WaitForProgram=false**，junction 钩子自然永不执行。这与编译无关（!error 探针证明 Custom.nsh 已正常 include）。
- **解决方案**：礼貌关闭宿主在用实例（WM_CLOSE + 轮询进程归零，Sublime hot-exit 保未保存内容），互斥体释放（CreateMutex 实证 GetLastError 由 183 归 0）后重测直接 PASS。
- **预防措施**：
  - **钩子失效排查顺序**：① `!error` 编译期探针证 include（注意 build_launcher 只回显 makensis 尾部 12 行，`!warning` 会被吞，必须用 `!error` 二分）；② `PAL_DEBUG=1` 重编译跑 debug.log 看 `Custom/*` 段是否成对（取证后必须普通模式重编译）；③ 全局枚举进程查**同 AppID/同名启动器**残留（不限包目录）。
  - 测试同 AppID 软件前必须全局查 PAL 互斥体冲突（`Work\_analysis\check_mutex.py`）。
  - 勿把「环境干扰」误判为「打包缺陷」——本次若先改 Custom.nsh 模板就是白修。

### 4.16 FeishuPortable：真实落点是 LarkShell 不是 Feishu + 托盘驻留收尾 + 7z SFX + api 版本前缀（2026-10-16 实战）

- **现象一**：首轮验证 junction 双建（`%APPDATA%\Feishu`、`%LOCALAPPDATA%\Feishu`）却仍 LEAK——`%APPDATA%\LarkShell` 236 文件 27.4MB、`%APPDATA%\LarkShellSingleton` 锁文件逃逸。
- **根因一**：飞书 8.x 的 Electron 壳沿用了国际版 Lark 的品牌目录名，**主数据落点是 `%APPDATA%\LarkShell`，单实例锁在 `LarkShellSingleton`**，`Feishu` 目录只是壳层配置。凭软件名猜落点必漏——必须以首轮动态验证的泄漏清单为准补 junction（四处全收后零泄漏）。
- **现象二**：junction 全生效后收尾报 TEARDOWN_FAIL——退出后四条 junction 全残留。
- **根因二**：飞书是**托盘驻留**应用，WM_CLOSE 主窗口只最小化到托盘，主进程不退；测试脚本 40s 轮询耗尽后 `kill_pkg` 无差别连 PAL 启动器一起强杀 → PostPrimary 拆链钩子被跳过（VS Code 系同型教训复现）。
- **解决方案二**：`test_new4.py` 改四段式收尾——WM_CLOSE → 等 12s → `PostThreadMessage(WM_QUIT)` 投给包内全部线程（Toolhelp32 枚举，托盘程序唯一优雅退出途径）→ 等 20s → **只杀非启动器进程**让 PAL 自己走 PostPrimary 拆 junction → 等 40s → 兜底全杀。重测 junction 退出即拆、PASS。
- **现象三**：飞书安装器 `Feishu-win32_x64-8.2.14-signed.exe`（495MB）7z 识别为 `Type=PE`、Linker 14.16，非 NSIS 非 Inno，但 `7z x` 能直接解出完整程序文件。
- **根因三**：它是 **7z SFX 自解压包**（PE 头内嵌 7z 压缩流），单层解开即是程序本体。update_engine extract 已新增 `7z_sfx` 类型通道。
- **现象四**：飞书 api（`feishu.cn/api/package_info?platform=16`）detect 误报「有更新」。
- **根因四**：`data.version_number` 返回 `Windows@V8.2.14` 带平台前缀，`packaging.Version` 解析失败退化为字符串比较。update_engine 的 api 源新增可选 `version_regex`（本包配 `V(\d+\.\d+\.\d+)`）抽取纯版本号；同时 api 的 `version_field/url_field` 支持点路径下钻（`data.version_number`）。
- **预防措施**：新版本源接入必须把 detect 的 `latest_version` 原始串与纯版本号都留档比对；新软件落点一律以首轮泄漏扫描为准，禁止按品牌名臆测目录。

### 4.17 ZenBrowserPortable：Mozilla 风格 7z SFX 直解失败 + PATH 上的 7z.EXE 是缺 dll 的残血版（2026-10-16 实战）

- **现象**：`zen.installer.exe` 走 update_engine `7z_sfx` 通道报 `Cannot open the file as archive`；同机 `7za t` 却能正常列出（`Offset = 131665`、`Method = LZMA:25 BCJ2`）。
- **根因**：两层叠加——① Zen 安装器是 Mozilla 风格 SFX，7z 压缩流在 PE 偏移 131665 处且**尾部还有 10102 字节附加数据**，严格模式直开被拒，独立版 7za 会自动扫签名容错；② PATH 上 `<本机工具目录>/tools\7z.EXE` 缺 `7z.dll`，只是外壳加载器，**任何真实压缩流（尤其 LZMA）都解不了**，Feishu 当时的成功属侥幸路径。
- **解决方案**：`update_engine.find_7z()` 改为**优先独立版 7za**（`shutil.which("7za")` → `<本机工具目录>/tools\7za.exe` → PATH 7z → Program Files），修复后引擎直解 Zen 安装器成功（65 文件，PE x64 复核通过）；侦察期兜底方案是抽签名 `37 7A BC AF 27 1C` 起的核心流另存 `.7z` 再解（`recon_zen.py`）。
- **预防措施**：解包器选型以「无外部 dll 依赖的独立版」为第一优先；`find_7z` 返回值变更后须用真实 SFX 样本回归一次 extract。

### 4.18 WPSPDFPortable：WPS PDF 无官方独立客户端 + 盘上目录被宿主 Total Uninstall 锁死（2026-10-16 实战）

- **现象一**：WPS PDF 官网（pdf.wps.cn）只有在线转换与 236MB 全家桶在线安装器，**没有 PDF 模块的独立离线安装包**。
- **根因一**：金山把 PDF 能力收进 WPS Office 套件统一分发，独立 PDF 客户端已下架。
- **解决方案一**：采用用户预置的「雨糖科技特别版 v12.8.0.23123_x86」（Total Uninstall 监控日志佐证文件清单），`ProgramExecutable=WPSPDF\12.8.0.23123\office6\wps.exe`、`args=/pdf` 直进 PDF 模块；动态验证证实数据落点 `%APPDATA%\Kingsoft`，一条宿主 Junction 收纳即零泄漏。
- **现象二**：建包后想把盘上目录 `Work\WpsPDFPortable` 规范大小写为 `WPSPDFPortable`，`os.rename` 报 WinError 32。
- **根因二**：宿主常驻的 TotalUninstall 便携实例（`Tu_P.exe`，父进程 TUPortable.exe）的 **cwd 停在该目录**（此前用它分析雨糖日志留下的事发现场）。
- **解决方案二**：不杀宿主进程（避免干扰用户 TU 会话），先以 `gen_update_configs.py` 的 `CANONICAL_NAME` 映射把 yaml 项目名纠为 `WPSPDFPortable`；用户关闭 TU 后执行两步改名（`WpsPDFPortable` → `_wtmp` → `WPSPDFPortable`，绕过 Windows 大小写不敏感直改无效），随后移除映射并重新生成配置。Windows 文件系统大小写不敏感，过渡期路径访问不受影响。
- **预防措施**：用 Total Uninstall 等监控工具分析项目目录内的样本后，及时关闭再做大改；第三方重新打包的软件须在 THIRD_PARTY_NOTICES 明示「无官方哈希，以用户预置目录为准」。

## 五、启动器与图标

### 5.1 便携启动器全部显示默认图标

- **现象**：编译出的便携启动器在文件资源管理器、任务栏、Alt+Tab 中均显示**默认空白图标**，无法区分不同软件。
- **根因**：PAL 编译时未嵌入原程序图标资源。
- **解决方案**：用 `exeico` 从原程序 EXE 提取图标并嵌入启动器：

  ```bat
  exeico exe "原程序.exe路径" "输出.ico路径"
  ```

  原程序有多个图标变体（不同尺寸/状态）时，优先使用主图标。
- **预防措施**：`_analysis` 已沉淀 `extract_icons.py`、`make_icons.py`、`check_icons.py`、`gen_icon_map.py` 图标处理流水线；新包走流水线，不手工处理。

### 5.2 启动器不必要的重编译

- **现象**：每次软件更新都重新编译启动器，浪费时间且引入配置漂移风险。
- **根因**：误以为版本更新必须重编启动器。
- **解决方案**：**启动器 exe 通常不需要随版本重新编译**，除非主程序路径或启动参数发生变化。更新只改 `App\` 程序文件与 appinfo.ini 版本号。
- **预防措施**：更新流程中明确"launcher.ini 无变化则不重编"。

### 5.3 目录联接（Junction）导致的路径混乱

- **现象**：`_analysis\junction_fix.py` 的存在反映便携包曾因目录联接导致真实路径解析错误。
- **根因**：构建或整理过程中使用了目录联接，PAL 或验证脚本解析到联接目标而非便携包内路径。
- **解决方案**：构建产物的存放一律使用真实目录，不用联接；遇到历史遗留联接用 `junction_fix.py` 修正。
- **预防措施**：`Work\` 与 `Template Center\` 下禁止创建目录联接。

### 5.4 PAL Generator 沿用 nsi 残留 AppID，生成串包 exe（2026-10-15 实战）

- **现象**：对 WeMeetPortable 调用 `PortableApps.comLauncherGenerator.exe` 编译，包里却多出一个 `CodeArtsAgentPortable.exe`，且目标 exe 编译中途失败丢失。
- **根因**：Generator 直接读取 `Template Center\PortableApps.comLauncher\Other\Source\PortableApps.comLauncher.nsi` 中 `!ifndef PACKAGEID / !define PACKAGEID ...` 的**兜底值**——该值残留着上一个编译包（CodeArtsAgentPortable）的 AppID，Generator 不会改写它，于是按残留 AppID 产出串包 exe。
- **解决方案**：删除串包产物；编译一律使用项目自有 `_analysis\build_launcher.py`——它的 `_patch_nsi_defines` 每次都会把 PACKAGEID / NamePortable / PACKAGE 改写为当前包的值，不存在残留串包问题。
- **预防措施**：**禁用 PAL Generator，编译只走 build_launcher.py**；nsi 源码是被构建器直接改写的有状态文件，不要指望它"干净"。

### 5.5 exeico `exe` 模式取错图标，真图标被漏掉（2026-10-15 实战）

- **现象**：`exeico exe WeMeetApp.exe appicon.ico` 反复只得到 766 字节的单张 32x32 小图标，编译后启动器仍是默认图标观感；而 WeMeetApp.exe 实际内含 131845 字节的多尺寸真图标。
- **根因**：exeico 的 `exe` 模式取"主图标"的策略不可靠，对多图标资源的程序可能取到最小/错误的资源。用 `exeico bin <exe> <目录>` 提取全部图标资源后可见真相：`#101.ico`（128 KB 多尺寸，真图标）与 `#102.ico`（22 KB）。
- **解决方案**：`exeico bin` 提取全部图标 → 按文件大小选最大的多尺寸 ico → 覆盖 `App\AppInfo\appicon.ico` → 重新编译。验证时用 `exeico bin <新exe> <目录>` 确认内嵌资源（**不要信 `exe` 模式的回读结果**——它对已知正确的 exe 也会误报 766 字节）。
- **预防措施**：图标提取固定走 `bin` 模式；编译产物图标体积 = exe 体积应明显增大（本次 101 KB → 229 KB，差值≈ico 体积，可作为快速自检信号）。

### 5.6 编译时旧 exe 未结束，"Can't open output file"（2026-10-15 实战）

- **现象**：build_launcher.py 编译失败，makensis 报 `Can't open output file`，`[FAIL] 编译失败 rc=1`。
- **根因**：旧版 WeMeetPortable.exe（及 WeMeetApp 子进程）仍在运行，输出文件被占用锁定。
- **解决方案**：编译前结束同名启动器与主程序进程：

  ```powershell
  Get-Process | Where-Object { $_.Name -match "WeMeetPortable|WeMeetApp" } | Stop-Process -Force
  ```

  强杀后必须善后：检查并合并宿主残留数据回 Data、删除 `Data\PortableApps.comLauncherRuntimeData-*.ini`（否则下次启动弹框，见 4.2）。
- **预防措施**：编译前置步骤固定为"结束进程 → 清理残留 → 再编译"；把强杀当作崩溃场景对待，善后动作不可省。
  - ★ **按名结束进程有红线**：`Where-Object Name -match` 命中的是**映像名**，若该名与宿主正式安装版同名（Trae CN / WorkBuddy / Cursor 等），会连带杀掉宿主程序。改写为按**可执行路径**过滤（`$_.Path.StartsWith($root)`），见 2.7。

### 5.7 `ReadINIStr` 只认第一个同名段：`AppID` 必须写进首个 `[Details]`（2026-10-15 实战）

- **现象**：CodeArtsPortable / QuarkCloudDrivePortable / FoxitPDFPortable 三包双击启动器后**弹出空文本错误框**（只有"确定"按钮，标题栏一片空白），点确定后退出；主程序永不启动。
- **根因**：`appinfo.ini` 的 `[Details]` 段被写了**两次**（原模板段 + 追加段），而 `AppID` 只写在**后面的重复段**里。NSIS 的 `ReadINIStr` 走 `GetPrivateProfileStringW`，**只读第一个同名段，后续重复段被忽略** → `Core.nsh` 的 `.onInit` 两次 `ReadINIStr` 取不到 `AppID` 进入 `${Errors}` 分支，弹 `$(LauncherFileNotFound)`；而该 LangString 在 1033 语言表未设置 → 弹框正文为空。用最小 NSIS 脚本实证：`ReadINIStr` 对 `CodeArts Details/AppID` 返回 `(ERR)`，而对 `Details/Name` 正常。
- **解决方案**：把 `AppID`（及相关键）**插进第一个 `[Details]` 段的段首**，并删除末尾的重复 `[Details]` 块；`build_launcher.py` 的 `fix_appinfo()` 增加 `_section_body()` 只返回**第一个**同名段的正文区间后再插入，从工具层杜绝复发。三包重建后主程序 +5s 启动 OK。
- **预防措施**：
  - **往 ini 末尾追加同名段是无效修法**，正确做法是"合并进第一个同名段"。
  - 启动失败且**弹框正文为空**时，优先查 `appinfo.ini` 的 `[Details]/AppID` 是否存在且位于首个段。
  - 顺手修掉根因的另一半：该 PAL 模板 1033 语言表有 12 个 LangString 未设置，导致所有 PAL 报错弹框正文为空 —— 报错无从读起，排障成本成倍增加。

### 5.8 含中文路径的 launcher.ini 必须存成 UTF-16 + BOM（2026-10-15 实战）

- **现象**：MiaoshouPortable 启动即弹错退出，主程序不启动。
- **根因**：`MiaoshouPortable.ini` 里 `ProgramExecutable=妙手\妙手.exe` 含中文，而文件按 **UTF-8** 存盘。NSIS 用 `ReadINIStr`（ANSI API）读取时把 UTF-8 字节按本地 ANSI/GBK 解码，`妙手` 变成 `濡欐墜`（同名目录/文件自然找不到），`${FileExists}` 判定失败 → 弹 `$(LauncherFileNotFound)` → 退出。插桩实测打印 `PROBE-IAM-ProgramMissing 'App\濡欐墜\濡欐墜.exe'` 直接坐实。
- **解决方案**：把 `MiaoshouPortable.ini` 整文件转 **UTF-16LE + BOM**（`raw[:2] == b"\xff\xfe"`），重新编译后手工实测 `妙手.exe` ×5 + `MiaoshouPortable.exe` 全部正常起来。
- **预防措施**：
  - **ini/nsh 的编码按内容定**：`launcher.ini`（值含非 ASCII）必须 UTF-16 + BOM；`Custom.nsh` 则按各包编译实测为准 —— 本项目中 **Zoom 的 Custom.nsh 必须 UTF-8 无 BOM**，而 **WeMeet 的必须带 BOM**，两者相反，不可互套。
  - 分析脚本读 ini/nsh 一律做编码自适应（`read_text()`：无 BOM 先试 `utf-8-sig`，再退 `gbk`），否则脚本自己也解析不到 `ProgramExecutable`。
  - **2026-10-16 全量重编译补充**：`build_launcher.py` 用 configparser 读 appinfo.ini 时 `encoding="utf-8"` 对**带 UTF-8 BOM** 的文件（WeMeet）会因首字符 `\ufeff` 粘在 `[Details]` 前报 `MissingSectionHeaderError`。已改 `utf-8-sig`（剥 BOM、无 BOM 行为不变）并在写回时保留原 BOM 状态。Python 侧所有 ini 读取统一用 `utf-8-sig`。

### 5.9 PAL 图标五件套缺失 + 手工 DIB 解码丢 alpha 变黑角（2026-10-16 实战）

- **现象**：21 个便携包启动器图标"都有点问题"——普查发现 17 个包的 `appicon.ico` 是 766 字节单帧 32px 占位图标（exeico `exe` 模式遗留，见 5.5），且**全部 21 个包都缺 PAL 标准的 `appicon_16/32/75/128.png` 四件套**（标准见 `Template Center\PortableApps.comLauncher\App\AppInfo`）。
- **根因**：早年只做 `appicon.ico` 单文件，从未按 PAL 五件套标准出齐 PNG；后期补 PNG 时 PIL 的 `IcoImagePlugin` 对部分 ico 帧报 `Unsupported BMP header type (0)` / `Truncated File Read`，改手工解析后又把 32 位 DIB 帧包成 BMP 交给 PIL——BMP 路径忽略 alpha 通道，导致图标四角变成不透明黑块。
- **解决方案**：
  - `Work\_analysis\icon_survey.py` 普查 ico 帧数/最大边/PNG 缺失；
  - `Work\_analysis\fix_icons.py` 用 exeico **bin 模式**重提取全部包 ico（挑最大候选）；
  - `Work\_analysis\fix_icons2.py` 手工解析 ico 帧：PNG 压缩帧直接 `Image.open(BytesIO)`；32 位 DIB 帧**手工解码 BGRA 保留 alpha**（`Image.frombytes("RGBA",(w,h),px,"raw","BGRA")` + `FLIP_TOP_BOTTOM`，DIB 高度字段是 2 倍含 AND 掩码）；
  - 验证标准：128px PNG 左上角像素 alpha 必须为 0（`(0,0,0,0)`），`(0,0,0,255)` 即黑角缺陷。
- **预防措施**：新包制作流程把"图标五件套 + 四角透明度检查"列入验收清单；ico→PNG 一律走 fix_icons2 的手工帧解析路径，不再用 PIL 默认 IcoImagePlugin。

### 5.10 exeico 对部分程序产出头损坏的 ico，须用 pefile 手工重建（2026-10-16 实战）

- **现象**：TraeCNPortable 用 exeico `bin` 模式提取到的 `#1.ico`（182 KB）所有帧既非 PNG magic 也非合法 DIB 头（帧数据区开头是 `f1f1f1ff` 这类裸像素），PIL 与手工解析全部失败；GRPICONDIRENTRY 按 14 字节正确解析后发现各帧 `dwBytesInRes` 与 exeico 写入 ico 目录的 `sz` 完全对不上（如 128x128 帧真实 67624 字节被写成 2088）。
- **根因**：exeico 重建 ICONDIR 头时帧偏移/尺寸计算错误，帧数据本身完好但目录头已损坏。 exeico 并非对所有 exe 都可靠。
- **解决方案**：`Work\_analysis\fix_traecn_icon.py` 用 pefile 直接读 `RT_GROUP_ICON`(id=14) + `RT_ICON`(id=3) 资源，按 GRPICONDIR（14 字节/项：`wWidth wHeight wColorCount wReserved wPlanes wBitCount dwBytesInRes nId`）重建标准 ico——数据 blob 原样搬运，只重写 ICONDIR 头。重建后 6 帧（16/32/64/128/256×2）全部合法。
- **预防措施**：ico 提取后必须验证每帧 magic（PNG=`\x89PNG`，DIB=首 4 字节 `40,0,0,0`）再入库；验证脚本已并入 icon_survey.py 流程。GRPICONDIRENTRY 是 14 字节不是 13——步进写错会让 id 解析全部错位（本次连踩两次）。

### 5.11 Typora 安装包伪装 NSIS 实为 Inno Setup——静默安装卡死与识别证据（2026-10-16 实战）

- **现象**：`typora-setup-x64.exe` 7z 显示 Linker 2.25（NSIS 特征值），按 NSIS 套路 `7z x` 却只解出 `.text/.rsrc` 等 PE 节区；改用 NSIS 静默参数 `/S /D=` 安装直接**卡死无响应**。
- **根因**：Typora 安装器是 **Inno Setup 6.0.0**——它恰好也用 Linker 2.25 段头，7z 列表特征与 NSIS 撞车。决定性证据是卡住进程的临时目录 `%TEMP%\is-JOC42.tmp\typora-setup-x64.tmp`：**`is-` 前缀是 Inno Setup 的签名**（NSIS 的临时目录是 `ns*.tmp` 无前缀规律）。
- **解决方案**：杀掉卡住的 Inno 进程后走 innounp 2.71.2（`<本机工具目录>/tools\innounp`）静态解包，`{app}\` 411 文件完整取出；update_engine 的 inno 通道（为 Cursor 所建）直接复用。Typora 已登记 `package_type=inno`。
- **预防措施**：安装包类型识别不能只看 7z 的 Linker 版本号——NSIS/Inno 均可能显示 2.25；识别顺序应为 ① `7z x` 试解（出节区=PE 壳）→ ② 检查 `%TEMP%\is-*.tmp`（Inno 签名）与 `%TEMP%\ns*.tmp`（NSIS 签名）→ ③ 分别走 innounp / 7z。innounp 解包前必须先清场卡住的同名安装器进程。

### 5.12 主程序藏在版本号嵌套子目录时 exeico 提图标必失败（2026-10-16 实战）
- **现象**：WPSPDF 构建时 `[警告] exeico 未提取到图标 rc=1`，回退成默认图标；手工对真实路径跑 exeico 却能正常提取。
- **根因**：构建脚本按 `App\<app_sub>\<exe_main>` 拼图标提取目标，而 WPS 主程序实际在 `App\WPSPDF\12.8.0.23123\office6\wps.exe` 版本嵌套目录内，拼出来的路径根本不存在，exeico 对不存在的输入返回 rc=1。
- **解决方案**：包定义新增 `icon_exe` 覆盖字段（相对 `App\<app_sub>\` 的显式路径），`extract_icons()` 取 `cfg.get("icon_exe", cfg["exe_main"])`；本次用 `fix_wps_icon.py` 把已提取的 `IDI_ICON1.ico` 生成五件套补入 portableapps 与 dist 两侧。
- **预防措施**：凡主程序带版本号/多层嵌套目录的包（WPS、部分金山系），建包时先确认 `exe_main` 的直接父级是不是 `app_sub`，不是就必须配 `icon_exe`。

### 5.13 PAL [FilesMove] 的值必须是目录——带文件名会让用户设置凭空蒸发（2026-10-16 实战）

- **现象**：ReNamer 两轮浸泡复测首窗都是 "Terms of Use" EULA，且退出后 `ReNamer.ini` 在 Data 与 App 两侧都不存在——用户设置每轮清零。
- **根因**：`[FilesMove]` 配成了 `settings\ReNamer.ini=%PAL:AppDir%\ReNamer\ReNamer.ini`。PAL 源码 `Segments\FilesMove.nsh` 的 `_FilesMove_Start` 是 `$2=GetFileName(键)`、`$1=值\$2`——**值只该是目录**，文件名由键自动追加。值再带文件名就拼出 `…\ReNamer.ini\ReNamer.ini` 非法路径，PrePrimary 还会在 `App\ReNamer\` 下**创建一个名为 `ReNamer.ini` 的空目录**挡住应用写同名文件，PostPrimary 的 RemoveIfEmpty 又把它抹掉，表现为"文件人间蒸发"。
- **解决方案**：值改为纯目录 `%PAL:AppDir%\ReNamer`；同时取证发现 den4b 的真实设置文件是 **`Settings.ini`**（含 `FirstLaunch=0` EULA 接受标记）而非猜想的 `ReNamer.ini`，键名一并修正。修复后二轮启动直进主窗口，`Settings.ini` 在 Data 持久化。
- **预防措施**：① 写 `[FilesMove]` 必须**读 PAL 段源码确认值语义**（目录，不是全路径），同类错误在 FSCapture 的 `fsc.db` 上同步踩了一次；② 设置文件名禁止按品牌名臆测——首轮浸泡后若 Data 无预期文件，用「移动窗口法」（SetWindowPos 改窗口位置触发设置保存）取证真实文件名，FSCapture 的 `fsc.db` 即用此法实证；③ 源包自带的程序旁文件（如 FSCapture 的 `Portable.db`/`Draw.db`）**禁止纳入 FilesMove**——PAL 的 in-package 分支发现目标在包内已存在时会直接删除 Data 副本。

### 5.14 网盘分享页当版本源：HTML 里永远看不到文件列表（2026-10-16 实战）

- **现象**：用户给出 ReNamer 的蓝奏云链接与 WPSPDF 的城通网盘链接作为更新源；两页 `requests.get` 均返回 200，但 HTML 全文搜不到任何真实版本号（只能搜到无关的 `1.0`/`1.4` 之类）。
- **根因**：两类网盘都是**前端动态渲染**，文件清单不在首屏 HTML 里。① 蓝奏云文件夹分享页把接口 token（`fid`/`uid`/`puid`/`t`(ibf9xt)/`k`(_hdlzm)）写在页面内联 JS 中，文件列表要 POST `/filemoreajax.php?file=<fid>` 才返回（`msg.zt=='1'`，`msg.text[]` 每项含 `name_all`，每页 50 条）；② 城通是 Vite SPA，HTML 是空壳，且**目录元数据与文件列表是两个不同接口**——`/api/v2/resource?kind=dir&id=…` 只返回 `data.file`（folder_id/folder_name）与 `capabilities.authority`，**`data.rows` 不存在**；真正的清单在 `/api/v2/listing`。
- **解决方案**：引擎新增 `lanzou_folder` 与 `ctfile_dir` 两类版本源（`scripts/update_engine.py`），均从文件名抽版本号取最大。实证参数（2026-10-16）：蓝奏云 token 每次抓页面现取后 POST；城通 `GET /api/v2/listing?kind=dir&id=2655733-65162656-79a0f9&folder_id=0&fk=&passcode=2023&type_id=0&start=0&length=20` **无需带 authority** 即可返回 `data.rows[]`（name/size/date/href）。ReNamer→7.10、WPSPDF→12.8.0.23123，两包由 needs_manual 翻转 ok，在线源覆盖 6→8。
- **预防措施**：① **判断网盘页有无版本数据，禁止只看 HTML**——先抓 XHR，路径上的 4 个坑：城通缺 `passcode` 返回 423、`folder_id` 传真实目录 id 返回 403（须保持 `0`）、`kind=file` 返回 403；蓝奏云 token 是一次性的，**每次检测必须重新抓页面**，不能缓存；② 蓝奏云分享内的 `renamer_pro_*-Portable.7z` 是**纯 7z 归档**（非 SFX），故 `extract` 通道放行 `7z` 与 `7z_sfx` 同源处理；③ 版本正则要按文件名格式定制（`_7.10-`、`_12.8.0.23123_`），通用正则必须要求含小数点，否则会把日期 `20260817` 误当版本；④ 网盘页属**第三方分发**，config 的 `note` 必须写明「非官方源」，get 不到直链时 detect 只报版本号（引擎会 `pop("download_url")`）。

## 六、部署与运维

### 6.1 与原版并行导致 CLSID 冲突

- **现象**：绿色化输入法与原版同时存在，输入法行为异常或系统语言栏崩溃。
- **根因**：绿色版与原版使用**同一套 CLSID**（GUID 来自原版安装，跨机器通用），并行时注册表互相覆盖。
- **解决方案**：绿化前**必须先用官方卸载程序清理原版**，切勿并行。
- **预防措施**：README 部署注意事项第一条即强调；企业分发脚本中先检测原版是否存在。

### 6.2 多用户环境 HKCU 不生效

- **现象**：管理员在 A 账户绿化后，B 账户登录看不到输入法。
- **根因**：`SortOrder`、`DirectSwitchHotkeys`、`Assemblies` 等 HKCU 项**仅对当前用户生效**。
- **解决方案**：其他用户需各自运行一次绿化脚本（或登录后运行）；企业环境可配套登录脚本。
- **预防措施**：部署文档明确多用户限制。

### 6.3 批量清理前未 dry-run

- **现象**：直接执行批量删除/归档脚本，误删了仍需保留的便携包。
- **根因**：缺少"先演练后执行"的安全机制。
- **解决方案**：`cleanup-manifest.json` 采用 **dry-run 优先**——先以 `"dry": true` 生成完整清单（每个包的体积、归档日志数、动作），人工确认后再转正式执行。
- **预防措施**：任何批量清理/归档操作必须先 dry-run 输出清单，确认无误后再执行。

### 6.4 更新时覆盖 Data 目录导致用户数据丢失

- **现象**：用新版便携包整体覆盖旧版后，用户配置、插件、对话记录全部丢失。
- **根因**：把"更新"理解成了"整体替换"。
- **解决方案**：更新十条原则前两条——`Data\` **永不覆盖**；`App\AppInfo\` 自定义配置永不整体覆盖。更新只替换 `App\{软件名}` 程序文件。
- **预防措施**：更新前必须先把整个便携包备份到 `Backup\{软件名}\{旧版本号}`，保留最近三个版本。

### 6.5 依赖软件内置自动更新

- **现象**：便携版运行一段时间后自动更新，更新程序把文件写到宿主目录或把便携结构破坏。
- **根因**：未拦截软件内置的自动更新机制。
- **解决方案**：便携版**必须拦截或重定向自动更新**（Custom.nsh 处理，或把更新目录重定向到 `Data\`）；版本跟进走官方包手动更新流程。
- **预防措施**：更新后验证清单中必须重新检查自动更新、后台进程、开机自启三项。
