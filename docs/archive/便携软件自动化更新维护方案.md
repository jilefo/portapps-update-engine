# 第一部分：方案总纲（对应 V6.1 协议第 19 章）

## 1. 核心结论与定位

本方案整合《便携软件更新策略》全部有效结论，确立长期更新维护的最佳方式。核心结论一句话：

**不把"下载最新安装包 → 本机安装 → 拷出来"作为日常方案**（仅作最后兜底 L4）；维护重点从逐个手工更新 19 个项目，转变为维护一套通用 Python 更新引擎加 19 份轻量配置。日常主力是官方 ZIP 包整体替换，程序可重生、数据只保留、候选先行、门禁发布、指针回滚。

设计总基调：

- 全 Python 实现（requests、psutil、packaging、PyYAML，可选 bsdiff4），PowerShell 仅在被 Python 调度时作兜底适配。
- 证据驱动：每阶段产出结构化证据入 evidence 目录，失败开问题单，changelog 追加式记录。
- 稳定优先：stable 永远不被未验证版本覆盖，Data 目录在任何阶段都不可被触碰。
- 版本切换权归外部引擎，禁止软件内置更新器自作主张。

## 2. 总体架构：一个引擎 + 19 份配置

不为每个项目写独立完整脚本，而是写一个通用更新引擎，每个软件只维护一份 YAML 配置。维护重点从"逐个手工更新 19 个项目"变成"维护 1 套引擎 + 19 份轻量配置"。

引擎入口：`scripts\update_engine.py`，统一 CLI 子命令：

- `detect`：版本检测（可 `--all` 或 `--project 名称`）
- `download`：下载与哈希校验
- `extract`：按 L1 到 L3 优先级解包提取
- `diff`：新旧版本差异分析
- `test`：候选版本冒烟测试
- `stage`：候选版本归档
- `release`：门禁校验与版本切换（`--confirm` 显式确认）
- `rollback`：回滚至指定历史版本
- `report`：生成更新报告

配置文件：`Configs\<项目名>.yaml`（字段规范见第 15 节）。

## 3. 更新策略四级优先级

对每个项目按以下优先级选择更新方式，上一级失败才降级到下一级，降级原因必须记录：

| 级别 | 方式 | 适用条件 | 关键约束 |
|---|---|---|---|
| L1（首选） | 官方 ZIP / 便携包直接替换 | 官方提供 ZIP、portable 版或 Electron 应用官方发布压缩包；Cursor、Qoder、CodeArts 等 VS Code / Electron 系优先 | 下载 → SHA-256 校验 → 解压到新版本目录 → 保留 Data → 测试 → 切换 |
| L2 | 安装包静态解包 | 无 ZIP 但安装包为 NSIS / Inno Setup / MSI 等常见格式 | 用 7-Zip（NSIS）、innounp（Inno Setup）、lessmsi（MSI）解出文件，不真实安装、不写系统；保留原始安装包作为证据 |
| L3 | 沙盒/虚拟机隔离安装捕获 | L2 解包失败；程序依赖安装器释放的组件或在线下载器 | 在 Sandboxie / Windows Sandbox / VM 快照环境中静默安装，Procmon / Regshot 捕获写入基线，提取文件后销毁沙盒；生成新基线并与旧基线做 diff |
| L4（兜底） | 手动安装再拷出 | 无解包方案且沙盒不可用 | 每次都要重做便携化与基线监控，成本最高；必须登记降级原因 |

禁止的第五种方式：让软件内置更新器在正式便携目录中自行升级。该方式会写回 %LOCALAPPDATA%、破坏重定向、使引擎失去版本追踪、产生半更新状态，在任何情况下都不得采用。

## 4. 核心设计原则：三层分离与版本目录

每个接入更新引擎的项目采用"程序层、封装层、数据层"三分离：

- **App 层（可重生，消耗品）**：主程序文件与运行时资源，更新时整体替换。
- **Launcher 层（稳定）**：便携启动器、启动参数、环境变量注入、更新器禁用配置；更新时原则上不动，仅在差异分析显示需调整时修改。
- **Data 层（资产）**：配置、登录态、对话历史、插件扩展、缓存索引；更新引擎永不覆盖。

推荐版本目录结构（在项目现有结构兼容前提下逐步迁移，不要求立即搬家）：

- 项目根下的 `versions\vX.Y.Z\`：各历史版本完整程序目录
- 项目根下的 `versions\current.txt`：内容为当前版本号；启动器读取该文件决定启动哪个版本目录；回滚仅需改写此文件
- 项目根下的 `Data\`：永久用户数据，跨版本共享
- 项目根下的 `Staging\`：候选版本工作区，如 `Staging\<项目>\v新版本-candidate\`
- 项目根下的 `Backups\<版本>-<时间戳>\`：更新前 App 快照，保留最近 3 版
- 项目根下的 `version.json`：当前版本号、更新源、最后检查时间、更新通道

模型文件、大体量下载内容独立外置（如 `Data\Models` 或独立目录），不进入 App 更新包。

## 5. 七阶段流水线

引擎按阶段推进，每阶段独立可执行、可断点续跑、产出结构化证据：

**阶段一 detect（版本检测）**：按第 15 节配置的版本源优先级获取最新版本，与 version.json 比对（packaging.version 语义化比较），写入 `reports\data\update_versions.json`。无可靠来源的项目标记 needs_manual，不猜测版本。

**阶段二 download（下载与安全校验）**：优先官方来源，记录下载 URL、文件大小、SHA-256；官方提供可信哈希或数字签名则校验并记录结果；缺少可信基准时，明确记录"仅本地计算哈希，未验证官方真实性"，不得宣称已验证。原始安装包归档至 `Staging\<项目>\downloads\`。

**阶段三 extract（解包提取）**：按 extract_strategy 执行 L1 直接解压 / L2 静态解包 / L3 沙盒捕获；L3 捕获时同步产出新版安装写入基线（文件清单、注册表键、服务、计划任务），与旧基线 diff；失败降级时记录原因。输出候选程序目录树。

**阶段四 diff（差异分析）**：比较新旧版本文件清单、哈希、大小、目录结构、启动器参数、运行库、配置模板。重点自动标记四类高危变化：

1. 新增或变更的更新器组件（Update.exe、app-update.yml、Squirrel 文件、自动升级服务）。
2. 新增的服务、计划任务、启动项、遥测组件。
3. 存储路径变更（userData 位置、扩展目录、缓存目录迁移）。
4. 依赖大版本跨越（Electron 主版本、Node、内置运行时）。

命中第 1、3、4 类时 release_policy 自动升级为 manual_confirm；新增系统写入点自动生成白名单候选条目，待人工复核。

**阶段五 test（冒烟测试）**：在候选目录上执行最小用例集 S01（冷启动）、S02（二次启动）、S03（配置持久化）、S08（目录迁移）、S12（残留检查）；复用 run_scenario.py 与证据体系；检查进程正常、日志无阻断错误、数据正确写入 Data。内置更新器的禁用处置必须在测试中验证有效（无更新相关后台进程、无更新目录写入）。

**阶段六 stage（候选归档）**：测试通过后，候选版本移入 `versions\vX.Y.Z-candidate\`（或 Staging 候选区），生成更新报告（旧版本、新版本、差异摘要、测试结果、风险标记、回滚命令）。此时 stable 未被触碰。

**阶段七 release（门禁发布与切换）**：门禁条件为冒烟全 PASS、无未解释高危差异、Data 完整性校验通过（更新前后 Data 快照对比，差异为零或仅为预期内变更）、更新器禁用有效。通过后执行：psutil 确认主进程退出 → 备份当前 App 至 Backups → 原子更新 current.txt → 写回 version.json → 追加 changelog → 更新状态卡与看板。Qoder 系列追加执行监控基线重新对比；WinClaw / Lobster 追加图标校验与启动校验。任一门禁失败：保留旧版、禁止替换、建立问题单、标记阻塞。

## 6. 内置更新器禁用规范

每个接入项目必须在首次接入时执行 `scripts\disable_updater.py` 并留存处置记录。按优先级尝试，至少一种生效且经测试验证：

1. 启动参数禁用：启动器追加 `--disable-updates`、`--no-auto-update`、`update.mode=none` 等参数。
2. 配置文件禁用：argv.json 写入 `"disable-updates": true`，或应用自身配置中的更新开关。
3. 组件物理处置：重命名或移除 `App\resources\app-update.yml`、Update.exe、Squirrel 相关组件；改名而非删除，保留恢复路径，处置动作登记 changelog。
4. 环境变量禁用：如 `UPDATE_DISABLED=1` 等应用支持的变量。

约束：不得破坏软件正常启动与核心功能；每次版本更新后 diff 阶段重新检测更新组件变化，变化即告警并重新执行禁用处置；处置证据（执行前后的文件状态、进程检查、目录写入检查）归档。

## 7. 候选版本与门禁发布模式

发布策略采用"候选版本 + 门禁"，禁止发现新版本立即替换 stable：

- 默认 release_policy 为 manual_confirm：候选就绪后生成报告，人工确认后执行 `release --confirm`。
- 仅对连续两次更新冒烟全 PASS、差异分析无高危项、历史稳定的低风险项目，可经人工批准将 release_policy 降为 auto。
- 大版本跨越（主版本号变更）、更新器行为变更、存储路径变更、强登录/授权机制变更：无条件强制人工复核。
- 更新失败或门禁拒绝：自动回滚指针（若已切换）、保留候选与日志、建立问题单，stable 保持原状。
- 终端用户侧原则：交付给终端用户的便携包禁止用户在包内直接自动升级程序本体；升级必须通过下载新版完整/增量便携发布包完成。

## 8. 更新后回归测试

- 最小集（所有更新必跑）：S01 冷启动、S02 二次启动、S03 配置持久化、S08 目录迁移、S12 残留检查。
- 完整集（触发条件任一）：大版本跨越、差异分析命中高危变化、冒烟出现 FAIL 后修复、Qoder 系列、WinClaw / Lobster——执行 12 场景全量加关键场景 3 轮回归。
- Qoder 系列专项：每次更新后重新执行 parse_qoder_logs.py 与 compare_baseline.py，比对新版安装/运行行为与既有基线，新增写入点进入白名单流程。
- WinClaw / Lobster 专项：更新后重跑 verify_icon.py（四尺寸校验加图标缓存清理后复检）与启动校验（S01 / S02）。
- 登录态与授权验证：更新后验证 Data 中登录态是否仍生效；失效属正常情况的登记 KnownIssues，不得伪造登录成功；需账号验证的场景标记人工介入。

## 9. 回滚机制

- 回滚操作：修改 current.txt 指回旧版本号（写临时文件后 os.replace 原子替换），或执行 `update_rollback.py --to 版本号`；启动器随后加载旧版本目录。
- 升级前三件套（强制）：冻结 Data 快照（目录树加哈希清单至 `Backups\pre_<新版本>_Data\`）；备份当前 App 至 `Backups\<旧版本>-<时间戳>\`；生成 rollback.md 写明版本号、时间戳、回滚命令与验证方式。
- 版本保留策略：Backups 与 versions 保留最近 3 版，超过自动清理最旧（清理前确认非唯一副本）。
- 回滚触发条件：新版本启动失败（启动器轮询超时未检测到主进程）、冒烟或回归关键场景失败、用户反馈功能异常。
- 回滚后处理：Data 目录原位保留（Data 通常向上兼容）；若新版曾写入导致旧版不识别的 schema 变更，记录 KnownIssues，必要时从 pre_ 快照定向恢复受影响文件；回滚动作本身必须复测 S01 与 S03 并留证。

## 10. 可选增强：差分更新

定位为分发效率优化，非必需能力，默认关闭：

- 工具：bsdiff4（Python 库）生成与应用增量补丁；适用于自建分发或团队内网多机场景。
- 流程：以 Backups 中保留的旧版全量包为基线，对新版全量包生成 .patch 与 .meta.json（含旧包哈希、新包哈希、补丁哈希）；应用前先校验本地基线哈希与补丁自身哈希。
- 降级规则：大版本跨越（Electron 主版本升级、工具链变化）可能导致差分包大于全量，自动降级为全量下载；基线仅保留最近 3 到 5 版，更老版本直接全量。
- 约束：差分仅优化下载量，不改变第 5 节的七阶段门禁流程；未启用 delta_update 配置的项目忽略本节。

## 11. 维护节奏分级

- P0 高频高危类（Cursor、Qoder 系列、CodeArts 系列、CodeBuddy、Comate、JoyCode、WorkBuddy）：每周自动检测；候选版本自动准备至 stage；发布默认人工确认。
- 常规工具类（AiPyPro、Miaoshou、MiniMaxCode、OfficeAce、TodayCN、WeMeet、QuarkCloudDrive）：每月检测；仅重大版本迭代启动更新流程，小版本可按配置跳过。
- 不更新类（FoxitPDF）：按用户要求（2026-10-16）**不纳入更新流程**——不生成 Configs 配置（`gen_update_configs.py` 的 `EXCLUDED` 集合已含 `FoxitPDFPortable`），引擎任何子命令不会对其执行 detect/download/extract 等操作；该包的维护仅保留目录结构、数据持久化与垃圾清理等静态项。
- 紧急修复类（WinClaw、Lobster）：修复稳定并建立版本快照前不接入自动更新；稳定后按 P0 节奏纳入。
- 紧急安全更新：官方说明含重大安全修复时走加急流程——检测 → 下载 → 解包 → 冒烟（压缩至 S01 / S02 / S12）→ 人工确认 → 切换；全程留证。
- 定时调度：Windows 任务计划程序调用 Python 脚本（schtasks 创建每日/每周任务），或启动器冷启动时顺带触发 detect；避免常驻后台进程。

## 12. AI 工具更新维护特有风险与对策

1. 模型与运行时分离：模型文件（数 GB 级）独立于 App 更新包，放 `Data\Models` 或外置目录；引擎只管程序层。
2. 登录态与 API Key：登录态存于 Data 自动保留；API Key 等敏感信息放 `Data\secrets`，绝不写入 version.json、配置仓库或日志；大版本后 token 失效登记 KnownIssues，不绕过认证。
3. 扩展与插件：VS Code 系工具扩展默认装于用户主目录 .vscode / .cursor 下的 extensions，必须重定向至 `Data\extensions`（启动器参数或 Junction），否则升级后扩展丢失；Junction 方案登记白名单并说明清理策略。
4. 首启自动下载的运行时/模型/二进制依赖：重定向至 `Cache\` 并登记白名单或便携策略，不混入 App 版本目录。
5. 云端服务依赖变化：新版可能变更接口地址、认证方式、网络策略；冒烟测试至少确认可启动、可进入主界面、无网络异常导致的启动失败；深度功能验证受账号边界限制时如实标记。
6. 后台常驻进程类设计：部分工具启动时安装常驻后台进程并自动下载更新重启（对便携化致命）；diff 阶段专门检测新后台进程与自启动注册，发现即标记 S1 并拦截。
7. GitHub API 限流与代理：批量检测 19 个项目时配置 GITHUB_TOKEN 环境变量（未认证限速 60 次/小时，token 通过环境变量读取不落盘）；企业内网配置 requests 代理（HTTPS_PROXY 环境变量或配置项），代理未穿透是更新失败的常见根因。
8. 配置 schema 兼容：升级前扫描 Data 中可能被新版改变结构的文件（settings.json、argv.json、state 数据库、Web 存储）；发现迁移需求时在更新报告标记 migration_required，升级后触发迁移脚本并验证。
9. 版本回退可能导致 Data schema 不兼容：升级前快照 Data，回滚时视情况同步回滚 Data 或接受部分功能异常并记录。
10. 图标缓存：更新后执行 `ie4uinit.exe -show` 或重启 explorer 清缓存，避免资源管理器显示旧图标误导验收。

## 13. 与现有状态机的融合

更新引擎不另起体系，完全复用 V6.1 既有机制：

- 脚本规范：引擎模块遵循 V6.1 第 4 章全部工程规范（run ID、证据、--dry-run、原子写、熔断）。
- 状态持久化：版本状态并入 state.json 与状态卡字段（当前版本、最新版本、更新状态）。
- 证据体系：每阶段证据入 `evidence\<项目>\<run-id>\update-<阶段>\`。
- 问题单：更新失败建立 ISSUE 单，严重级别按 V6.1 第 10.1 节判定。
- 白名单：diff 阶段产出的新增写入候选进入 whitelist 流程。
- changelog：每次 release 或 rollback 自动追加条目；版本更新提交格式建议 `chore(update): 项目 vX.Y.Z → vA.B.C [UPDATE-xxx]`。
- 基线联动：Qoder 系列更新后重跑基线对比；其他项目更新后重跑 check_residuals.py。
- 看板联动：dashboard.html 展示更新状态列；数据源为 `reports\data\update_versions.json`。

## 14. 更新 KPI

从引擎结构化数据计算，不得手工填造：

- 版本检测覆盖率 = 有可靠版本源配置的项目数 / 19。
- 下载校验成功率 = 通过哈希/签名校验的下载次数 / 总下载次数。
- 解包成功率 = L1 / L2 解包成功次数 / 总解包尝试次数（L3 / L4 降级单列统计）。
- 冒烟通过率 = 冒烟全 PASS 的候选版本数 / 进入冒烟的候选版本数。
- 发布回滚比 = 执行回滚次数 / 正式发布次数（趋势指标，无目标值，异常升高需排查）。
- Data 完整率 = 更新前后 Data 差异为零或仅预期变更的更新次数 / 总更新次数，目标 100%。
- 更新器禁用有效率 = 禁用验证通过的更新次数 / 总更新次数，目标 100%。

## 15. 配置文件字段规范（Configs\<项目名>.yaml）

必备字段：

- project：项目逻辑名称；dir：实际目录
- category：高频高危 / 常规 / 紧急修复
- version_source：type 与 url（api / github_releases / latest_yml / page_regex / manual）；page_regex 时附正则与 last_verified_at
- download_url 或 url_pattern：官方下载来源或可靠 URL 解析规则
- package_type：zip / nsis / inno / msi / msix / electron_installer / unknown
- extract_strategy：direct_zip / static_unpack / sandbox_capture / manual_fallback
- entry_exe：启动程序相对路径
- launcher_args：启动参数、环境变量、工作目录
- data_dir：Data 目录相对路径（引擎保护清单）
- protected_paths：禁止覆盖的文件与目录清单
- extensions_dir：扩展/插件目录重定向规则（如适用）
- updater_disable：禁用方式（参数 / 配置 / 待处置组件清单）
- test_profile：冒烟测试项（默认 S01,S02,S03,S08,S12）
- full_regression_trigger：触发完整回归的条件列表
- rollback_policy：保留版本数量（默认 3）与回滚条件
- update_channel：stable / beta / 其他官方通道
- release_policy：auto / manual_confirm / blocked
- schedule：weekly / biweekly / monthly
- delta_update：布尔值（默认 false）
- proxy：可选代理配置
- last_checked_at：最后检测时间
- current_version：当前版本号

版本检测优先级（写入选用的级别与最后验证时间）：

1. 官方 Update API 或更新清单（最优）：VS Code 系 `/api/latest/win32-x64/stable` 类接口；electron-builder 发布的 latest.yml（含 version、path、sha512 三字段，可直接校验）。
2. GitHub Releases API：取 tag_name 与 assets 列表；资产名用正则匹配（如 win32-x64 与 zip 的组合正则）而非硬编码文件名。
3. 官方下载页解析：脆弱，页面一改即失效；仅作备用，必须记录页面地址、版本正则、下载链接规则、最后验证时间，失效时自动告警并降级为手动登记。
4. RSS / Atom 更新日志或 Release Notes：辅助来源。
5. 手动登记：无稳定公开接口的软件不强行爬取，配置中标记 source 为 manual，定期人工检查并回填版本号。

重要约束：检测到新版本不等于具备可靠更新能力；版本号未变但文件可能已变（以哈希为准）；正式版、预览版、灰度版可能混发，配置必须锁定 update_channel。

# 第二部分：当前采用方案一页摘要

当前方案是"Python 更新引擎 + 单项目配置 + App/Data 分离 + 候选版本门禁发布"的半自动流水线，日常更新不采用"下载安装包 → 安装 → 拷出"，那条路只作为最后兜底。

- **总体架构**：一个 `update_engine.py` + 19 份 `Configs\<项目名>.yaml`，维护 1 套引擎加 19 份轻量配置。
- **更新方式**：L1 官方 ZIP 直接替换（主力）→ L2 静态解包 → L3 沙盒捕获 → L4 手动重拷（兜底）；软件内置更新器一律禁用，版本切换权收归外部引擎。
- **三条核心原则**：三层分离（App 可换、Launcher 稳定、Data 永不动）；候选版本加门禁发布（默认 manual_confirm，高危变化强制人工）；差异分析卡四类高危项（更新器、服务任务遥测、路径变更、依赖大版本）。
- **七阶段流水线**：detect → download → extract → diff → test → stage → release，每阶段可断点续跑，release 前冻结 Data 快照、备份 App、原子替换 current.txt、自动追加 changelog；失败自动回滚、保留旧版、开问题单。
- **维护节奏**：高频高危类周检、常规类月检、WinClaw / Lobster 修复稳定前不接入；任务计划调 Python，无常驻进程。
- **体系衔接**：全 Python、证据入 evidence、看板增加版本与更新状态列、更新器禁用纳入每次必验项。

一句话概括：L1 官方 ZIP 整体替换为主力，App 可换、Data 不动、候选先行、门禁发布、指针回滚——安装重拷只是沙盒都不可用时的最后手段。

# 第三部分：智能升级路线图（L+1 至 L+6）

当前方案的天花板在确定性规则——引擎只能比对已知模式。真正的"更智能"是把决策权分梯度下放：低风险全自动、中风险 AI 辅助、高风险人机共决。以下按投入产出比排序，共 6 级，可逐级加装，不必一次性上齐。

## 3.1 总览表

| 级别 | 名称 | 核心能力 | 实现难度 | 适合何时上 |
|---|---|---|---|---|
| L+1 | 事件驱动检测 | Webhook / RSS 推送替代轮询 | 一星 | 引擎稳定后 |
| L+2 | AI 辅助差异分级 | LLM 读 changelog 与 diff 报告，自动判级 | 两星 | 优先上 |
| L+3 | 双版本并行（便携版蓝绿部署） | 旧版新版同盘共存，秒级切换与回退 | 一星 | 数据分离后天然支持 |
| L+4 | CAS 内容寻址去重 | 版本间只存变更文件，磁盘省 60% 到 80% | 三星 | 版本积压 5 版以上后 |
| L+5 | 自愈 Agent | 失败后 AI 读日志、提修复、自动重试 | 三星 | 有 10 次以上历史失败样本后 |
| L+6 | 预测性调度 | 学历史更新节奏，闲时预下载 | 两星 | 运行 3 个月后 |

## 3.2 L+1：事件驱动检测

现状是定时轮询（每日/每周任务计划）。升级为事件驱动：

- GitHub 托管项目：配置 Webhook 推送到本地轻量 HTTP 服务（Flask 单文件即可），Release 发布事件即时触发 detect，不再等定时器。
- 提供 RSS / Atom 的项目：用 Python feedparser 订阅 Release Notes，新条目即触发。
- 保留定时轮询作为兜底（Webhook 服务可能宕机）；事件触发与定时触发共用同一个 detect 入口，去重逻辑靠版本号比对。

收益：新版本发现延迟从最长 24 小时（每日检测）降到分钟级；且减少无效轮询请求（降低 GitHub API 限流压力）。

## 3.3 L+2：AI 辅助差异分级（最推荐先上）

现状的 diff 阶段靠规则匹配"新增更新器 / 服务 / 路径变更 / 依赖大版本"四类高危项，容易漏掉语义级风险（比如 changelog 写"migrate storage to new location"，代码层面只改了一个常量，规则抓不到）。加一层 LLM 分析：

实现要点（`scripts\update_ai_triage.py`）：

1. 输入三部分：diff 报告的结构化摘要（新增/删除/修改文件清单与哈希）、changelog 原文（截断至约 3000 字符）、项目配置上下文（当前架构、Data 目录约定）。
2. 构造提示词，要求 LLM 输出 JSON：risk_level（low / medium / high）、breaking_changes 列表、portability_risks 列表（新写入点 / 路径变更 / 更新器变化）、auto_release_allowed 布尔值、extra_tests_needed 建议补充的测试场景、reasoning 判断依据。
3. LLM 可选本地 Ollama（如 qwen2.5-coder）或云端 API；调用超时与失败时降级为纯规则判定，不阻塞流程。
4. 关键约束：AI 只给建议，规则仍是底线。AI 判 low 但规则命中"新增服务 / 计划任务"，仍强制 manual_confirm；AI 判 high 但规则未命中，标记提示人工重点查看。避免把一次偶然启动成功误判为可自动发布。
5. AI 判级结果与人工最终决策一起归档，形成"AI 建议 vs 人工结论"的对照记录，用于后续评估 AI 可信度，逐步放宽或收紧其权限。

同类落地案例：Apify 的 Changelog Triage Agent 专门盯多产品 changelog，自动打 BREAKING / WARNING / INFO 标签并推送告警，思路可完全借鉴到这 19 个项目。

## 3.4 L+3：双版本并行观察（便携软件的蓝绿部署）

由于已是 `versions\vX.Y.Z\ + current.txt 指针` 结构，天然支持蓝绿——不用回滚，直接切换：

实现要点（`promote_with_observation` 流程）：

1. 候选版本通过冒烟后，不直接标记 stable，而是把 current.txt 切到 candidate（用户立刻可用新版），原子替换指针。
2. 旧版本目录不删，保留一个观察期（默认 24 小时），在版本状态里标记 observation_until 时间戳。
3. 观察期内后台静默检查三件事：启动成功率（启动器上报）、%APPDATA% 是否出现新写入（复用 check_residuals.py）、崩溃日志新增（事件日志过滤）。
4. 观察期满无异常 → 标记 stable，changelog 记录转正；有异常 → 一键回滚 current.txt 到旧版，并触发 L+5 的 AI 失败分析（若已部署）。

这是 canary deployment 思想在单机便携场景的等效实现——一个人既是生产者也是金丝雀，但旧版本就地保留意味着"发现异常 → 秒回滚"的代价趋近于零。

进阶玩法（可选）：A/B 并行运行——用 Sandboxie 同时拉起旧版和新版，各跑一轮冒烟，把两边的行为差异（启动耗时、内存、写盘量）出报告。适合大版本跨越时用。

## 3.5 L+4：CAS 内容寻址去重（磁盘大头）

19 个项目 × 保留 3 版 = 最多 57 份完整程序目录。Electron 应用版本间 90% 文件是相同的（Electron 运行时、locale、pak 资源），全量存储浪费严重。

做法：引入 content-addressable storage（内容寻址存储）思路，把每个版本目录改成"对象库 + 清单"：

- `Versions\objects\`：所有去重后的文件，按 SHA-256 前两位分桶存储（如 `ab\cd\abcd1234...`）。Electron 主 DLL 等多版本共享同一份物理文件。
- `Versions\manifests\<项目>\vX.Y.Z.json`：文件清单，内容为"相对路径 → 对象哈希"的映射。
- 工作区组装：启动时按清单用硬链接（os.link，同卷零拷贝）把对象拼装到目标目录，或直接让启动器指向清单组装的工作区。

两个核心函数的算法描述（Python 实现约 30 行）：

- build_manifest（入库）：遍历版本目录所有文件 → 逐个计算 SHA-256 → 若对象库中不存在该哈希则建立硬链接入库（obj.parent.mkdir 后 os.link）→ 生成 path 到 hash 的清单字典 → 写入 manifests 目录。
- restore_from_manifest（还原）：读取清单 JSON → 对每个条目在目标目录创建父目录 → os.link 从对象库硬链接到目标路径 → 完成。硬链接拼装秒级完成，不占额外磁盘。

收益测算：磁盘占用从约 19 × 3 × 平均 500MB ≈ 28GB 降到约 19 × 500MB + 增量差异 ≈ 11GB，节省 60% 以上。额外福利：CAS 的内容寻址天然就是完整性证明（哈希即校验），配合 current.txt 切换，回滚也只是重建硬链接，秒级完成。

注意事项：硬链接要求同一 NTFS 卷；跨卷迁移时改用复制；对象库清理需引用计数（检查所有 manifest 是否还引用该哈希后再删）。

## 3.6 L+5：自愈 Agent（失败自动修复）

现状流程是：更新失败 → 建问题单 → 等人。加一层 Agent 实现失败自愈：

流程（对应业界 AI Agent Incident Response 模式：分诊、根因、修复、升级各自独立，每步有明确边界）：

1. 触发：冒烟或观察期失败。
2. 收集上下文：stderr 与退出码、事件日志片段、diff 报告、Data 目录 diff、Procmon 片段（如有）。
3. AI 诊断：把上下文交给 LLM（本地 Ollama 或 API），要求输出假设列表（按可能性排序）与建议修复动作。
4. 白名单修复动作（自动可执行的封闭集合）：补建 data 目录、修改 argv.json 重定向参数、重命名新增的 updater 组件、修正 launcher 参数转义。仅限改便携包内部文件，不能动系统、不能动 Data、不能绕过授权。
5. 重跑冒烟：最多 2 次重试（加首次共 3 次尝试，与协议熔断规则对齐）。
6. 成功 → 自动发布（若该配置允许）并把根因与修复沉淀到 `docs\04-避坑手册.md`；失败 → 完整上下文打包上报人工（已触发熔断，不再盲试）。

约束：自愈动作全部留证据（改动前后 diff 与哈希）；同一根因的修复模式成功 3 次后可固化为规则，从 AI 路径移到确定性代码路径。

## 3.7 L+6：预测性调度

运行 3 个月后，update_versions.json 里已有每个项目的历史更新节奏。可做三件事：

- 预测下次更新时间：按项目更新频率直方图（Cursor 每周二更、Qoder 每周一更、Foxit 月更），提前 2 小时预下载，避开使用高峰。
- 闲时批处理：凌晨 3 点一次性把 19 个项目的候选版本全部准备好（download + extract + diff + test 跑完），早上只需要扫一眼报告决定哪些发布。
- 异常检测：某项目突然从"周更"变成"日更"，自动提高检测频率并提示可能有大版本或紧急安全修复。

## 3.8 落地分期建议

第一阶段（本周可做，性价比最高）：

1. L+3 双版本并行观察：改 current.txt 切换逻辑加观察期标记，约 10 行代码。
2. L+2 AI 差异分级：接一个本地 Ollama 或便宜 API，在 diff 阶段插入一次 LLM 调用加规则兜底。

第二阶段（1 到 2 周后）：

3. L+4 CAS 去重：用 manifest 加硬链接方案替换 versions 全量存储。
4. L+1 Webhook 事件驱动：GitHub 项目配 webhook 到本地 Flask 单文件服务。

第三阶段（1 个月后，有历史数据再上）：

5. L+5 自愈 Agent：需要积累至少 10 次以上真实失败样本才能形成有效判断。
6. L+6 预测调度：需要 3 个月节奏数据。

## 3.9 暂不建议引入项

- 完全无人值守 auto 发布：风险不对称（省 5 分钟对比破坏 Data 的风险），坚持人工确认门禁。
- 多机分布式同步：目前单机 19 项目，用不上分布式。
- 自训 ML 模型判风险：LLM 提示词已够用，训练数据不足，标注定错成本高。

## 3.10 总结

当前方案是"引擎 + 规则"；加上 L+2（AI 辅助分级）和 L+3（双版本并行观察）后升级为"引擎 + 规则 + AI 建议 + 并行观察"，这已接近单机便携软件维护的天花板——再往上堆智能边际收益就低了，不如把精力放在把 19 个项目的基线真正测扎实。落地顺序：先建 19 份配置与版本检测，用 CursorPortable 做第一个全流程试点（detect → download → extract → diff → test → stage → release → rollback 全链路演练），稳定后逐级加装智能增强。
