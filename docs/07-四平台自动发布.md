# 07 · 四平台自动发布

> 对应任务书步骤 6。目标：**在 GitHub / Gitee / GitCode / CNB.COOL 四个平台都能
> 一键自动发布，且不需要逐平台手工操作。**

---

## 1. 先弄明白一件事：CI 到底发布什么

本仓库是「配方开源（MIT）+ 二进制不随仓库分发」模式：

| | 是否入库 | 体积 |
|---|---|---|
| `portableapps/` 元数据、`_shared/` 工具链、文档 | 是 | 10.5 MB（1,710 文件） |
| `<产品根>/` 可运行产物（39 个便携程序本体，默认 `D:\Portapps`） | **否**（仓库外 + `.gitignore` 双保险） | 59.12 GB |

CI 在**全新克隆**上跑，拿不到产品根里的第三方二进制，也没有构建它们的环境。
所以自动发布的是**配方包**，不是便携程序本体：

```
PortableApps-formula-v1.5.0.zip   git archive 打包的全部入库文件
RELEASE-NOTES.md                  CHANGELOG.md 里对应该版本的条目
SHA256SUMS                        逐文件 SHA-256
release_manifest.json             版本、时间戳、四道门禁的结论（机器可读）
```

便携程序本体的分发走 `06-开源与发布.md` 的三个选项
（GitHub/Gitee Releases 手工上传、网盘 + `update.py` 拉取、Gitee Releases）。
若将来要让 CI 自动分发二进制，需先把产物放到 CI 可拉取的位置
（CNB Generic 制品库 / 外网 URL / 自建 NAS），再在流水线里加一步下载——
本文件末尾 §7 给了改法。

## 2. 统一入口：`_shared/tools/release.py`

四个平台不各写一套逻辑，全部收敛到这一个脚本，两个子命令：

```bash
# 1) 门禁 + 版本一致性 + 打包（只读，本地可反复跑）
python _shared/tools/release.py prepare --out build/release

# 2) 创建 Release 并上传附件
python _shared/tools/release.py upload --dir build/release \
    --platform github|gitee|gitcode --repo owner/name --tag v1.5.0
```

`prepare` 做的事（任一步失败即 `die()`，**不发半成品**）：

| 步骤 | 内容 |
|---|---|
| 门禁 × 4 | `audit_repo.py`、`check_custom_nsh.py`、`test_structure.py <Pkg> --ini-only` × 39、`audit_before_push.py` |
| 版本一致性 | CHANGELOG 顶部版本 ↔ 每包 `version.json` ↔ 每包 `appinfo.ini` 三者比对 |
| 打包 | `git archive`（只收入库文件，天然排除二进制与 Data/） |
| 校验 | SHA-256、`release_manifest.json`（含门禁结论，事后可追溯） |

### 两条防假绿设计（都是踩过的坑）

1. **`test_structure.py` 是单包脚本**，必须逐包传包名。
   在仓库根裸跑会由 `_pkg.py` 回退出 `PKG=<仓库目录名>`，报一串"缺 appinfo.ini"的假错。
   已在 `_pkg.py` 加了存在性校验，推导不出真实包时退出并列出 39 个可用包名。
2. **版本一致性必须自报覆盖度**。第一版实现只 `glob("*/dist/*/version.json")`，
   扫到 1 个就报「0 不一致」——而 `version.json` 由更新引擎运行期写入，
   实际只有 1/39 个包存在。现在按包全集逐包找，缺的明确计数：
   `覆盖度: 1/39 个包有 version.json`。
   （2026-10-19 迁移后 `version.json` 随产品树位于 `<产品根>/<Pkg>/`，
   由 `_paths.product_dir()` 解析；全新克隆里 0/39 也如实报 0。）

### 2.1 包级发布：39 个包各发各的（与整仓级是两回事）

除整仓配方包外，每个包还能单独发一个**本包的配方包**。两者分工不同：

| | 整仓级（§2） | 包级（本节） |
|---|---|---|
| 配置 | 仓库根四个平台的 release 配置 | `<Pkg>/.github/workflows/release.yml` × 39 |
| 触发 tag | `v1.7.0` | `CursorPortable@v1.7.0` |
| 产物 | `PortableApps-formula-v1.7.0.zip`（全部入库文件） | `CursorPortable-formula-3.25.6.0.zip`（本包配方） |
| 平台 | 四平台 | GitHub（包级只此一处，够用） |

**为什么包级发的是配方、不是便携程序**：第三方程序躺在
`portableapps/App/<程序>/` 里，被 `.gitignore` 排除。实测
`CursorPortable` 源树 `App/` 下只入库 9 个元数据文件，而产品树 `App/`
有 995 MB 第三方程序。CI 在新克隆上 `build-portable.py` 出来的，是
「有启动器、无程序」的空壳——发布它没有意义。所以包级发布的内容是：

```
<Pkg>/portableapps/**           便携化配置（NSIS + PAL 元数据）
<Pkg>/LICENSE                   MIT
<Pkg>/THIRD_PARTY_NOTICES.md    第三方权利声明（开源必带）
<Pkg>/README.md                 包说明
```

**为什么 tag 要带包名前缀**：39 份 release.yml 原先全用 `tags: ['v*']`，
推一个 `v1.7.0` 会同时触发 39 条流水线去抢建同一个 Release。
改成 `<Pkg>@v*` 后各发各的，且 `CursorPortable@v1.7.0` 不匹配整仓级的
`v[0-9]+.[0-9]+.[0-9]+`，互不干扰。

```bash
git tag -a CursorPortable@v3.25.6 -m "CursorPortable v3.25.6"
git push origin CursorPortable@v3.25.6      # 只发这一个包
```

三个配套脚本（都由 `_shared/tools/gen_release_workflows.py` 生成的
workflow 调用，改模板请改生成器）：

| 脚本 | 作用 |
|---|---|
| `_shared/scripts/package_formula.py` | 打配方 zip + SHA256；**只打 git 跟踪的文件**，并报告打包文件数与总字节 |
| `_shared/tools/print_artifact_paths.py` | 解析产物真实路径，按 GITHUB_OUTPUT 格式输出；产物缺失 **exit 1** |
| `_shared/tools/gen_release_workflows.py` | 78 份包级 workflow 的唯一生成源；`--check` 逐个比对并解析 YAML |

```bash
# 本地预演一个包的发布链路（与 CI 上完全相同的三步）
python _shared/scripts/test_structure.py CursorPortable --ini-only
python _shared/scripts/package_formula.py CursorPortable
python _shared/tools/print_artifact_paths.py CursorPortable

# 校验 39 包 × 2 份 workflow 是否与模板一致（CI 上必跑）
python _shared/tools/gen_release_workflows.py --check
```

## 3. 触发规则（四平台一致）

| 平台 | 配置文件 | 触发 |
|---|---|---|
| GitHub | `.github/workflows/release.yml` | push tag 匹配 `v[0-9]+.[0-9]+.[0-9]+`（含 `-rc1` 后缀）、`workflow_dispatch` 手动 |
| Gitee Go | `.workflow/release.yml` | push tag 前缀 `v` |
| GitCode | `.gitcode/workflows/release.yml` | push tag 匹配 `v[0-9]+.[0-9]+.[0-9]+` |
| CNB.COOL | `.cnb.yml` | `$: tag_push` |
| 包级（仅 GitHub） | `<Pkg>/.github/workflows/release.yml` × 39 | push tag 匹配 `<Pkg>@v*`（包名前缀，避免 39 条抢同一个 Release） |

**只认 Tag，不在每次提交时发布**——这正是任务书的要求（"避免每次提交都触发发布"）。
要发新版就：

```bash
# 1. 更新 CHANGELOG.md，加一段 ## [X.Y.Z] — YYYY-MM-DD
# 2. 本地预演（不出网、不创建 Release）
python _shared/tools/release.py prepare --out /tmp/rel
# 3. 打 tag 并推送（推到哪个平台，就触发哪个平台的流水线）
git tag -a v1.6.0 -m "release v1.6.0"
git push origin v1.6.0        # GitHub
git push gitee v1.6.0         # Gitee
git push gitcode v1.6.0       # GitCode
git push cnb v1.6.0           # CNB.COOL
```

四个平台可分别推同一个 tag，互不影响；也可以只推其中几个。
只发某一个包时用 `git push origin CursorPortable@v3.25.6`（见 §2.1）——
它不会命中上面四条整仓级流水线。

## 4. 各平台配置要点与差异

### 4.1 GitHub Actions

- `permissions: contents: write` 才能建 Release；令牌用内置 `secrets.GITHUB_TOKEN`，
  **无需自建 Secret**。
- `actions/checkout` 必须 `fetch-depth: 0`，否则 `git archive` 拿不到完整对象。
- 上传前置了 `upload-artifact`：即使发布失败，产物仍可下载排查。

### 4.2 Gitee Go

- 配置文件在 **`.workflow/`** 目录，且要在网页端「流水线」里**启用**才会激活
  （仓库里放了 yml 不等于流水线已启用）。
- 需要自建令牌，在「流水线 → 参数配置 → 凭证」注入为环境变量 `RELEASE_TOKEN`，
  令牌需 `user:open_api` 或仓库写权限。
- ★ **唯一需要你按实例确认的一处**：Gitee Go 的「执行 shell」插件 id 随实例版本
  变化，社区常见 `build@shell`。保存报未知插件时，进「流水线 → 新建任务 →
  执行 shell 脚本 → 切 YAML 视图」抄下真实 step id 替换即可，其余不用动。
- 备选（不耗令牌）：改用官方 `release@gitee` 插件，但附件名必须写死
  （含版本号）。配置样例见 `.workflow/release.yml` 末尾注释。

### 4.3 GitCode Pipeline

- 目录是 **`.gitcode/workflows/`**，不是 `.github/workflows/`——目录错了流水线
  根本不识别。
- 语法是 GitHub Actions 兼容集，但 action 是平台自有的一套：
  `checkout-action@0.0.1`、`setup-python@0.0.1`。
- runner：`ubuntu-latest` / `euleros-2.10.1`。
- **有发行版**，且 API 走**预签名 URL 上传**（不是 multipart）：
  先 `GET /api/v5/repos/{owner}/{repo}/releases/{tag}/upload_url` 拿地址，
  再 `PUT`。`release.py` 的 gitcode 分支已按这个流程实现。

### 4.4 CNB.COOL

- 配置文件在仓库根 **`.cnb.yml`**。
- 发版用**内置任务** `type: git:release`（不是镜像），`tag_push` 事件下
  自动取触发的 Tag，无需传 `tag`；描述用 `descriptionFromFile` 指向
  `build/release/RELEASE-NOTES.md`。
- ★ **`git:release` 不上传附件**，附件必须再用 `cnbcool/attachments` 插件单独传。
  这是四平台里唯一要分两步的平台，已在 `.cnb.yml` 里体现。
- `overlying: true` 设为叠加模式，避免重复发布时先删后建误伤历史 Release。

## 5. Secrets / 凭据清单

**任何令牌都不写进仓库**，全部走平台 Secrets 或流水线凭证：

| 平台 | 变量名 | 值 | 注入位置 |
|---|---|---|---|
| GitHub | `GITHUB_TOKEN` | 内置，自动 | `secrets.GITHUB_TOKEN` |
| Gitee | `RELEASE_TOKEN` | Gitee 访问令牌 | 流水线 → 参数配置 → 凭证 |
| GitCode | `RELEASE_TOKEN` | GitCode 访问令牌 | 仓库 → Settings → Secrets |
| CNB | 无需 | `git:release` 用流水线身份 | — |

`release.py` 按 `RELEASE_TOKEN` → `GITHUB_TOKEN` → `GITEE_TOKEN` → `GITCODE_TOKEN`
的顺序取第一个非空值；一个都找不到且未加 `--dry-run` 时直接退出，**不会静默跳过上传**。

令牌最小权限：对目标仓库的**写权限**即可，不要给 user 全域令牌（GitCode/Gitee 尤其）。

## 6. 首发验证步骤

按顺序做一遍，确认四平台都能自动发：

```bash
# ① 本地干跑（不出网，验证门禁与打包）
python _shared/tools/release.py prepare --out /tmp/rel
#    期望：四道门禁全 exit 0；输出 TAG=v<版本>、四个产物及其 SHA-256

# ② 校验产物自洽
cd /tmp/rel && sha256sum -c SHA256SUMS
python -c "import json;d=json.load(open('release_manifest.json'));\
print(d['tag'], d['repo_version'], [g['ok'] for g in d['gates']])"

# ③ 打 tag，先只推 GitHub
git tag -a v1.6.0 -m "release v1.6.0" && git push origin v1.6.0

# ④ 到 GitHub → Actions → release，确认：
#    - 四个 job 全绿
#    - Release 页面出现 v1.6.0，4 个附件齐全、体积与 SHA256SUMS 对得上
#    - 下载 zip 能解开，解开后是仓库源码（无产品树二进制、无 Data/）

# ⑤ 同样方式推 gitee / gitcode / cnb 三个 tag，各自确认：
#    - Gitee：仓库 → 发行版 页面
#    - GitCode：仓库 → 发行版 页面（附件是预签名上传，注意大文件超时）
#    - CNB：云原生构建 → 流水线记录；Release 在仓库页面，附件单独一步上传

# ⑥ 回滚演练：删掉刚建的 Release / tag，确认重推同一 tag 能再发一次
#    （Gitee 用 allowUpdate:true，CNB 用 overlying:true，GitHub 会因
#     Release 已存在而失败——先在网页删掉旧 Release 再重推）
```

**判定标准**：四个平台各自出现一个新的 Release，含 4 个附件，
`release_manifest.json` 里四道门禁 `ok` 全为 `true`。

## 7. 已知限制与扩展点

| # | 限制 | 说明 / 改法 |
|---|---|---|
| 1 | CI 不发布 59 GB 便携二进制 | 设计使然。要自动分发：把产物放到 CNB Generic 制品库或外网 URL，在 `.cnb.yml` 加下载步，再交给 `cnbcool/attachments` 上传 |
| 2 | `version.json` 仅 1/39 个包存在 | 更新引擎运行期才写。门禁已如实报覆盖度（`1/39`），不阻塞发布；补齐可作为独立小任务 |
| 3 | Gitee Go shell 插件 id 待确认 | 见 §4.2，30 秒可改 |
| 4 | GitHub 重复推同一 tag 会失败 | GitHub 不允许重复创建同名 Release。重发前先在网页删掉旧 Release |
| 5 | CNB `git:release` 无附件能力 | 已用 `cnbcool/attachments` 插件补上，属平台限制而非配置疏漏 |
| 6 | 包级 release 只在 GitHub | 设计使然。包级是 GitHub 侧的便利能力（各包可单独发版），四平台发布一律走整仓级 |
| 7 | 包级 tag 必须带包名前缀 | `CursorPortable@v1.0.0`。用裸 `v1.0.0` 会让 39 条流水线同时抢建同一个 Release |
| 8 | 包级产物在 CI 上不含第三方程序 | 配方包里本就没有程序（§2.1）。要在 Release 里附带可运行包，需在自建 runner 上跑 `portableapps.yml` |
