## 1. 启动器（`Launcher\*.ini` / PAL）类

### 1.1 主入口 ini 缺失 —— PAL 按 `$BaseName` 拼路径

**现象**：`WPSOfficePortable.exe` 双击弹 `is missing [Launch]:ProgramExecutable`，
而同包的 WriterPortable / SpreadsheetsPortable 都正常。

**根因**：PAL 运行期用 **启动器 exe 的文件名**（`$BaseName`）拼配置文件：
`$EXEDIR\App\AppInfo\Launcher\$BaseName.ini`。一个包有 5 个 exe 就要有 5 个同名 ini。
当时只生成了 4 个分体的，唯独主 exe 的漏了。

**做法**：建包后**必须**断言「每个 exe 都有同名 ini」，别只测其中一个。

```python
for exe in glob("dist/*.exe"):
    assert isfile(f"App/AppInfo/Launcher/{basename(exe)[:-4]}.ini")
```

### 1.2 宿主 junction 残留导致「便携启动中止」

**现象**：QQ / TIM / QQNT 第一次能开，之后再也打不开，弹「便携启动中止」。

**根因**：这类包用 junction 把宿主目录（Tencent、Tencent Files 等）接进包内。
上一轮清理**只拆了 8/13 条**，剩下的被判定为"他人占用" → 拒绝启动。

**做法**：清理范围要覆盖**全部宿主根**，且每轮测试前做冷启动（杀进程 + 拆全部 junction）。
探针的正确语义应是：

| 退出码 | 含义 | 动作 |
|---|---|---|
| 0 | 自己的 junction | 接管 |
| 1 | 他人包进程**确实在运行** | 弹互斥中止（符合设计） |
| 2 | 无 LinkTarget（异常） | 报错 |
| 3 | 悬垂残留 **或** 所有者进程已死 | 删除并重建 |

### 1.3 ★ PowerShell 解析错误退出码 = 1，与探针语义撞车

**现象**：修好死代码后，QQ/TIM/QQNT **全部**打不开，一律弹互斥中止。

**根因**：给探针补「所有者进程探活」时连踩两坑——

1. **死代码**：注释写"插到 `exit 1}` 之前"，代码却是
   `src.replace(ANCHOR, ANCHOR + NEW_LINES)`，插到了**之后**。
   `exit 1}` 已经把分支关掉了，新加的 9 行永远不执行。
2. **游离右花括号**：挪对位置后，块尾变成 `...exit 3}` + 残留一行 `exit 1}`，
   后者不闭合任何块 → **PowerShell ParserError**。
   而 `powershell -File` 遇语法错误的退出码**恰好是 1**，
   与"他人包真在运行"的语义退出码 1 完全撞车 → 所有外来 junction 一律被当成"有人占用"。

**做法**：
- 修改生成脚本时，**打印 diff 并实读生成后的行号区间**，不要相信注释。
- 语义退出码**避开 1**（PowerShell 用它表示解析/运行失败），改用 0/2/3。
- 任何"块尾追加"类补丁，改完立刻做语法解析校验，且**必须带正样本**（见 §6.1）。

### 1.4 ★★ 含中文路径的 launcher ini：UTF-8 会直接挂（本轮实证矩阵）

**现象**：MiaoshouPortable 原本 3 轮全 PASS；把它的 launcher ini 从 UTF-16LE
"规范化"成 UTF-8 之后，**R2、R3 连续 FAIL**（无子进程、Data 零写入）。

**根因**：该 ini 的 `ProgramExecutable=妙手\妙手.exe` **含中文**。
NSIS 读取无 BOM / 带 BOM 的 UTF-8 时按 ANSI 解码 → 路径乱码 → 找不到程序。

**实证矩阵**（`scripts/test_ini_encoding_matrix.py`）：

| launcher ini 编码 | 结果 |
|---|---|
| **UTF-16LE（原始）** | ✅ PASS（还原后连续 2 次 PASS） |
| UTF-8 **带** BOM | ❌ FAIL（子进程 0、Data 新写 0） |
| UTF-8 **无** BOM | ❌ FAIL（3 轮排查 R2/R3 实测） |

**做法**：
- **不要动 launcher ini 的编码**。想统一编码前先看路径里有没有非 ASCII。
- `appinfo.ini` 用 UTF-8 **没问题**（36 个含中文描述的包已实证），
  它不参与启动路径解析——两者区别别搞混。
- Python 侧解析 launcher ini 要按 BOM sniff 编码，否则 configparser 直接抛
  `MissingSectionHeaderError`，还会让审计工具误报"未重定向"。

### 1.4b ★ `Custom.nsh` 的编码要求与 ini **正好相反**：UTF-8 且必须无 BOM

**现象**：`BaiduNetdiskPortable` / `CodeArtsAgentPortable` 的 `Custom.nsh`
带 UTF-8 BOM（2026-10-18 结构自检双树共抓到 4 个文件）。

**根因**：NSIS 会把 BOM 的 `EF BB BF` 当成一个 token 解析，报
`Invalid command`。这里和 §1.4 **方向恰好相反**：

| 文件 | 正确编码 | 错误后果 |
|---|---|---|
| `Custom.nsh` | UTF-8、**无 BOM** | 带 BOM → NSIS `Invalid command` |
| `Launcher\*.ini`（含中文路径） | **UTF-16LE** | 转 UTF-8 → 路径乱码、起不来 |
| `appinfo.ini` | UTF-8（有无 BOM 均可） | 不参与启动路径解析，无影响 |

**做法**：用 `_shared/tools/fix_strip_bom.py` 剥离并备份；
CI 由 `audit_repo.py` 的 D 项强制。**别把两条规则记反**——
"ini 要 UTF-16" 和 "nsh 要 UTF-8 无 BOM" 是两套独立约束。

> 讽刺但真实的一点：本轮 BOM 是被**新写的**结构自检抓到的，
> 而此前的 `check_custom_nsh.py` 只查引号/管道病态、没查 BOM，漏了很久。
> 说明**每新增一个维度都可能翻出旧账**，自检项要持续加。

### 1.5 严禁重定向 `USERPROFILE`

**现象**：Electron 系应用启动即崩。

**根因**：Electron 的 `app.getPath('appData')` 经 `SHGetKnownFolderPath` 展开
`%USERPROFILE%`，若得到不存在的路径会直接崩溃。

**现状**：本库仍有 11 个包写了 `USERPROFILE=%PAL:DataDir%\settings\user`，
因为它们**同时**保证该目录在启动前已存在，故实测可正常运行；
但这属于"能用但危险"的配置，新包不要照抄。
详见 [`archive/踩坑记录.md`](archive/踩坑记录.md) §3.4。

### 1.6 ★★ 「上次未正常关闭」残留会让 PAL **拒绝启动程序**（本轮实证）

**现象**：双击便携包，弹一个英文框

    XXX Portable did not close properly last time it was run and will now clean up.
    Please then start XXX Portable again manually.

点「确定」后**什么都没发生**——程序根本没启动。用户视角就是「一直打不开 / 启动异常」，
而且不知道还要再点一次。

**根因**（PAL 源码实证，`_shared\toolchain\PortableApps.comLauncher\Other\Source\`）：

```nsis
; PortableApps.comLauncher.nsi
Section
    Call Init          ; Function Init 第 1 段就是 ${RunSegment} Custom
    ...
    ${IfNot} ${FileExists} $DataDirectory\PortableApps.comLauncherRuntimeData-$BaseName.ini
        ... Call Execute                     ; ← 正常启动的唯一路径
    ${Else}
        MessageBox MB_ICONSTOP $(LauncherCrashCleanup)   ; ← L421，只弹框
    ${EndIf}
    ${CallPS} Post -                          ; 直接收尾，程序压根没起来
```

那个 ini 只在 PAL **正常收尾**时删除（`Segments\Core.nsh` L113）。任何
强杀进程 / 断电 / 崩溃 / 上一次收尾卡死，都会把它留在 `Data\` 下；
下次启动必然命中 Else 分支。**ini 里没有任何配置项能关掉这个行为。**

**为什么容易被误判**：冒烟脚本 `smoke_real.py` 的 `pre_clean_rt()` 会在启动前
主动删掉这个 ini，所以**冒烟永远 PASS**，问题只在真实用户手里复现。
（本次就是靠"不做任何预清理"的 3 轮冷启动 + 抓对话框文本才抓到的。）

**做法**：新增 `Custom.nsh_Init` 自愈钩子——它是 PAL `Function Init` 的第 1 段，
**早于**上面的 `FileExists` 判断：

1. `FindFirst` 探测有无残留 ini；没有就零开销跳过（正常路径不增加启动时间）；
2. 有则生成 ps1 探测「除自身外包内是否还有进程」；
3. 确认**无存活实例**才 `Delete`。有实例则完全不动，保留 PAL 原有行为——
   绝不绕过"已在运行"保护，也不破坏 junction 互斥。

两个硬约束：

- **Init 阶段 `$DataDirectory` 尚未赋值**（`Variables` 段才设），路径一律用 `$EXEDIR\Data`；
- **改完必须重编 exe**。`Custom.nsh` 是编译进启动器的，改文件不重编等于没改（§2.1 §2.2）。

一键修复：`python _shared/tools/fix_launcher_rtdata.py --apply`，再重编启动器。

### 1.7 ★★ Electron / VSCode 系有**两条**落盘路径，环境变量只管得住一条

**现象**：`[Environment]` 里老老实实写了 `APPDATA=` / `LOCALAPPDATA=` 重定向，
冒烟也全绿，但用户的 `C:\Users\<名字>\.trae-cn`、`.cherrystudio`、`.codearts`
却一路涨到几百 MB —— 数据根本没进便携包。

**根因**（本机实测，2026-10-18）：

| 落盘位置 | 应用取路径的方式 | 改 `%APPDATA%` 环境变量有用吗 |
|---|---|---|
| `%APPDATA%\<Vendor>` | `SHGetKnownFolderPath(FOLDERID_RoamingAppData)` | **没用**，它不读环境变量 |
| `%USERPROFILE%\.<name>` | Node `os.homedir()` / Electron `app.getPath('home')` | 只读 `USERPROFILE`，也不能乱改（见 §1.5） |

所以「重定向了个寂寞」：只有真正读环境变量的程序（Win32 传统程序）才吃这套，
Electron/Chromium/VSCode 系一律绕过去。

**怎么判断你的包有没有这问题**（别靠猜）：
```bash
python _shared/tools/scan_host_leak.py --min-mb 1      # 宿主真实目录（非 junction）清单
python _shared/tools/probe_leak_perf.py --set risky    # 实测：跑一遍看宿主哪些目录被写
```
判据只有一条：**包退出后，宿主上仍以「真实目录」存在**（junction 已被拆掉，
真实目录不会自己消失）。`~/.xxx` 是最常见的漏网之鱼，因为大家只盯着 `%APPDATA%`。

**修法**：junction 接管，别想着靠环境变量。
`_shared/tools/fix_dot_home_dirs.py` 就是干这个的（沿用 §1.2 的合并语义：
宿主真实目录先 `robocopy` 进 Data 再移除，**不丢数据**；已是 junction 则不抢不拆）。

**刻意不做**：`~/.workbuddy`、`~/.codebuddy` 之类**宿主正在用**的点目录，
一旦接管会直接打断宿主上跑着的同名软件 —— 这类只能手工决定。

### 1.8 ★★ 卡顿：一次 PowerShell 调用 = 1.37 秒

**本机实测**（冷启动，6 次平均）：

| 启动一个子进程 | 单次耗时 |
|---|---|
| `powershell -NoProfile -ExecutionPolicy Bypass -File x.ps1` | **1.37 s** |
| `cmd /c echo x` | **0.082 s** |

差 **16 倍**。而 QQPortable 一次冷启动要派生 **24 次**子进程调用（其中约 12 次
PowerShell），光等 PowerShell 就 ~16 s —— 用户体感就是「点了半天没反应」。

**为什么会有这么多次**：junction 三路判定（§1.2）原先写成「只要宿主路径是
reparse point，就无条件叫一次 PowerShell」。宿主上有 N 个 junction 就是 N 次。

**修法（已落地）**：`_shared/tools/opt_fast_junction_probe.py`
把判定改成 **NSIS 原生快速路径**，不启任何子进程：

1. 在 TARGET 里写探针文件 → HOST 下能看见 → **0**（本包所有，崩溃残留）
2. 否则试探 HOST 是否可写 → 写不进去 → **3**（联接目标已失效）
3. 只有「联接存活但不属本包」这一种**少见**情况才回退 PowerShell 精判 1/3

快速路径**不读包名**，所以对任何含 `NP_JunctionProbe` 的包都无损适用。
QQ 系由此从 12 次 PowerShell 降到 0~1 次。

**记住这条**：`Custom.nsh` 里每写一个 `nsExec::ExecToStack 'powershell ...'`，
就给用户加 1.37 秒。能用 NSIS 内置指令（`FileOpen` / `CreateDirectory` /
`${FileExists}`）判定的，绝不要开 PowerShell。

## 2. 双树与构建产物类

### 2.1 改了配置却不生效：你改的是哪棵树？

每个包有两棵树，用途不同：

| 树 | 作用 | 是否有应用二进制 |
|---|---|---|
| `portableapps/` | **构建输入**（源树）：appinfo、Launcher ini、Custom.nsh、DefaultData | ❌ 只有元数据 |
| `dist/<Pkg>/` | **可运行产物**：真正的 `App\<程序>\`、编译好的 exe | ✅ |

**坑**：
- 改了 `portableapps/` 的 ini 而没重编 → `dist/` 里的 exe 还是旧的。
- 反过来，直接改 `dist/` 里的 ini → 下次构建被覆盖，改动丢失。

**做法**：改 `portableapps/` → 重编 → 同步；临时热修才动 `dist/`，且事后回写源树。

### 2.2 旧编译产物让"已修好的钩子"看起来仍然失效

改完 `Custom.nsh` 必须重编。**编译零 warning 不等于生效**——
`Debug.nsh` 缺失是预期内的，别被它掩盖真正的报错。
详见 [`archive/踩坑记录.md`](archive/踩坑记录.md) §4.10。

### 2.3 dist 的 `appinfo.ini` 缺段（本轮修复 23 个包）

**现象**：`dist`（真正分发的那棵树）的 `appinfo.ini` 只有
`[Details] [Version] [Installation]`，缺 `[Format]` 和 `[Control]`。

**后果**：PortableApps 平台读不到 `Start` / `ExtractIcon` / `Icons`，
菜单里信息不全。

**做法**：构建流水线末尾加断言——dist 树的 appinfo 必须含
`[Format] [Details] [Version] [Control]`。修复脚本：
`_shared/tools/fix_appinfo_production.py`（文本级合并补段，不覆盖 dist 专有内容）。

### 2.4 ★★ 制作期残留进了包目录（含第三方二进制，开源即事故）

**现象**：`LobsterAIPortable` / `QoderCNIDEPortable` / `WinClawPortable` 下
有 `_制作素材/`，`KukuAIPortable` 下有 `evidence/`，合计 **53.5MB**。

**里面是什么**（制作便携版时的取证快照，做完就没用了）：

| 内容 | 问题 |
|---|---|
| `Uninstall*.exe` / `unins000.exe` | **第三方卸载程序二进制** → 违反"不分发第三方二进制" |
| 安装/卸载监控 `.reg` | 含宿主机器注册表快照 |
| `XX 日志 - 文件和文件夹.txt` | 单个 12~18MB，含**本机绝对路径** |
| `_icons/#1.ico` | 图标提取缓存，图标早就进 `AppInfo` 了 |

**为什么只有 3 个包有**：命名不统一的历史遗留——有的包叫 `_制作素材`、
有的叫 `evidence`、有的（大多数）做完就清了。**这正是危险所在**：
没有统一规范，就靠人记得清。

**做法**：
- 已全部移出仓库归档（`GreenSoftMake/Backups/制作素材归档/<包名>/`），
  取证材料没丢，仓库干净。
- `.gitignore` 加了硬规则：`_制作素材/ 制作素材/ evidence/ _icons/
  leftover*.txt unins*.exe unins*.dat Uninstall*.exe *.reg *日志*.txt`
- **新包做完立刻清**，别等开源前才扫。

**同类但更狠的一例**：`CursorPortable/dist/CursorPortable/Backups/`
是更新引擎留下的**旧版本 3.24.18 完整程序备份**——
**993MB / 15157 个文件**。它在 `App\` 之外，`.gitignore` 的
`*/dist/*/App/*/` 规则**管不到**，差点进 git。
判断依据：`version.json` 显示 `current_version=3.25.6`、
`previous_version=3.24.18`，而 3 轮冒烟是在 3.25.6 上跑的 → 旧备份无回滚价值。

> 教训：**`.gitignore` 的排除规则要覆盖 `dist/<Pkg>/` 下的所有非标准项**，
> 不能只盯 `App\`。标准结构只有 `App/ Data/ Other/ <Pkg>.exe help.html`，
> 其余都要问一句"它该不该在这"。

### 2.5 ★ 脚手架给每个包复制一份脚本（39×7 ≈ 270 份实质是 7 份）

**现象**：每个包下都有 `scripts/`（6 个脚本）和 `tests/`（1 个测试）。

**实测重复度**：

| 文件 | 份数 | 重复情况 |
|---|---|---|
| `toolchain.py` | 39 | hash **全同** |
| `package-paf.py` / `.ps1` | 36 | hash **全同** |
| `build-portable.ps1` | 39 | hash **全同** |
| `build-portable.py` / `gen-sbom.py` / `test_structure.py` | 各 39 | 差异**只有两行**：docstring 包名 + `PKG = "<包名>"` |

**为什么是坑**：改一个模板要改 39 处，改漏一处就埋雷；
而且让人误以为"每个包有自己的构建逻辑"，实际上没有。

**做法**：收敛为 1 份参数化通用版放 `_shared/scripts/`，
包名由「命令行参数 > 当前目录名 > `PAF_PKG` 环境变量」推导。
包目录下**只放包自己的东西**。

> 顺带修掉两个被这条掩盖的误报：
> `version.json`（更新元数据，有用）曾让 CursorPortable 报 FAIL；
> WPS 的 4 个分体 `*.Portable.exe`（多入口设计，正常）曾让整个包报 FAIL。
> 现在都进了 `test_structure.py` 白名单，全库 39/39 通过。

## 4. WPS 2023「首页壳」专章

**现象**：Writer / wpsPDF / 主入口启动后窗口标题全是「WPS文字」。

**根因**：WPS 2023 统一架构下，**所有组件启动都先落"首页壳"**：

- 类名规律 `Kx<Wps|Et|Wpp|Pdf>PromeMainWindow`；
- 首页壳含 4 个专属控件：`新建` / `最近` / `打开` / `暂无打开记录`，UI 文本仅 4~5 个；
- 组件开关（`/wps` `/et` `/wpp`）**确实生效**（类名不同），但界面都是首页；
- 截图像素对比：`wpsoffice.exe` 无参与 `/wps /w` 首屏 **sha256 完全相同**。

**解法**：穷举 14 组开关，唯 `/nostartpage` 能跳过首页壳（3 次复现 100%）——
首页控件只剩「新建」，UI 文本 5→18~20，标题变「WPS 文字 / WPS 表格 / WPS 演示」（**带空格**，可据此区分）。

| 启动器 | 命令 |
|---|---|
| 主入口（保留首页，语义正确） | `wpsoffice.exe` |
| 文字 | `wpsoffice.exe /wps /w /nostartpage` |
| 表格 | `et.exe /nostartpage` |
| 演示 | `wpp.exe /nostartpage` |
| PDF | `wpspdf.exe`（独立组件，无首页概念） |

## 5. Windows / Python 探测脚本类

### 5.1 `GetFileAttributesW` 失败返回 **-1**，不只 0xFFFFFFFF

```python
a = GetFileAttributesW(p)
if a != 0xFFFFFFFF:      # ❌ 恒为真，把不存在的目录判成 reparse point
if a in (-1, 0xFFFFFFFF):  # ✅
```

### 5.2 本机 `Documents` 被重定向到 D 盘

`%USERPROFILE%\Documents` 和未定义的 `%DOCUMENTS%` 都是**错的**。
必须读注册表：

```python
winreg.OpenKey(HKEY_CURRENT_USER,
    r"Software\Microsoft\Windows\CurrentVersion\Explorer\Shell Folders")
QueryValueEx(k, "Personal")
```

否则 `Tencent Files` 之类的残留永远扫不到，QQ 系问题反复复发。

### 5.3 `os.readlink` 对悬垂 reparse point 会抛 WinError 2/3

扫描脚本必须 `try/except`，否则整个清理流程崩在半路。

### 5.4 ctypes 64 位：不设 `restype`/`argtypes` 会静默截断句柄

`GetDC` / `CreateCompatibleDC` / `CreateCompatibleBitmap` / `SelectObject`
都要显式声明，否则 64 位句柄被截成 32 位，`SelectObject` 返回垃圾。

### 5.5 进程名精确匹配

`Get-Process -Name X` 是**精确名**（非子串）；psutil 按 `'tim'` 子串过滤
会误抓 `RuntimeBroker.exe`，得出"QQ 还在运行"的错误结论。

### 5.6 PowerShell 5.1 的 `Get-Item.LinkTarget` 为空

要用 `$li.Target | Select-Object -First 1` 兜底。

### 5.7 UI Automation 中文输出别走管道

走 stdout 会被 GBK(936) 打乱成乱码。让 PowerShell
`[System.IO.File]::WriteAllLines($path, $arr, UTF8Encoding)` 写文件，Python 再读。

### 5.8 DirectUI 应用没有子 HWND

WPS 用 DirectUI，`EnumChildWindows` 递归结果为空，靠"子窗口指纹"区分界面状态
会得到**三个界面完全相同的哈希**（等于什么都没测）。此时改用 UI Automation 控件树。

### 5.9 硬件渲染窗口截图黑屏

`PrintWindow` / 从窗口 DC `BitBlt` 对硬件加速窗口得到全黑。
改用**屏幕 DC** 抓图，并先 `SetWindowPos` 把窗口搬到已知坐标（如 60,60）避免多显示器偏移。

## 6. 验证方法类（最容易产出假结论）

### 6.1 ★ 空文件也能通过语法校验

**事故**：用 `Select-String` 重建待校验的 ps1，结果匹配不到任何内容 → **生成了空文件**；
空文件 `Parser::ParseFile` 当然 OK、运行退出码也是 0 → 得出"探针语义验证通过"的**假结论**。

**做法**：任何"生成 → 校验"链路，必须带**正样本**（故意写错一处，断言校验应当失败）。

### 6.2 ★ PNG 逐字节比对是最强的等价证据

两态截图若 **sha256 相同**，说明界面**逐字节一致**，可直接推翻
"某开关生效了"的假设。本轮正是靠这一条证伪了 `/wps /w`。

### 6.3 判定"启动成功"要用双维度

只看进程不够（进程起来但界面卡死），只看窗口也不够（后台应用无窗口）。
本库判定 = **包内子进程出现** ＋ **Data 目录有新写入**，两者同时满足才算 PASS。

### 6.4 回归要按"轮"跑

单次通过不能说明稳定：QQ 系会互相看到对方的 junction 残留，
必须**每轮前冷启动**（杀进程 + 拆 junction）。本库标准是 3 轮。

1. **先做监控分析**（ProcMon / Total Uninstall）拿到真实写入点，**再写 launcher.ini**

## 8. 更新策略类（2026-10-18 新增，全部为本次实证）

每个便携包目录里各有一个自包含的 `dist/<Pkg>/update.py`，
由 `_shared/tools/gen_update_strategies.py` 生成。下面是建这套东西时
真实踩到的 6 个坑，每一条都会导致"更新看起来成功了，其实坏了"。

### 8.1 版本号必须规范化后再比

**现象**：`CursorPortable` 永远提示"有新版本"。

**根因**：`appinfo.ini` 的 `PackageVersion` 是 PAL 要求的 **4 段**
（`2.1.0.0`），而上游 tag 是 `v2.1.0`、Zen 这种还带后缀 `1.23.3b`。
直接字符串比较 → 要么永远有更新，要么永远检测不到。

**做法**：统一 `norm_version()` 成 4 段整数元组再比——去 `v` 前缀、
去尾部 `b`、截断 `-`/`+` 后的预发布信息、非数字段降级为 0、补 0 到 4 段。

### 8.2 ★ 网页抓版本号的假信号（最容易自欺）

**现象**：探针一片绿，11 个源"全部可用"。

**根因**：打印命中片段的上下文一比对，全是假的——

| 包 | 抓到的"版本" | 真实来源 |
|---|---|---|
| TIM | `2.1.1` | 页面 sea.js 模块加载器的版本 |
| BaiduNetdisk | `2.1.1` | badjs-sdk 的版本 |
| QuarkCloudDrive | `0.1.78` | 静态 CSS 资源版本号 |
| TraeCN | `2.0.0.401` | 内联 JSON 里另一个组件的版本 |
| FoxitPDF | `476.233.31.949` | **SVG path 的坐标值** |

**做法**：
1. 第一遍正则命中的**必须**打第二遍——打印命中位置前后 200 字符，
   肉眼确认它紧贴"产品版本"语境；
2. 确认不了就**降级 `manual`**，把原因写进策略的 `note` 里，
   宁可人工，也不给假信号。本轮 11 个候选里只有 SublimeText 是真的。

### 8.3 ★ 解包之后必须"再便携化"，否则更新即破坏

**现象**（SublimeText 实测）：上游 `sublime_text_build_4215_x64.zip`
解压后自带两样东西，直接拷进去就出事——

1. **`Data/` 目录**：Sublime Text 用它做便携配置目录。PAL 这边是靠
   `[Environment]` 把数据重定向到 `dist/<Pkg>/Data/` 的，用上游的 Data
   会让用户数据落进 `App\` 里，脱离备份与迁移。
2. **`update_installer.exe`**：自带的自动更新器。一旦运行，会把便携版
   原地改写成安装版，便携性当场报废。现有版本里它是被改名成
   `update_installer.exe.disabled-by-engine` 的。

**做法**：`post_unpack()` 里做三件事——
- **剥掉单层外壳目录**（zip 常解出 `SoloMD_5.0.3/...`，多一层就找不到入口）；
- **`drop_paths`** 剔除上游自带的 `Data/` 等 PAL 自己管理的目录；
- **`disable_exe`** 把自带更新器改名加 `.disabled-by-engine` 后缀。

`disable_exe` 不是手填的，是从磁盘上现存的 `*.disabled-by-engine`
**反推**出来的（生成器自动扫描）。仓库里 4 个包有这种痕迹：

| 包 | 需要禁用的自带更新器 |
|---|---|
| FeishuPortable | `update.exe` |
| SublimeTextPortable | `update_installer.exe` |
| ZenBrowserPortable | `updater.exe` `default-browser-agent.exe` `pingsender.exe` `maintenanceservice.exe` `maintenanceservice_installer.exe` |
| ZoomPortable | `Installer.exe` `zUpdater.exe` |

**顺带**：备份只保留最近 3 份。一次 SublimeText 备份 172MB，
不清理的话重装几次就吃掉几个 G。

### 8.4 `--rollback` 在新进程里，`self._last_backup` 永远是 None

**现象**：单独执行 `python update.py --rollback`，永远回一句
"没有可回滚的备份"。

**根因**：`_last_backup` 是**上一次进程的内存状态**。回滚必然是新起
一次进程，这个值一定是 None——回滚功能等于不存在。

**做法**：`rollback()` 去 `BACKUP_ROOT` 里找**名字最大的那个备份目录**，
而不是依赖进程内变量。同时备份时把 `appinfo.ini` 一并存进
`备份目录/_appinfo/`，回滚时版本号跟着一起退——否则会出现
"文件是旧的、版本号是新的"这种对不上的状态。
拷回程序目录时要 `ignore=shutil.ignore_patterns("_appinfo")`。

### 8.5 路径上溯别数错层

**现象**：备份被写进了 `SublimeTextPortable/_shared/update/_backups/`，
凭空多出一个包内目录。

**根因**：`update.py` 在 `dist/<Pkg>/` 下，上溯关系是——

```
HERE            = <Repo>/<Pkg>/dist/<Pkg>     ← 脚本所在（便携包目录）
HERE.parent     = <Repo>/<Pkg>/dist           ← 注意：不是包根！
HERE.parents[1] = <Repo>/<Pkg>                ← 包根
HERE.parents[2] = <Repo>                      ← 仓库根（_shared/ 在这）
```

**做法**：用 `parents[N]` 显式写下标，别用连续 `.parent.parent`
（数着数着就错一层）。生成后务必实跑一次，看备份落在哪。

### 8.6 更新脚本一定要自包含

**现象**：最初把策略放在 `_shared/update/<Pkg>.py`，`import _base` 复用引擎。

**根因**：用户拿到的是 `dist/<Pkg>/` 目录，通常整个拷走，此时
`_shared/` 根本不在旁边，`import` 直接失败。

**做法**：引擎代码**内联**进每个 `update.py`（模板在
`_shared/tools/update_template.py`）。代价是 39 份重复，收益是
"拷走就能用"，这个取舍值得。批量执行器 `runner.py` 只负责**并发
`subprocess` 调用**各包的 `update.py --json`，自己不实现任何更新逻辑，
保证单跑和批跑行为完全一致。

### 8.7 模板里的占位符别用 `%` 格式化去拼

**现象**：生成出的文件里 `%%CONFIG%%` 原样留在代码里，`compileall` 报
`SyntaxError`。

**根因**：`'class S(%s):\n    pkg = "%%PKG%%"' % cls` —— `%` 运算符会把
`%%` 转义成 `%`，于是模板里的 `%%PKG%%` 永远匹配不上。

**做法**：字符串拼接用 `+` 或 f-string，别让含 `%%` 的文本过 `%` 运算符。
另外 docstring 里不要写与真实代码同形的片段（`class S(Strategy)`
这种），否则"替换第一个匹配"会先命中注释里的那份。

### 8.8 ★ `shutil.which("7z")` 找到的可能是个坏 7-Zip

**现象**：ZenBrowser 更新"没反应"——不报错、不落地，退出码还是 0。

**根因**：PATH 里靠前的 `<本机工具目录>/tools/7z.EXE` **旁边没有 `7z.dll`**
（只有 `7za.dll`）。于是：

```
7z                      → 正常打印帮助，rc=0      ← 看起来是好的
7z x zen.installer.exe  → Load Error: 7z.dll
                          Can't open as archive
                          rc=2
```

而它排在 `C:/Program Files\7-Zip\7z.exe` 前面，`shutil.which` 先返回它。

**做法**：
1. **别用"无参数跑一次"做健康检查**——坏掉的那个照样 rc=0，这个检查是骗人的；
2. 正确做法是**拿真实文件逐个试**，`_unpack_7z()` 里遍历候选，
   第一个 `returncode == 0` 的才算数，并把失败原因打出来；
3. 失败时**必须打印 7z 的 stdout/stderr 尾巴**，否则用户只看到"没反应"。

### 8.9 安装器解出来是多层，正主在子目录里

**现象**：ZenBrowser 的 `zen.installer.exe` 解出 `core/` + `setup.exe` 两个顶层项。

**根因**：`post_unpack()` 的"剥单层外壳"只在**只有 1 个顶层项**时才生效。
这里有 2 个，于是把 `core\` 和 `setup.exe` 一起拷进了 `App\Zen\`，
结果程序目录多套一层，入口 exe 找不到。

**做法**：加 `strip_root` 字段（Zen 配 `core`）+ `--strip` 命令行覆盖。
`post_unpack()` 先按 `strip_root` 进入子目录，再做后续处理。

### 8.10 冒烟脚本猜进程名会猜错

`smoke_real.py` 对未登记的包按 `<包名去掉 Portable>.exe` 推测，实测踩到两次：

| 包 | 猜的 | 实际的 |
|---|---|---|
| SublimeTextPortable | `sublimetext.exe` | **`sublime_text.exe`** |
| ZenBrowserPortable | `zenbrowser.exe` | **`zen.exe`** |

表现是"Data 有新写入、0 弹框"但判 FAIL——**应用其实完全正常**。
包名与进程名不同形的包必须显式登记进 `TARGETS`。

### 8.11 GitHub API 未认证限流（60 次/小时）

**现象**：4 个 GitHub 源一起报 `GitHub HTTP 403`，本地开发期高频调用时必现。

**根因**：未认证的 GitHub API 限额是 **60 次/小时**（按出口 IP 计）。
本库 4 个包走 GitHub，连着跑十几轮就打满了。

**做法**：
1. 脚本读环境变量 `GITHUB_TOKEN` / `GH_TOKEN`，带上后限额到 **5000 次/小时**，
   CI 里务必配；
2. 403 时给出**明确的提示文案**（"限流，设置 GITHUB_TOKEN 可到 5000 次/小时"），
   而不是干巴巴一个 `HTTP 403`；
3. **取新失败要退回上次成功的结果**（`_last_check.json`），状态标 `CACHED`。
   网络抖动和限流是**临时故障**，直接报 ERR 会让人误以为策略写错了。

**顺带**：批量执行器的超时要按模式区分（检测 90s / 更新 900s）。
统一 180s 时，一个卡住的请求能把整个批次拖到 3 分钟。
