# 06 · 开源与发布

> 本篇回答两个问题：**怎么开源到 GitHub 和 Gitee**、**软件文件那么大，平台空间够不够**。  
> 结论先说：**够，而且富余两个数量级**。本仓库 git 实际只跟踪 **1707 个文件 / 10.49 MB**，  
> 最大单个文件 375 KB（WPS 的 appicon.ico），没有任何文件超过 20 MB。  
> 原因是仓库采用「**配方开源 + 二进制不随仓库分发**」——第三方程序文件全在 `.gitignore` 里。



---

## 1. 体积实测（2026-10-18）

| 指标                | 实测值          | GitHub 红线                     | Gitee 红线   |
| ----------------- | ------------ | ----------------------------- | ---------- |
| 跟踪文件数             | 1707         | —                             | —          |
| 仓库总大小             | **10.49 MB** | 建议 < 1 GB                     | 单仓库 500 MB |
| 最大单文件             | **375 KB**   | > 50 MB 警告 / > 100 MB **硬阻断** | 单文件 50 MB  |
| > 20 MB 文件数       | **0**        | —                             | —          |
| 打包产物（`*.paf.exe`） | **0 个**      | —                             | —          |

工作区里 `portableapps/App/` 下有约 **12.6 GB** 第三方程序文件，  
但它们**全部被 `.gitignore` 排除**，`git add -A` 根本不收录。实测命令：

```bash
git ls-files | wc -l                                  # → 1707
git ls-files -z | xargs -0 du -ch 2>/dev/null | tail -1
```

所以：

- **Gitee 社区版单仓库 500 MB 是本仓库需求的约 48 倍**；
- **GitHub 建议的 1 GB 是约 100 倍**；
- 不需要 Git LFS（单文件最大才 375 KB，离 50 MB 警告线差 130 倍）。

> 平台配额会变，推之前以各自控制台显示为准；但按 10.49 MB 这个基数，  
> 即使配额缩水到 50 MB 也依然放得下。

### 1.1 为什么能做到这么小

| 目录                                              | 是否进 git | 说明                                                   |
| ----------------------------------------------- | ------- | ---------------------------------------------------- |
| `<Pkg>/portableapps/App/AppInfo/**`             | ✅       | 配方元数据：`appinfo.ini`、`Launcher/*.ini`、`Custom.nsh`、图标 |
| `<Pkg>/portableapps/App/<程序名>/**`               | ❌       | 第三方程序二进制（约 12.6 GB）                                  |
| `_shared/configs/<Pkg>.yaml` + `gen_update_strategies.py` | ✅ | **更新策略配方**（生成器即配方）                          |
| `<产品根>/<Pkg>/update.py`                        | ❌（仓库外） | 上一条的生成物，随产品树在 `D:\Portapps`，用 `--clean` 重生成 |
| `<产品根>/<Pkg>/App/**`                           | ❌       | 构建产物（程序二进制）                                          |
| `<Pkg>/portableapps/Data/`                      | ❌       | 运行期生成的用户数据                                           |

`LICENSE`（MIT）只覆盖**配方本身**，不重新授权第三方软件；  
每个包的 `THIRD_PARTY_NOTICES.md` 声明第三方权利。二进制走 Release 或网盘分发，  
详见 §5。

## 2. 推送前必须做的一件事：改作者身份

当前两个提交的 author 是**占位符**：

```
PortableApps Maintainer (placeholder) <maintainer@localhost>
```

开源后这会永久留在公开历史里。推送前替换成你的真实身份  
（GitHub 和 Gitee 用同一个 git 身份即可，两边都认 email）：

```bash
cd <仓库根>
git config user.name  "你的名字"
git config user.email "你的邮箱@example.com"

# 把唯一一个根提交的作者改成你自己（--reset-author 是必须的）
git commit --amend --reset-author --no-edit

# 或者：保留两个提交，只改第一个，再交互变基
# git rebase -i --root   # 第一个提交标记 edit → git commit --amend --reset-author --no-edit → git rebase --continue
```

改完 `git log --format='%an <%ae>'` 应显示你的真实身份。

> `git config`（不带 `--global`）只写本仓库，不会污染你其他项目。

## 3. 推送到 GitHub

```bash
cd <仓库根>

# 1. 在 github.com 新建空仓库（**不要**勾选 "Add a README"，
#    否则本地历史和远端不一致，首次推送会被拒）

# 2. 关联远端（HTTPS 方式；已配 SSH 则可换 git@github.com:<你>/<仓库>.git）
git remote add origin https://github.com/<你的用户名>/<仓库名>.git

# 3. 首次推送
git push -u origin main

# 4. 之后日常推送
git push
```

推送成功后，`.github/workflows/ci.yml` 会自动触发。CI 做五件事，  
全程**不依赖任何第三方二进制**（因为二进制本来就不在仓库里）：

| 步骤 | 命令                                                               | 作用                                           |
| -- | ---------------------------------------------------------------- | -------------------------------------------- |
| 1  | `python -m compileall -q _shared/tools`                          | 工具链语法校验                                      |
| 2  | `python _shared/tools/audit_repo.py`                             | 39 包元数据 / appinfo / Launcher / 编码铁律          |
| 3  | `python _shared/tools/check_custom_nsh.py`                       | Custom.nsh 的 PowerShell 病态扫描                 |
| 4  | `python _shared/scripts/test_structure.py <Pkg> --ini-only` × 39 | PAL 结构校验                                     |
| 5  | bash 段                                                           | 确认没混入 > 20 MB 文件、`Data/`、`*.paf.exe`、`*.bak` |

> 第 2、3 步曾在新克隆里分别是「假红」和「假绿」，已于 2026-10-18 修复，  
> 详见 §6。

## 4. 推送到 Gitee

Gitee 与 GitHub 用两套独立远端，同一份本地提交推两边即可：

```bash
cd <仓库根>

# 1. 在 gitee.com 新建空仓库（同样不要初始化 README）
# 2. 加第二个远端
git remote add gitee https://gitee.com/<你的用户名>/<仓库名>.git

# 3. 推送
git push -u gitee main
```

查看/管理多个远端：

```bash
git remote -v          # 应看到 origin 和 gitee 各两行
git remote remove gitee   # 断开某个远端（不动本地提交）
```

**注意事项**

- Gitee 社区版单仓库上限 500 MB、单文件 50 MB——本仓库 10.49 MB / 375 KB 远低于此。
- GitHub 的 Actions 在 Gitee 上不可用；Gitee 有自己的 Gitee Go CI，  
  需要另写 `.workflow/` 配置。若暂时不想配，可只在 GitHub 开 CI，  
  推送前在本地手动跑一遍 §7 的清单。
- 若需两边同步标签：`git push origin --tags && git push gitee --tags`。

## 5. 二进制怎么分发（不进 git）

三条路，按场景选：

**A. GitHub Releases（推荐，单文件上限 2 GB）**

```bash
# 打包（在对应包目录下）
python <仓库根>/_shared\scripts\package-paf.py <PkgName>

# 打 tag 并推送
git tag -a v1.0.0 -m "首个公开发布版"
git push origin v1.0.0

# 用 gh CLI 上传发布包与 SHA256SUMS（产物在产品根，按包唯一命名）
gh release create v1.0.0 "D:\Portapps\<PkgName>.zip" "D:\Portapps\<PkgName>-SHA256SUMS.txt" \
  --title "v1.0.0" --notes "见 CHANGELOG"
```

Release 附件**不占用仓库体积配额**，也不受 100 MB 单文件硬限制。

**B. 网盘 + `update.py`**（最贴近本仓库既有工作流）

每个包的 `<产品根>/<Pkg>/update.py`（生成物，仓库外）已内置蓝奏云 /
GitHub API 等下载通道，二进制放网盘、版本信息由 `update.py` 探测，
仓库里只留策略配方（`_shared/configs/<Pkg>.yaml` + 生成器）。

**C. Gitee Releases**：附件单文件上限 100 MB，适合放小包；  
大包仍建议走 A 或 B。

> 无论哪条路，发布包里都应带上对应包的 `THIRD_PARTY_NOTICES.md`。

## 6. 别让 CI 变成假绿（2026-10-18 修复记录）

开源后第一个坑不是体积，是**门禁在新克隆里失效**。两类都已修：

**假红 —— `audit_repo.py` 在克隆里 0/39**

它默认同时审计 `dist/` 和 `portableapps/` 两棵树。但 `.gitignore` 排除了  
`dist/<Pkg>/App/` 下的二进制，克隆里 `dist/<Pkg>/` 只剩 `update.py`，  
于是 39 个包全员报「缺 `appinfo.ini`」。

修法：按包自适应——`portableapps` 恒审（随 git 分发的配方），  
`dist` 仅在本机已装配时才审；跳过时打印提示而非静默；  
一个包都没审计到直接判失败。

**2026-10-19 迁移后**：`dist/` 已不存在，上述"已装配"判断由
`_shared/_paths.py` 统一解析——本机有 `D:\Portapps\<Pkg>` 就审计产品树，
全新克隆自动只审 `portableapps/` 源树，行为不变、零配置。

**假绿 —— `check_custom_nsh.py` 扫的是空集（源仓库里同样是假绿）**

它的过滤条件是 `"ExecToStack" in 行 and "Command" in 行`。  
但 2026-10-17 起全仓已从「nsExec 内联 `powershell -Command`」改成  
「`FileWrite` 生成 `.ps1` + `-File` 传参」，ExecToStack 行**均不含 `Command` 字样**。  
实测证据：39 个 `Custom.nsh` 里 `ExecToStack.*Command` 命中 **0 行**——  
也就是说这道门禁从改动那天起就在报「无病态（ps 内联行 0 行）」。

修法：按当前真实形态重建扫描面——

```
FileOpen $N "<path>" / FileClose $N   → 记录 / 注销句柄目标
FileWrite $N "..."                    → 目标为 .ps1 才适用脚本规则；
                                        写 .ini / 日志则 NSIS 变量展开是
                                        故意的（QoderCNPortable 的
                                        state.ini 曾被误报）
裸 $var（白名单 $EXEDIR/$DataDirectory 等路径常量除外）、''、^|
-Command 内联回归、''、^|
```

病态扫描收敛到 `scan_file()` 单一实现，`audit_repo.py` 改为复用它，  
避免两份过滤条件再次漂移。**扫到 0 个文件 / 0 个相关行时判失败**——  
否则「路径不存在 → 零输出 → exit 0」就是永远的假绿。

修复后新克隆内实测：`audit_repo` 39/39、`check_custom_nsh` 39 包  
（写 `.ps1` 1495 行 / 执行器 369 行，全部干净）。

**教训（对后续所有门禁通用）**：门禁必须能报告「我这次到底检查了多少东西」。  
只报「没问题」而不报检查量的门禁，等于没有。

## 7. 推送前本地自检清单

```bash
cd <仓库根>

# ① 门禁复跑（期望 39/39）
python _shared/tools/audit_repo.py

# ② Custom.nsh 病态扫描（期望「全部通过」）
python _shared/tools/check_custom_nsh.py

# ③ 确认没有二进制/路径泄漏/密钥
python _shared/tools/audit_before_push.py

# ④ 编码回环校验（期望「编码零漂移」）
git clone -q <仓库根> /tmp/_verify_clone
python _shared/tools/verify_roundtrip.py <仓库根> /tmp/_verify_clone

# ⑤ 看看到底会提交什么（应只有配方元数据 + 文档 + update.py）
git add -A --dry-run | wc -l
```

自查通过后再 §3 / §4 推送。

## 8. 常见坑

| 坑                                | 现象                                 | 规避                                                       |
| -------------------------------- | ---------------------------------- | -------------------------------------------------------- |
| 远端仓库勾了「初始化 README」               | 首次 `git push` 被拒（无共同历史）            | 建**空**仓库；已犯则 `git pull --rebase origin main` 后再推         |
| 忘了改作者身份                          | 公开历史里留着 `maintainer@localhost`     | §2，推送前 `--amend --reset-author`                          |
| `App/` 被误提交                      | 仓库突然几个 GB，Gitee 直接超限               | 每个包的 `.gitignore` 已挡；`git add -A --dry-run` 先过目          |
| 用 `git add -f` 强推二进制             | 单文件 > 50 MB 警告、> 100 MB GitHub 硬阻断 | 二进制走 Release / 网盘（§5）                                    |
| Windows 下 clone 后 ini 乱码         | `.gitattributes` 的 `-text` 例外被覆盖   | 已在 39 个包的 `.gitattributes` 里补齐；改规则务必用 `git check-attr` 验 |
| Contributors 在 macOS/Linux clone | `eol=crlf` 与本地工具冲突                 | 已在根 `.gitattributes` 声明 `* text=auto eol=crlf`，告知贡献者     |
