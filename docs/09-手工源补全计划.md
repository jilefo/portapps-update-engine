# 09 · 手工源补全计划（32 个 manual 包）

> **目标**：把 `version_source.type=manual` 的 32 个包，按「上游能不能被程序读到版本」分档，
> 给出**可执行的推进顺序**和**每个源接完怎么验收**，让自动发版覆盖率从 7/39 往上走，
> 同时**不引入任何猜出来的 URL 或接口**。
>
> **口径**（本文所有结论的边界）：
>
> 1. 只采信**仓库内真实存在**的信息：`_shared/configs/<Pkg>.yaml` 的字段、
>    `<Pkg>/portableapps/App/AppInfo/appinfo.ini` 的 Publisher / Homepage、
>    `<Pkg>/THIRD_PARTY_NOTICES.md` 的「安装包来源」、各包 `README.md` / `CHANGELOG.md`，
>    以及 `_shared/update/_cache/<Pkg>/_last_check.json` 里**历史检测留痕**。
> 2. 仓库内查不到的一律写「待联网确认」，**不填推测域名、不填推测 repo、不填推测 API 路径**。
> 3. 分档只回答「上游版本能否被程序读到」，**与** `release_policy`（能否自动发布）**正交**；
>    两者叠加才是这条链路能否真正自动发版的前提，见 §4 的例外说明。
> 4. 现状基线（2026-10-19）：39 包中可自动检测 **7 个**——`api` 2（Cursor / Feishu）、
>    `github_releases` 3（Joplin / SoloMD / ZenBrowser）、`lanzou_folder` 2（FSCapture / ReNamer）；
>    其余 32 个 `manual`，`detect` 只标 `needs_manual`、不联网、不阻塞流水线。

---

## 1. 分档定义

| 档 | 判定标准 | 能到什么程度 | 接线方式 |
|---|---|---|---|
| **A** | 仓库内已能确认存在**公开结构化接口**（JSON API）或**GitHub Releases**，且历史上有成功检测留痕 | **可全自动**：检测 + 升版 + 打 tag 全链无人 | `github_releases`（`repo` + 可选 `asset_regex`）/ `api`（`url` + `version_field`） |
| **B** | 只有**官网下载页 / 固定直链**，需要 HTML 正则或页面内 JSON 才能拿到版本 | **半自动**：能自动检测，但页面改版就会失效（失效表现为 `regex_miss`，不会乱报版本） | `page_regex`（`url` + **`regex`**，注意字段名不是 `version_regex`） |
| **C** | 仓库内查不到任何公开源；或线索指向登录 / 网盘 / 客户端内更新等不可匿名编程读取的渠道 | **只能人工 ingest**：人工下载 → `update_engine.py ingest` 接管 | `manual`（保持现状） |

> 分档是**当前证据强度**，不是终局判断：C 档包只要联网核实到一个可匿名访问的版本事实源，
> 就可以升到 B，再稳定跑两周可考虑升 A。
>
> **关于「建议源类型」的取值**：表中只写引擎**真实支持**的类型。任务口径里提到的
> `direct`（固定直链）在 `update_engine.py` 里**并不存在**——`detect_one()` 只认
> `github_releases` / `api` / `page_regex` / `lanzou_folder` / `ctfile_dir` / `manual`。
> 所以「只有官网页面或固定直链」的包，建议类型统一写 `page_regex`（用正则从页面/文件名取版本），
> 而不是臆造一个 `direct` 字段。

## 3. 分档汇总与推进顺序

### 3.1 汇总

| 档 | 数量 | 包数占比 | 接完后的自动检测覆盖率 |
|---|---|---|---|
| A | 2 | 6% | 7 → 9 / 39 |
| B | 10 | 31% | 9 → 19 / 39（全接满） |
| C | 20 | 63% | 保持 manual |

> 注意：**「能检测」≠「会发版」**。上述 32 个包里有 5 个的 `release_policy` 不是 `manual_confirm`：
> `manual_only` 3 个（FoxitPDF、SublimeText、WPSOffice）、`blocked` 2 个（LobsterAI、WinClaw）。
> 两类表现不同：
>
> - `manual_only`：**照常检测**（会出现在 `--json` 报告里），但 `_matrix_allowed()` 默认把它挡在
>   `--matrix` 之外，所以只报版本、不发版；
> - `blocked`：`detect_one()` **一进门就短路**返回 `status=blocked`，**根本不联网**。这类包即使
>   配了 `github_releases` / `api`，也要先把 `release_policy` 改掉才会真的去请求上游。
>
> 要让它们也自动发版，得先把 `release_policy` 改成 `auto`——那是**另一个决策**，不在本计划内。

### 3.2 推进顺序（每批做完再进下一批）

| 批次 | 包 | 为什么排这个顺序 |
|---|---|---|
| **第 1 批** | CherryStudioPortable、CodeArtsPortable | 已有历史成功留痕，只需把 `_cache` 里的线索固化成 config，属于**最低风险、最快见效**；CodeArts 顺带补上 0.2.3 → 0.2.6 的落后版本 |
| **第 2 批** | SublimeTextPortable（B 中证据最强，已有 html 命中）→ eDiaryPortable（有实存下载页 URL）→ TyporaPortable（有实存直链，仅缺版本位置） | 三个都有仓库内实存 URL，验证成本最低 |
| **第 3 批** | 腾讯系 5 个：QQNTPortable、QQPortable、TIMPortable、WeixinPortable、WXWorkPortable | 同一厂商，抓取模板可复用；但页面多为 JS 渲染，**先验证一个再复制**，避免 5 个一起白做 |
| **第 4 批** | BaiduNetdiskPortable、WPSOfficePortable | 页面版本口径不确定（尤其 WPS 的 4 段版本），预期可能降 C |
| **第 5 批** | 其余 C 档 20 个 | 逐个联网核实；**核实一次只做三件事**：找版本事实源 → 确认可匿名访问 → 确认版本号可正则。三件缺一件就维持 `manual`，不做半成品配置 |

**每批的硬性节奏**：一次只改一个包的 `version_source` → 本地 `--json` 验证 → `--matrix` 复核 →
再动下一个。禁止「一次性把 10 个 config 都改了再统一测」——那样失败时无法定位是哪个源的问题。

## 4. 单源验收标准（每接一个源都必须全过）
