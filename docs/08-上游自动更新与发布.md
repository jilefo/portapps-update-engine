# 08 · 上游自动更新与发布

> 目标：**上游软件一出版本，仓库自动改版本号、自动打 tag、自动发出包级 Release**，
> 人不需要每天去看官网。
>
> 本文件描述的是 2026-10-19 新增的「检测 → 升版 → 打 tag」链路，它**不重写**
> 已有的包级发布流水线（`<Pkg>/.github/workflows/release.yml` × 39），
> 只是给它喂 tag。发布物与四平台整仓发布见
> [07 · 四平台自动发布](07-四平台自动发布.md)。

---

## 1. 三条链路的分工

```
                 ┌──────────────────────────────────────────┐
  每 6 小时 ────► │ scan job  upstream_scan.py --matrix        │
  / 手动触发      │  39 包逐个问上游 → 只留 update_available    │
                 └──────────────────┬───────────────────────┘
                                    │ matrix: [{project,current,latest}]
                                    ▼
                 ┌──────────────────────────────────────────┐
                 │ publish job  max-parallel: 1（逐包串行）    │
                 │  ① bump_package.py --project X --version Y │
                 │     · appinfo.ini Version / VersionFormat │
                 │     · _shared/configs/X.yaml              │
                 │     · X/CHANGELOG.md 顶部插入条目          │
                 │  ② test_structure.py X --ini-only（门禁）  │
                 │  ③ git commit + push main                 │
                 │  ④ git tag X@vY + push                    │
                 └──────────────────┬───────────────────────┘
                                    │ tag 推送
                                    ▼
                 ┌──────────────────────────────────────────┐
                 │ 既有 <Pkg>/.github/workflows/release.yml   │
                 │  test_structure → package_formula → 发 Release │
                 └──────────────────────────────────────────┘
```

| 环节 | 谁负责 | 是否新增 |
|---|---|---|
| 检测上游版本 | `_shared/tools/upstream_scan.py` | 新增 |
| 改版本号（三处） | `_shared/tools/bump_package.py` | 新增 |
| 编排 / 打 tag | `.github/workflows/auto-release.yml` | 新增 |
| 打包 + 发 Release | 既有 39 份包级 `release.yml`（生成源 `gen_release_workflows.py`） | **未改一行** |

**刻意不碰既有脚本**：既有 `.py` 的行为一律不改，`update_engine.py` 只被
`import`（复用它的 `detect_one()`），`test_structure.py` 只被当门禁调用。

## 2. 工具一：`_shared/tools/upstream_scan.py`

批量检测 39 个包的上游最新版本，**复用** `_shared/update_engine.py` 的检测能力
（GitHub Releases / 官方 JSON API / 页面正则 / 蓝奏云文件夹 / 城通网盘目录），
不新写一套抓取逻辑，避免两套结果打架。

```bash
# 全量，人读格式
python _shared/tools/upstream_scan.py

# 单个包
python _shared/tools/upstream_scan.py --project CursorPortable

# 机器可读（JSON，含 manual / failed / summary）
python _shared/tools/upstream_scan.py --json > report.json

# GitHub Actions matrix（只含 update_available 且策略允许的包）
python _shared/tools/upstream_scan.py --matrix

# 严格模式：matrix 只放 release_policy=auto 的包
python _shared/tools/upstream_scan.py --matrix --honor-policy
```

`--matrix` 输出示例（2026-10-19 本机实跑）：

```json
{"include": [
  {"project": "CursorPortable",    "current": "3.25.6",   "latest": "3.25.9",   "policy": "manual_confirm"},
  {"project": "SoloMDPortable",    "current": "5.0.1.0",  "latest": "5.0.3",    "policy": "manual_confirm"},
  {"project": "ZenBrowserPortable","current": "1.23.2.0", "latest": "1.23.3b",  "policy": "manual_confirm"}
]}
```

- 元素字段固定 `project` / `current` / `latest` / `policy`，可直接喂
  `strategy.matrix: ${{ fromJSON(...) }}`。
- **默认策略闸门**：`release_policy` 为 `blocked` 或 `manual_only` 的包永远不进 matrix
  （这两类不自动发布）；`auto` 与 `manual_confirm` 会进。
- **`--honor-policy` 严格模式**：只放 `release_policy == auto` 的包。若结果为 0 个，
  stderr 会明确提示「当前 0 个包的 release_policy 为 auto，需先把目标包的
  release_policy 改为 auto 才能自动发布」，并附上有更新的包按 policy 的分布，
  避免把「策略挡住了」误读成「上游没更新」。
- 无论是否严格模式，stderr 都会单列被策略排除的数量
  （形如 `release_policy 排除 5 个（blocked 2 / manual_only 3）`），
  `--json` 报告里对应 `policy_excluded` / `policy_excluded_blocked` /
  `policy_excluded_manual_only` / `policy_auto` / `update_available_gated` 等字段。
- 无更新时输出 `{"include": []}`，工作流据此 `has_updates=false`，publish 直接不跑。
- `version_source.type == manual` 的 32 个包标 `needs_manual`，**不阻塞**整体，
  只在报告里列名字。

退出码（只有三种）：

| 码 | 含义 |
|---|---|
| 0 | 检测完成（含「有更新」「无更新」「大部分 manual」） |
| 2 | 用法错误（参数不对 / 未知包名） |
| 3 | **本应联网的包全部失败**（网络不通 / 全部 HTTP 错误 / 配置错） |

退出码 3 是刻意设计的告警：让 CI 红，而不是安静地「今天没有更新」。

## 3. 工具二：`_shared/tools/bump_package.py`

一个包从 `current` 升到 `latest`，要动的恰好是三处，本脚本一次改完：

| # | 文件 | 改动 |
|---|---|---|
| 1 | `<Pkg>/portableapps/App/AppInfo/appinfo.ini` | 现代布局改 `[AppInfo] Version` + `VersionFormat`；旧式布局改 `[Version] PackageVersion` + `[AppInfo] DisplayVersion`（保留 `11.8.2.11734 Professional` 这类后缀） |
| 2 | `_shared/configs/<Pkg>.yaml` | `current_version` + `last_checked_at`（UTC，`YYYY-MM-DDTHH:MM:SSZ`） |
| 3 | `<Pkg>/CHANGELOG.md` | 顶部插入 `## [<version>] — <YYYY-MM-DD>` 条目（有 `## [Unreleased]` 则插在其后） |

INI 有两种真实布局（现代 19 个 / 旧式 20 个，2026-10-19 实测），脚本按包自动判分支：

```
现代：19 个   旧式：20 个
旧式 = BaiduNetdisk, CherryStudio, CodeArts, FSCapture, Feishu, FoxitPDF, KukuAI,
       QQNT, QQ, QuarkCloudDrive, ReNamer, SoloMD, SublimeText, TIM, Typora,
       WPSOffice, WXWork, Weixin, ZenBrowser, eDiary
```

```bash
# 演练（不写盘，只打印将要改的位置）
python _shared/tools/bump_package.py --project CursorPortable --version 3.26.0 --dry-run

# 实跑
python _shared/tools/bump_package.py --project CursorPortable --version 3.26.0
```

stdout 一行 JSON，`status` 取值：

| status | 含义 | 退出码 |
|---|---|---|
| `bumped` | 三处已改并写盘 | 0 |
| `skipped` | 目标版本与现值等价（`3.25.6` 与 `3.25.6.0` 视为同一版） | 0 |
| `dry-run` | 仅演练，未写盘 | 0 |
| `error` | 参数/文件/权限问题 | 非 0 |

安全细节：

- **编码**：**按原文件编码回写，不做统一转换**。`decode_text()` 按 BOM 判四种情形——
  UTF-16LE（`FF FE`）、UTF-16BE（`FE FF`）、UTF-8 带 BOM（`EF BB BF`）、
  无 BOM 的 UTF-8（按 `utf-8` 严格解码，解不开就报错，**绝不按 GBK 猜**）；
  `encode_text()` 用同一编码写回，UTF-16 由脚本手工补 BOM（不依赖本机字节序，
  跨平台稳定）。
  因此两条推论：**①带 UTF-8 BOM 的旧文件不会被剥 BOM**——39 份 `CHANGELOG.md`
  与 2 份 `appinfo.ini` 现存的 BOM 原样保留，diff 只会出现真正改动的行，不再有
  「首行整体变化」；**②无 BOM 的 UTF-8 仍写无 BOM**，不会凭空长出一个 BOM。
  > ⚠ 风险提示：`MiaoshouPortable` 的启动器 ini
  > （`MiaoshouPortable/portableapps/App/AppInfo/Launcher/MiaoshouPortable.ini`）
  > 是 **UTF-16LE**（`FF FE` 开头）。
  > `bump` 对它一样按 UTF-16LE 回写并保留 BOM，**手工 bump 也不会写坏**。
  > 真正会写坏的是人工用记事本 / VS Code 把它「另存为 UTF-8」——
  > 那一步与本脚本无关，改这类 ini 请直接用 `bump_package.py` 或带编码选项的编辑器。
- **行尾**：原文件 CRLF 就写 CRLF、LF 就写 LF（取文件内第一种出现的风格，CRLF 优先，
  兼容混排老文件），逐文件判定，不做全库统一。
- **版本号校验**：正则 `^[0-9][0-9A-Za-z._-]*$`——必须以数字开头，其后只允许数字 / 字母 /
  `.` `_` `-`。所以 `3.26.0`、`9.9.36-53644`、`2026.0917.1230.0`、`1.23.3b` 都能过；
  空串、`latest`、带空格或 `/` `\` `(` `)` 的输入一律拒绝。
- **幂等**：CI 重跑同一版本不会产生空提交（`skipped` + `git diff --cached --quiet` 双保险）。

## 4. 工作流：`.github/workflows/auto-release.yml`

| 项 | 配置 |
|---|---|
| 定时 | `cron: '17 */6 * * *'`（UTC，每 6 小时；避开整点高峰） |
| 手动 | `workflow_dispatch`，输入 `project`（留空=全部 39 包）、`dry_run`（只检测不写）、`honor_policy`（默认 `false`，勾选后只自动发布 `release_policy=auto` 的包） |
| 并发 | `concurrency: auto-release-${{ github.ref }}`，`cancel-in-progress: false`（排队不取消，避免半路掐断推 tag） |
| scan job | 跑 `upstream_scan.py --matrix`（`honor_policy=true` 时追加 `--honor-policy`），写 `matrix` / `has_updates` / `manual` / `honor` / `policy_auto` / `policy_gated` / `policy_excluded` 等 output，并把「被策略挡住 vs 确实无更新」的结论写进 Job Summary |
| publish job | `needs: scan`、`if: has_updates == 'true'`、`strategy.max-parallel: 1` |
| 逐包步骤 | 判 tag 是否已存在 → bump → `test_structure.py <Pkg> --ini-only` → commit+push → `git tag <Pkg>@v<ver>` → push tag |
| 令牌 | 优先 `secrets.RELEASE_PAT`，缺失时回退 `secrets.GITHUB_TOKEN` |
| 权限 | `permissions: contents: write` |

三个关键设计：

1. **`max-parallel: 1` 是硬要求**。每个包都要改工作区文件、提交并推 `main`，
   并行跑会互相覆盖工作区、`git push` 互相顶掉；串行 + push 失败时 rebase 重试 3 次。
2. **tag 已存在就整包跳过**。GitHub 不允许重复创建同名 tag/Release，
   所以先 `git rev-parse --verify refs/tags/<Pkg>@v<ver>`，命中则不做任何改动
   （`::notice` 记录）。这也让手工重跑是安全的。
3. **只 add 三个文件**：`appinfo.ini` / `CHANGELOG.md` / `_shared/configs/<Pkg>.yaml`，
   不用 `git add -A`，避免把 `matrix.json`、`report.json`、`__pycache__` 带进仓库。

### 4.1 令牌回退会发生什么（务必知道）

`RELEASE_PAT` 缺失时会回退 `GITHUB_TOKEN`，工作流**照常推 tag**，但 GitHub 有一条
防递归规则：**用 `GITHUB_TOKEN` 推送产生的 commit / tag 不会触发新的 workflow**。
也就是说 tag 推上去了、下游 `<Pkg>/release.yml` 不会跑、Release 不会出现。

因此回退时日志会打 `::warning` 与三行 ⚠ 说明，并给补推命令：

```bash
git push --force origin refs/tags/<Pkg>@v<ver>   # 用 PAT 或人工账号重推
```

### 4.2 `release_policy` 安全闸门（谁能被自动发布）

每个包的 `_shared/configs/<Pkg>.yaml` 里有 `release_policy`，它决定「上游有更新时，
这条链路敢不敢自动升版 + 打 tag」。四种取值的处理方式：

| release_policy | 含义 | 默认（`honor_policy=false`） | 严格模式（`--honor-policy` / `honor_policy=true`） |
|---|---|---|---|
| `auto` | 允许全自动发布 | **进 matrix，自动发布** | **进 matrix，自动发布** |
| `manual_confirm` | 允许自动发布，但保留「人可复核」的语义默认值 | **进 matrix，自动发布** | 不进 matrix（被严格模式挡住） |
| `manual_only` | 只允许人工发版 | **永不进 matrix**（只计入统计） | 永不进 matrix |
| `blocked` | 明确禁止发布（下架 / 合规 / 上游不可信等） | **永不进 matrix**（只计入统计） | 永不进 matrix |

要点：

- **`blocked` / `manual_only` 是硬闸门**，任何模式下都不会自动发布；它们仍然参与检测，
  只是被排除出 matrix，并在 stderr 与 `--json` 的 `policy_excluded*` 字段里单独计数，
  不会被悄悄忽略。
- **`manual_confirm` 是默认放行的**（保持历史行为不变）：不加严格模式时，
  上游一更新就会自动走到打 tag；需要「只有明确标了 `auto` 才能发」时再开严格模式。
- **严格模式用法**：
  - 命令行：`python _shared/tools/upstream_scan.py --matrix --honor-policy`
  - 工作流：`workflow_dispatch` 勾选 `honor_policy`（等价于给 scan 追加 `--honor-policy`），
    定时任务默认不勾（即保持默认放行 `manual_confirm`）。
  - 若严格模式过滤后为 0 个包，stderr 会给出：
    「当前 0 个包的 release_policy 为 auto，需先把目标包的 release_policy 改为 auto 才能自动发布」，
    并附上本次有更新的包按 policy 的分布，便于判断到底是「没更新」还是「策略太紧」。
    当前仓库（2026-10-19）**没有任何一个包是 `auto`**，所以严格模式必然为空——
    要启用它，先把目标包改成 `auto`。
- **matrix 为空时的 Job Summary 会区分两种原因**：①被策略闸门挡住
  （列出包名与其 policy，并提示改成 `auto`）；②确实无上游更新。不会再出现
  「明明上游有新版本，CI 却说没有更新」的误判。
- 当前分布（2026-10-19，共 39 包）：`manual_confirm` 34 / `manual_only` 3 / `blocked` 2，
  `auto` 0。

> 改策略只改 `_shared/configs/<Pkg>.yaml` 的 `release_policy` 一行，
> 不需要动工作流；工作流每次运行都会重新读取配置。

## 5. 需要的 Secrets

| 名称 | 是否必需 | 值 / 权限 | 说明 |
|---|---|---|---|
| `RELEASE_PAT` | **强烈建议** | 对 `owner/repo` 有 **Contents: Read and write** 的 fine-grained PAT（或 classic PAT 的 `repo` 域） | 唯一能保证「推 tag → 下游自动发布」的凭据 |
| `GITHUB_TOKEN` | 自动 | workflow 内置 | 回退用；**推 tag 不会触发下游**，只适合临时试跑 |

配置位置：仓库 → **Settings → Secrets and variables → Actions → New repository secret**。

PAT 有效期建议 90 天并在到期前轮换；过期后工作流会退化为 GITHUB_TOKEN 模式，
表现为「提交和 tag 都推上了，Release 页面没东西」——本文件就是为了让你能一眼定位这个现象。

### 6.1 补一个版本源的步骤

1. 找到**可编程读取**的版本事实来源（优先级：官方 GitHub Releases > 官方 JSON API >
   官方下载页正则 > 第三方重打包页）。
2. 在 `_shared/configs/<Pkg>.yaml` 里把 `version_source` 换成对应类型：

```yaml
# ① GitHub Releases（最稳）
version_source:
  type: github_releases
  repo: owner/name
  asset_regex: 'Setup-.*\.exe$'      # 只用来确认「有可用安装包」，可省

# ② 官方 JSON API
version_source:
  type: api
  url: https://example.com/api/version
  params: { platform: win32-x64 }     # 可选
  version_field: data.version_number  # 支持点分路径
  version_regex: 'V(\d+\.\d+\.\d+)'   # 字段里混了前缀时用
  url_field: data.download_link       # 可选，仅记录直链

# ③ 官方页面正则
version_source:
  type: page_regex
  url: https://example.com/download
  regex: 'Version\s+(\d+\.\d+(?:\.\d+)*)'   # 注意字段名是 regex，不是 version_regex

# ④ 蓝奏云文件夹分享（第三方重打包）
version_source:
  type: lanzou_folder
  url: https://xxx.lanzoum.com/bXXXXXXXX
  version_regex: 'App\.(\d+\.\d+(?:\.\d+)*)\.'

# ⑤ 城通网盘目录
version_source:
  type: ctfile_dir
  url: https://urlapi.ctfile.com/api/v2/listing
  params: { id: '1234567' }
  version_regex: '_(\d+\.\d+(?:\.\d+)*)-'
```

3. 立刻验证（**非 0 退出就说明源不可用，别提交**）：

```bash
python _shared/tools/upstream_scan.py --project <Pkg> --json
# 看 status：ok 才算接上；network_error / regex_miss / api_error 都是没接上
```

4. 首次接上后跑一次 `--matrix`，确认该包出现在 matrix 里（有更新时），
   再确认 `bump_package.py --dry-run` 能把三处正确改出来。

> `release_policy` 字段仍保留在配置里供人工参考，但**默认闸门不看 `manual_confirm`**——
> 只挡 `blocked` / `manual_only`，所以 `manual_confirm` 的包只要进了 matrix 就会自动升版并发布，
> 等于把 7 个自动源包的 `manual_confirm` 实际执行成 `auto`。要恢复人工确认，见 §7-④。

## 7. 已知限制

| # | 限制 | 说明 / 应对 |
|---|---|---|
| 1 | **`GITHUB_TOKEN` 推送不触发下游** | GitHub 防递归机制。tag 能推上，包级 `release.yml` 不跑 → 无 Release。必须配 `RELEASE_PAT`；回退时日志会明确警告并给补推命令 |
| 2 | **发布物是配方，不是二进制** | 包级 Release 只含 `portableapps/` 元数据 + LICENSE + THIRD_PARTY_NOTICES + README（第三方程序在 `.gitignore` 外）。要发可运行包需自建 runner 跑 `portableapps.yml`，见 07 文档 §2.1、§7 |
| 3 | **只有 7/39 包有可自动检测的版本源** | 其余 32 个标 `needs_manual`，不阻塞流水线、也不会被自动发版。单源接法见 §6.1，32 包的 A/B/C 分档与推进顺序见 [09 · 手工源补全计划](09-手工源补全计划.md) |
| 4 | 自动升级绕过 `release_policy: manual_confirm` | 默认口径下 `--matrix` 只挡 `blocked` / `manual_only`，`manual_confirm` 照样自动发版。要人工确认：手动触发时勾 `honor_policy=true`（只放 `release_policy=auto`），或把 `auto-release.yml` 的 `schedule` 注释掉只留 `workflow_dispatch` |
| 5 | GitHub 定时任务会延迟 | 高峰期 cron 可能晚 5–20 分钟；且仓库连续 60 天无提交活动时，schedule 会被自动停用（需进 Actions 页手动启用） |
| 6 | BOM / 编码一律按原样保留 | `bump` 按原文件编码回写（UTF-16LE / UTF-16BE / UTF-8 带 BOM / 无 BOM UTF-8 四种），带 BOM 的旧文件**不会**被剥 BOM，diff 只含真正改动的行。想统一编码要另跑一次性工具（如 `fix_strip_bom.py`），不属于 bump 的职责 |
| 7 | 版本号等价判定是宽松的 | `3.25.6` = `3.25.6.0`。上游若只改第四位而配置里只写三位，会被判成 `skipped`；需要精确到第四位就在 configs 里写全 |
| 8 | 上游改版会把检测打回 manual | 页面结构 / API 字段 / 反爬变化 → `regex_miss` / `api_error`。此时**不会**乱报版本，也不会失败整个流水线（除非全部联网包都失败，才退出码 3 报警） |
| 9 | 自动发布不做内容审查 | bump 只写版本号与 CHANGELOG 条目，不校验上游改动是否破坏便携化（如安装器换成 MSIX）。发版后仍需人工抽查一次启动 |
| 10 | 提交身份是 `github-actions[bot]` | 用 PAT 推送时提交人仍写 bot 身份，不是 PAT 所有者；需要审计归属请自行改 `git config user.*` |

## 8. 日常运维

```bash
# ① 今天哪些包有更新（只读，本机随时可跑）
python _shared/tools/upstream_scan.py

# ② 只看 matrix（CI 用同一份输出）
python _shared/tools/upstream_scan.py --matrix

# ③ 手动演练某个包的升版（不写盘）
python _shared/tools/bump_package.py --project CursorPortable --version 3.25.9 --dry-run

# ④ 本地把链路走完（会真改文件，注意先 commit）
python _shared/tools/bump_package.py --project CursorPortable --version 3.25.9
python _shared/scripts/test_structure.py CursorPortable --ini-only

# ⑤ 语法门禁（不联网、不写盘）
python -m compileall _shared/tools
python _shared/tools/gen_release_workflows.py --check
```

排查表：

| 现象 | 大概率原因 |
|---|---|
| 有 tag、没 Release | 用了 GITHUB_TOKEN 推 tag（§7-①）；配 `RELEASE_PAT` 后重推 tag |
| scan 红了（退出码 3） | 全部联网包都失败：检查 runner 出网、上游域名可达性 |
| matrix 一直是空 | 上游确实没更新，或 configs 里 `current_version` 已等于最新 |
| tag 存在但内容不对 | tag 已存在会被跳过（§4-②）。要重发先删 tag + Release 再跑 |
| bump 报 error | 包名拼错 / `--version` 不合规 / 目标文件被占用（Windows 上常见） |

## 9. 相关文件

| 文件 | 作用 |
|---|---|
| `_shared/tools/upstream_scan.py` | 批量检测（`--project` / `--json` / `--matrix`），复用 `update_engine.detect_one` |

| `<Pkg>/.github/workflows/release.yml` × 39 | 下游包级发布（tag `<Pkg>@v*`），由 `gen_release_workflows.py` 生成 |
