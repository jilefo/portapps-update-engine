## 1. 为什么用 rename 而不是「复制 → 校验 → 删源」

这是本次方案的核心决策，直接由磁盘空间逼出来：

| 事实 | 数值 |
|---|---|
| dist 总体积 | 59.12 GiB |
| D: 盘当时剩余 | 30.6 GB |

**空间不够复制**。但源（`D:\Projects\PortableApps\<Pkg>\dist`）与目标
（**`D:\Portapps`**）在**同一个卷**上，于是 `os.rename` 是更优解：

- **零拷贝、零额外空间**——只改目录项，59 GB 瞬时完成；
- **原子**——要么整棵树过去，要么原样不动，不存在"搬了一半"的中间态；
- 比"复制→校验→删源"**更安全**——后者在删源之前磁盘占用翻倍（放不下），
  且删源是二次破坏动作。

代价与对策：

- rename 后**指向树内绝对路径的 junction 会失效** → 工具自动重定点（§3.1）；
- 无法做"物理备份" → 用**预迁移 manifest**（逐文件 SHA-256）替代，
  校验强度不降（真出了事能精确定位到哪个文件不一致）。

## 5. 事故、缺陷与修复（本次真实踩到）

### 5.1 ★ ComatePortable junction 重定点「假成功」

**现象**：迁移日志记 `重定点 1`，但审计发现该 junction 目标仍是
**已迁走的旧路径**（悬空）。

**根因**：`repoint_junction()` 用了 `old_target.replace(str(old_root), str(new_root))`，
而该 junction 的目标被写成**小写盘符** `d:\Projects\...`，
`str.replace` **大小写敏感** → 替换静默不匹配；
更要命的是 **`mklink /J` 对不存在的目标也返回 0**，
于是"重建成功"的判断只看返回码 → 假成功。

**修复（工具三处）**：

1. 抽出 `replace_root_prefix()`，用 `lower().find()` 做**大小写不敏感**替换，
   匹配不到返回 `None` 而不是原样返回；
2. 重建前**校验新目标真实存在**——拒绝建立指向空路径的悬空 junction；
3. `mklink` 之后**回读 junction 目标并与预期比对**（回读校验），
   任一不符就删除重建的 junction 并**回滚到旧目标**，不让包停在更糟的状态。

**现场修复**：用修好的工具重跑，junction 目标已改为
`D:\Portapps\ComatePortable\App\Comate\...\zulu-cli\bin`，
穿透访问可见 `zulu` / `zulu.cmd` 两个文件 ✓。

> 顺带修掉一个健壮性问题：中文 Windows 下 `cmd /c mklink` 输出是 GBK，
> `capture_output=True, text=True` 按 UTF-8 解码会在后台线程抛
> `UnicodeDecodeError`，真实报错被 traceback 盖掉 → 显式指定
> `encoding="gbk", errors="replace"`。

**衍生工具**：为把这类问题变成可巡检项，新增
`_shared/tools/audit_junctions.py`（junction 健康度审计，
逐条回读目标并验证可达，区分包内/相对/树外三类，自报覆盖度）。
它立刻派上用场——扫出 12 条悬空联接（§5.2）。

### 5.4 ★★ junction 重定点整段是死代码（本次最严重的一处）

**现象**：WorkBuddyPortable 补迁后，工具输出两条
`[WARN] junction 已不存在: ...\dist\WorkBuddyPortable\Data\...`，
但整体仍报 `PASS 1 / FAIL 0 / SKIP 0`。

**追下去发现这是本次最严重的一处，而且是三重叠加**：

```
# 缺陷 1：用迁移「前」的路径去定位 junction
inside_juncs = [(Path(src) / j["rel"], ...)   # src = <Pkg>/dist/<Pkg>
...
os.rename(str(src), str(dst))                 # ← 这一步之后 src 整棵没了
...
for jp, tgt in inside_juncs:
    if not jp.exists():                       # ← src 都没了，恒为 False
        print("[WARN] junction 已不存在")      #   于是全部 continue
        continue                               #   重定点一个都没执行
```

1. **路径错**：第 4 步按 `src`（迁移前）拼出绝对路径，第 5 步 rename 之后
   `src` 整棵消失 → 第 6 步 `jp.exists()` 恒为 False → 整段 `continue`。
   **重定点功能从头到尾没生效过**，Comate 那一例是事后用临时脚本手工修的。
2. **判定错**：即使路径改成 `dst / rel`，`Path.exists()` **会跟随目标**——
   目标悬空时返回 False，恰好跳过最需要修的那些 junction。
   必须用链接本身的属性 `is_junction()`（GetFileAttributesW 不穿透）。
3. **校验假绿**：`diff_manifest` 只比 `junction_count`。目标是绝对路径，
   换根必变，所以按绝对值没法比——于是干脆没比，
   只比数量 → **悬空联接照样 PASS**，前面那 38/38 就是这么绿的。

**三处一起修**（`_shared/tools/migrate_dist.py`）：

| # | 修复 | 对应缺陷 |
|---|---|---|
| 1 | 存 `rel` 而非绝对路径，第 6 步用 `dst / rel` 定位 | 路径错 |
| 2 | 存在性判定 `jp.exists()` → `is_junction(jp)`（不跟随目标） | 判定错 |
| 3 | manifest 增记 `target_rel`（树内目标相对路径），`diff_manifest` 逐个比 (rel, inside, target_rel) | 校验假绿 |
| 4 | 新增 `repoint` 子命令（幂等，可预览），用于修历史损伤与交叉确认 | 可修复性 |

**判定边界的取舍**（避免从"假绿"摆到"假红"）：
只有**迁移时目标在树内**的 junction 才是迁移的责任。树外目标
（宿主重定向、历史遗留悬空联接）由 PAL 在运行时创建、退出时拆除，
数量随每次冒烟起落。若一律判负，39 包会假红 9 包——实测那 12 条
全是 2026-10-17 前 `GreenSoftMake\Work\<Pkg>\` 的历史悬空联接，**0 条存在**，
早已与本次迁移无关。故树外 junction 只记备注、不判负。

**受控复现（真实包上验证，非推演）**：把 WorkBuddyPortable 一个 junction
的目标改回已搬走的旧路径，两种判定对比：

| 判定 | 结果 |
|---|---|
| 旧（只比数量） | **PASS** ← 假绿 |
| 新（逐个比目标） | **FAIL：`迁移时树内 junction 现已不在`** |
| 用 `repoint --yes` 还原后 | PASS，穿透可见目标内容 |

**单测 15 项全 PASS**，含：旧路径 `.exists()` 恒 False（缺陷复现）、
新路径 `is_junction()` 为 True、正样本自比 PASS（证明不是恒红）、
树外 junction 被清理不判负但留备注、重复重定点幂等。

**全量回归**：新判定下 39 包 **39 PASS / 0 不符**，junction 总数 4。

> 三条教训：
> ① **先做动作再定位对象时，路径要用动作后的形态**——rename 会搬走整棵树。
> ② **判链接在不在，要用链接本身的属性，不要用 `.exists()`**（跟随目标）。
> ③ **校验只比数量等于没比**；必须折算成跨根可比的形态再逐个比。
> ④ 顺带：写期望值时别用被测函数那一套逻辑现场算——我在单测里用
> 大小写敏感的 `.replace` 算期望值，把 bug 本身当成了正确答案（第 19 条）。
