## 2. 为什么放在 `dist/<Pkg>/`，而且要自包含

第一版把策略放在 `_shared/update/<Pkg>.py`，39 个脚本共享一个 `_base.py`。
**这个设计是错的**：用户拿到的是 `dist/<Pkg>/` 这个目录，通常整个拷走，
此时 `_shared/` 根本不在旁边，`import` 直接失败。

改成：

```
<Repo>/<Pkg>/dist/<Pkg>/
├── <Pkg>.exe
├── help.html
├── update.py          ← 本包的更新脚本，引擎内联，单目录可运行
├── App/
└── Data/              ← 用户数据，更新时永不触碰
```

- **自包含**：39 份引擎代码重复，换来"拷走就能用"，取舍值得。
- **批量执行器只做调度**：`_shared/update/runner.py` 并发 `subprocess`
  调用各包 `update.py --check --json`，自己不实现任何更新逻辑，
  保证单跑与批跑行为一致。
- **生成器 + 模板**：`_shared/tools/update_template.py`（引擎）
  + `gen_update_strategies.py`（39 个包的 SPEC）→ 产出 39 个 `update.py`。
  改策略改 SPEC 后重生成，不手改生成物。

## 4. 端到端实测（3 个包真实升级）

### 4.1 SublimeText 4200 → 4215（html 源 + zip 包）

```
当前=4200.0.0.0  最新=4215  -> UPDATE
下载 -> sublime_text_build_4215_x64.zip   完成 26.8MB
剔除上游 Data（PAL 自己管理，不能用上游的）
禁用自带更新器 update_installer.exe
备份 App\SublimeText -> _shared\update\_backups\SublimeTextPortable\SublimeText-20261018-113329
已替换 App\SublimeText
版本已回写 4215.0.0.0
结构校验：PASS
```

| 检查 | 结果 |
|---|---|
| `PackageVersion` / `DisplayVersion` | 4200.0.0.0 → **4215.0.0.0** |
| 上游 `Data/` 是否残留 | 无（已剔除） |
| `update_installer.exe` | 已改名 `.disabled-by-engine` |
| `Data/` 用户数据 | 未被触碰 |
| 结构校验 | PASS |
| 真实启动冒烟 | `sublime_text.exe` 出现、Data 新写入、**0 弹框 → PASS** |

**回滚实测**：把版本改回 4200 复现更新场景 → 再更新（生成含 `_appinfo` 的
新备份）→ `--rollback` → 版本退回 4200.0.0.0，文件同步还原，无 `_appinfo` 残留；
随后重新应用回到 4215。

### 4.4 实测中修掉的 2 个真问题

**① PATH 里靠前的 7-Zip 是坏的**。`<本机工具目录>/tools\7z.EXE` 旁边缺
`7z.dll`，表现是：`7z` 无参数 → 打印帮助、rc=0（**看起来是好的**），
但 `7z x 真包` → `Load Error: 7z.dll` + `Can't open as archive`、rc=2。
而它排在 `C:\Program Files\7-Zip\7z.exe` 前面，导致所有 NSIS/Inno 包
**静默解包失败**。修法：拿**真实文件**逐个试候选，第一个成功的才算数，
失败时打印 7z 的输出尾巴。

**② 安装器是多层结构**。`zen.installer.exe` 解出 `core/` + `setup.exe`
两个顶层项，而"剥单层外壳"只在**只有 1 个顶层项**时生效 → 会把 `core\`
套进 `App\Zen\`。修法：新增 `strip_root` 字段（Zen 配 `core`）+ `--strip`
命令行覆盖。

**③ 顺带**：`smoke_real.py` 猜进程名错两次（`sublime_text.exe`、`zen.exe`），
表现为"Data 有新写入、0 弹框却判 FAIL"——应用其实正常。已显式登记。

## 5. 安全设计

| 机制 | 说明 |
|---|---|
| **dry-run 默认** | 不加 `--execute` 只演练，不落地 |
| **Data 永不触碰** | 只替换 `App\<程序子目录>`，数据在 `dist/<Pkg>/Data/` |
| **自动备份 + 回滚** | 保留最近 3 份；失败自动回滚；`--rollback` 可手动退回 |
| **版本号同步回退** | 备份时存 `appinfo.ini`，回滚时一起退 |
| **下载原子化** | 写 `.part` 再改名，中断不会留下"看起来下完了"的半截包 |
| **再便携化** | 剥外壳目录 / 剔除上游 `Data/` / 禁用自带更新器 |
| **临时故障兜底** | 取新失败（限流 / 断网）退回上次成功结果，状态标 `CACHED`，不谎报"包坏了" |
| **GitHub 限流应对** | 支持 `GITHUB_TOKEN` / `GH_TOKEN`（60 → 5000 次/小时）；403 给出明确提示 |
| **7-Zip 逐个试** | 拿真实文件试候选，避免 PATH 里的坏 7z 让解包静默失败 |

## 6. 用法

```bash
# 单个包（在其便携目录下）
cd SublimeTextPortable/dist/SublimeTextPortable
python update.py --check                      # 只检测，只读
python update.py --update                     # 演练
python update.py --update --execute           # 真更新
python update.py --ingest <下载好的包> --execute   # 人工下载后接管
python update.py --rollback                   # 回滚

# 批量（仓库根）
python _shared/update/runner.py --check --all
python _shared/update/runner.py --check --auto          # 只查有在线源的
python _shared/update/runner.py --check --report        # 出 Markdown 报告
```

**人工接管的包**（32 个）也走同一套：`--ingest` 会自动解包、剥外壳、
剔除上游 Data、禁用自带更新器、备份、替换、探测新版本号回写、结构校验，
人工成本只剩"去官网下载这一步"。
