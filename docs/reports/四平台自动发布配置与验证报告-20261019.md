## 2. 发现的问题与取证

### 2.1 ★★ 34 份 release.yml：三处缺陷叠加 = 全绿 + 零产物

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | 附件写 `<Pkg>/dist/*.7z`，而打包器只产 `.zip` | `package-paf.py` 第 37 行只有 `make_archive(..., "zip")`；全库无任何 7z 生成器 |
| 2 | 打包步带 `--checksum-only`，该开关**跳过打包** | `package-paf.py`：`if "--checksum-only" not in sys.argv:` 才 `make_archive` |
| 3 | 无产物时 `[WARN] + return 0`，不失败 | 同上：打印 `[WARN] 未找到本包 zip` 后 `return 0` |

三重叠加的净效果：**34 条流水线全绿，附件 0 个，无人报警。**
统计确认：含 `dist/*.7z` 的 34 份、含 `--checksum-only` 的 34 份。

### 2.2 ★ 64 份附件路径写死，与动态解析必然对不上

`<Pkg>/dist/*.zip` 看着是工作区相对路径，但产物实际落在 `_paths.artifact_root()`。
把 `_paths` 置成 CI 的真实状态（`portapps_root.txt` 缺席——它已被 `.gitignore`
排除；默认产品根不存在）后实测：

```
CI 上 product_dir    = <内置默认产品根>\CursorPortable
CI 上 zip 产出      = <内置默认产品根>\CursorPortable.zip
release.yml 却上传  = <工作区>\CursorPortable\dist\*.zip     ← 必然不是同一个
```

换句话说，**写死的那 64 份没有一份能对上**。

### 2.3 包级发布的内容本身就没有意义（前提取证）

| 位置 | 内容 |
|---|---|
| 源树 `portableapps/App/` 入库文件 | **9 个**（全是 AppInfo / Launcher / 图标元数据） |
| 产品树 `App/` | `AppInfo` + `Cursor`(995 MB) + `default` |

第三方程序被 `.gitignore` 排除 → CI 上 `build-portable.py` 的产物是
「有启动器、无程序」的空壳。发布它没有意义。

**处置（用户选定）**：包级发布改为发布**配方**
（`portableapps/` + LICENSE + THIRD_PARTY_NOTICES.md + README.md）。

### 2.4 tag 作用域冲突

39 份 `release.yml` 全部 `on: push: tags: ['v*']`（实测 36/36 如此）。
推一个 `v1.7.0` → 39 条流水线同时触发，每条都去创建同名 Release。

### 2.5 其它

| # | 问题 | 数量 |
|---|---|---|
| a | 缺 `permissions: contents: write`（建 Release 会 403） | 34 份 |
| b | 缺 `test_structure` 门禁与 `gen-sbom` 步骤 | 34 份 |
| c | `portableapps.yml` 上传 `path: <Pkg>/dist/`——迁移后该目录已不存在 | 36 份 |
| d | 缺 `release.yml` / `portableapps.yml` 的包 | 3 个（FoxitPDF / SublimeText / WPSOffice） |
| e | `JoplinPortable` 混有 4 份上游模板遗留 workflow | 4 份 |
| f | **已入库**的备份文件（`Custom.nsh.bak6/.bak7`） | 6 个 |

(e) 的 4 份：`automerge.yml`（自动合并指定作者的 PR）、
`build-linux.yml` / `build-windows.yml`（引用上游 `Other/Update/Update.ps1`，
且 `endsWith(github.repository,'Portable')` 在本仓恒假）、
`up-release.yml`（运行时从第三方仓库 master 拉脚本执行）。

（`grep -E '...|\.bak'` 会命中），且会被发布流程带进公开产物。

## 3. 修复内容

### 3.1 新增三个脚本

| 脚本 | 作用 |
|---|---|
| `_shared/scripts/package_formula.py` | 打单包配方 zip + SHA256。**以 git 跟踪集为准**（见 §4.3），带体积护栏，报告打包文件数与总字节 |
| `_shared/tools/print_artifact_paths.py` | 解析产物真实路径，按 GITHUB_OUTPUT 输出；**缺产物 exit 1** |
| `_shared/tools/gen_release_workflows.py` | 78 份包级 workflow 的唯一生成源 + `--check` 门禁 |

修法要点（不是再改一遍字符串，而是改变维护方式）：
**workflow 由生成器产出，附件路径不写字面量，由脚本从唯一定义处解析。**

### 3.2 包级 release.yml 模板

```yaml
on:
  push:
    tags: ['<Pkg>@v*']          # 带包名前缀，不再 39 条抢同一个 Release
permissions:
  contents: write               # 原 34 份缺失
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - 结构校验（test_structure.py <Pkg> --ini-only）
      - 打包配方（package_formula.py <Pkg>）
      - 解析产物路径（print_artifact_paths.py <Pkg> → GITHUB_OUTPUT）
      - 创建 Release（files 用 ${{ steps.artifacts.outputs.* }}，不写死路径）
```

### 3.3 包级 portableapps.yml

- `PORTAPPS_ROOT` 提到 **job 级** `env:`（原先若写在 step 级，后面三个 step 读不到）
- 指向 `${{ runner.temp }}\portapps`：不依赖 D: 盘存在，也不把产物写进工作区
- `path:` 改为 3 行动态路径，`if-no-files-found: error`

### 3.4 清理清单（已备份）

```
build/cleanup-backup-20261019/          （被 .gitignore 覆盖，不入库）
├── JoplinPortable/.github/workflows/{automerge,build-linux,build-windows,up-release}.yml
└── {QQNT,QQ,TIM}Portable/.../Custom.nsh.bak{6,7}-20261017
```

删除用 `git rm`（受版本控制，旧内容可从 `git show HEAD:<path>` 取回），
**未**在受控目录里另留 `.bak`。


### 4.2 端到端演练（按 CI 上完全相同的三步）

对三个原先缺 workflow 的包逐个跑通：

```
WPSOfficePortable    [PASS] 结构校验 → 44 文件 / 2034.8 KiB → 路径解析 ok

```

全量：`配方打包：成功 39 / 失败 0 / 合计 39`

### 4.3 ★ 打包器以 git 跟踪集为准（修掉了自己刚犯的错）

首版用 `rglob` 扫文件系统，把本机未跟踪的备份打进了公开产物：

```
rglob  → 18 项（含 appinfo.ini.bakfix、Custom.nsh.bak-dot-20261018 两个垃圾）
git    → 15 项（与 CI 新克隆完全一致）
```

教训已写入 `04-避坑手册` §10.5：本机与 CI 得到两份不同产物，且垃圾被发布出去。

### 4.4 路径解析工具的正负样本

```
正样本（产物存在）  → formula=...\CursorPortable-formula-3.25.6.0.zip   rc=0
负样本（未打包过）  → [FAIL] 产物不存在：...FSCapturePortable-formula-*.zip   rc=1
```

关键：负样本走 **stderr**、**不向 stdout 输出任何内容**（不污染 GITHUB_OUTPUT）、
**rc=1**（不会像 `package-paf.py` 那样 WARN 后 return 0）。

```bash

# 只恢复工作流：重新生成即可
```
